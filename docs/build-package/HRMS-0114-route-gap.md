## Zero identity check at all — 0 unexplained (was 9, then 5)

All 5 that showed up were investigated individually (not guessed at):

- 3 turned out to have real protection tonight's audit tool structurally
  can't see — `msgraph.py`'s mail/calendar routes check a session cookie
  **inside the function body** (`_require_account()`), not via FastAPI's
  `Depends()`. Verified safe; guarded by
  `tests/test_route_permission_audit_real_app.py::test_msgraph_manual_exception_guard_still_has_real_protection`
  so this doesn't silently rot if that function is ever removed.
- 1 was a clear, mechanical oversight and got fixed directly tonight:
  `GET /hr-assignments/by-candidate/{candidate_id}` now has
  `require_permission("candidate.view")`, matching its sibling
  PATCH/DELETE routes.
- 1 was clearly intentional and got moved to the public-routes list:
  `GET /msgraph/auth/callback` (an OAuth redirect target — structurally
  can't require a token, since it fires before any session exists).
- 1 was explicitly documented as public in its own route summary and got
  moved to `PUBLIC_ROUTE_TEMPLATES`: `POST /jobs/{job_id}/apply`
  (candidates applying from a public job board). **This needs rate
  limiting per Phase 1 B4** — not yet enabled anywhere in this app, see
  the developer handoff.

**2 remain as genuine open questions — need a decision, not a guess:**

1. **`GET /jobs/active-jobs`** — its own docstring says "Authenticated
   HR/Admin user" but has no dependency at all. Two possible fixes with
   opposite implications:
   - It's meant to be internal-only → add
     `dependencies=[Depends(get_current_hr_or_admin)]`
   - It's meant to be a public job board listing (the `Jobs.jobStatus`
     model already has a `"public"` value, suggesting this was planned)
     → add `"/jobs/active-jobs"` to `AuthenticationMiddleware.PUBLIC_ROUTES`
   Picking wrong either leaks internal job data publicly, or breaks an
   intended public job board feature. **Decide which one this is meant
   to be, then apply the matching one-line fix above.**

2. **`POST /ai-agent/webhook/email-reply`** — explicitly documented
   "No auth required", with a comment acknowledging it needs hardening
   that was never done ("or add bearer token via dependencies as needed
   in production"). It processes an incoming candidate reply through
   Gemini and merges the result into that candidate's record — callable
   today by anyone who can guess/enumerate a `candidate_id`, with no
   rate limiting either. It's meant to be called by **both** external
   services (a scheduler, an email webhook) **and** manually from the
   HR portal — a `Depends(get_current_hr_or_admin)` would break the
   external-caller use case, so a plain permission check is the wrong
   fix here. **Needs a shared-secret / webhook-signature style check**
   (e.g. a header compared against a value in `.env`, following the
   secrets-manager pattern already used everywhere else) — a small
   design decision, then a small, mechanical implementation.

## Coarse auth only — 49 routes (tracked, not an emergency)

These already have a real identity check — `get_current_candidate`
(candidate can only reach their own record) or
`get_current_hr_or_admin`/`get_current_internal_user` (any logged-in
staff member) — just not a specific `require_permission(...)`. Not
dangerous today, but worth tightening as this codebase's RBAC coverage
matures. Full current list: run the command above, second section.
Categories, unchanged from the original sweep:

- Candidate self-service (aadhar, pan, education, experience, documents,
  offer response, job application status, etc.) — the coarse check here
  (`get_current_candidate`, self-scoped by definition) is arguably
  already the *right* model, not a gap to necessarily "fix."
- Internal/HR staff (hr/users/*, interviews/*, offer-letter approval
  queue) — these are better candidates for tightening to a specific
  permission, since "any logged-in staff member" is broader than
  intended for things like viewing all users or approving offers.
- AI agent conversation read endpoints — review whether these need
  `candidate.view` specifically.

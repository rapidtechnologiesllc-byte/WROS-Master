Generated by `app/core/route_security_audit.py` against the real app
(`app.main:app`). Started at 58 apparently-ungated routes on
2026-07-20; ended the same day at 0 unexplained gaps.

Re-run any time to refresh:

```bash
python -c "
from app.core.route_security_audit import find_routes_missing_permission_declaration, find_routes_with_only_coarse_auth
from app.middleware.auth_middleware import AuthenticationMiddleware
```

## Zero identity check at all — 0 unexplained

The 58 initial hits broke down as:

- **~49 already had real protection** the first pass of the audit tool
  couldn't see (`get_current_candidate`, `get_current_hr_or_admin`,
  `get_current_internal_user`, `get_current_user`) — not RBAC-fine-grained,
  but a real identity boundary. These are now tracked separately as
  "coarse auth only" (below), not counted as dangerous.
- **1 clear oversight, fixed directly**: `GET /hr-assignments/by-candidate/{candidate_id}`
  now has `require_permission("candidate.view")`, matching its sibling
  PATCH/DELETE routes.
- **1 structurally-must-be-public, reclassified**: `GET /msgraph/auth/callback`
  (OAuth redirect target — fires before any session exists) is now in
  `AuthenticationMiddleware.PUBLIC_ROUTES`.
- **1 intentionally-public, reclassified**: `POST /jobs/{job_id}/apply`
  (candidates applying from a public job board, explicitly documented
  as such) is now in `AuthenticationMiddleware.PUBLIC_ROUTE_TEMPLATES`
  (a new segment-aware matcher, since a plain string match against a
  `{job_id}` placeholder would never match a real resolved request
  path). **Still needs rate limiting per Phase 1 B4** — not yet enabled
  anywhere in this app.
- **3 verified safe, left alone**: the `msgraph.py` mail/calendar routes
  check a session cookie *inside the function body*
  (`_require_account()`), invisible to `Depends()`-tree scanning but
  real. Guarded by
  `test_msgraph_manual_exception_guard_still_has_real_protection` so
  this can't silently go stale if that function is ever removed.
- **2 genuine open questions, resolved after confirming actual intent**:
  - `GET /jobs/active-jobs` — its query mixes `"active"` and `"public"`
    status jobs together, so making the whole endpoint public would
    leak internal, not-yet-published jobs. Confirmed internal-only →
    now has `require_permission("job.view")`.
  - `POST /ai-agent/webhook/email-reply` — needed to work for both
    external callers (a scheduler, a mail webhook) and manual HR-portal
    use. Now requires either a shared secret (`X-Webhook-Secret` header,
    checked against `WEBHOOK_SHARED_SECRET` in `.env`) or a valid
    internal-user bearer token — see
    `app.core.webhook_auth.require_webhook_secret_or_internal_user`.
    **`WEBHOOK_SHARED_SECRET` still needs to be generated and added to
    `.env` on the VPS** — a value was generated locally tonight (see the
    developer handoff for where it landed) but has NOT been deployed.
    Until it is, this endpoint fails closed (503) for the secret path —
    internal HR-portal use still works via bearer token in the
    meantime.

## Coarse auth only — ~49 routes (tracked, not an emergency)

Real identity check (candidate-self-service, self-scoped by definition;
or any-logged-in-staff-member), just not a specific
`require_permission(...)`. Not dangerous today. Run the command above
for the current full list. Worth tightening over time, especially the
internal/HR-staff category (viewing all users, approving offers) where
"any logged-in staff member" is broader than probably intended.

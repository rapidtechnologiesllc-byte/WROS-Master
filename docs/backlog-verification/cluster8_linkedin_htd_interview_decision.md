# Cluster 8 verification: EPIC-P4 (LinkedIn Sourcing) / EPIC-P5 (HTD) / EPIC-P6 (Interview Decision Engine)

Verified directly against code in `OnboardingModule-Backend` and `OnboardingModule-Frontend-main`. Sheet "Status" column not trusted for any row below.

## Headline findings (read this first)

1. **EPIC-P4 is 0/9, confirmed by ID search, not just absence.** No file in the backend contains `HRMS-P401` through `HRMS-P409` or `S-128`-`S-136`. There IS a `app/services/linkedin_sourcing_service.py` + `app/models/sourcing.py`, but they belong to a **different epic** entirely (`HRMS-1102`/`HRMS-1103`, EPIC-11 "Workforce Demand Monitoring Agent"). That engine sources LinkedIn candidates only reactively, when a demand's bench-first check fails, via an unbuilt "EPIC-P9 Boolean Search Engine" + unbuilt LLM query generation. It has no nightly keyword crawl, no InMail AI outreach, no recruiter contact queue, no session/rate-limit manager, no quality scoring, no analytics dashboard — i.e. it does not satisfy any of S-128 through S-136 even partially, despite superficially overlapping subject matter ("LinkedIn" + "sourcing").

2. **EPIC-P6's core engine is real, tested, and completely unwired to any endpoint or screen — confirmed, not assumed.** `grep` across `app/api/` for `interview_pipeline`, `SubmissionInterview`, `DemandInterviewPanel` returns **zero** matches. The one live API endpoint file for interviews (`app/api/v1/endpoints/interviews.py`) imports the *old* legacy `Interview`/`InterviewPanel` models (Integer PKs, one-candidate-one-job-one-round), never the new engine. `interview_service.py` (the new engine) is only ever imported by `calendar_matching_service.py`, which is itself not imported by any endpoint either. `interview_no_show_service.py` is wired into `app/core/scheduler.py` as a background job (so no-show detection runs for real) but there is still no create/view path for a `SubmissionInterview` anywhere reachable from the frontend. `tests/test_submission_interview_pipeline.py` (463 lines, 24 tests) exercises the engine directly and passes, confirming the logic is real, just orphaned.

3. **Critical WROS-ID collision found in the codebase's own comments**, worth flagging back to whoever owns ID assignment: this cluster's sheet says `HRMS-P605` = "Override Escalation Notifications" and `HRMS-P606` = "Two-Level Interview Configuration". The actual code (`app/services/submission_service.py`, `app/models/candidate.py`) uses **those same IDs** for unrelated compliance rules: `HRMS-P605` = "only BENCH/ACTIVE/ALLOCATED employees may be submitted" (Market Profile Rule) and `HRMS-P606` = "only W2_FULLTIME may be submitted, fails closed on UNKNOWN" (Employment Type Rule). `HRMS-P601` matches cleanly both places (5-year experience floor), but P605/P606 do not. Evidence below is mapped to the cluster's *semantic* story description, not the colliding ID string, and this collision is called out per-row where relevant.

4. **EPIC-P5 (HTD): the "Buddy Program / Graduation Gate" (S-067/S-364/S-365, confirmed built 2026-08-04) does NOT satisfy any of this cluster's 5 remaining stories.** It's `S-364/HRMS-0520` — a generic 30-day, 35-KPI onboarding tracker for *all* new hires (buddy assignment + graduation), with no HTD-track-specific logic (no Java-depth scoring, no job tagging, no HTD interview process, no deployment-readiness checklist, no HTD-vs-standard reporting). The only HTD-tagged code that does exist in the repo (`S-360/HRMS-P506-REV`, a 4-phase post-hire training gate: INDUCTION → SHADOW_DELIVERY → CONTROLLED_OWNERSHIP → CORE_ELIGIBILITY_REVIEW) is *also* a different WROS ID than any of this cluster's 5 (P501/P502/P505/P508/P510) and covers post-hire training progression, not pre-hire job tagging/candidate scoring/interview process/deployment checklist/reporting. None of the cluster's 5 EPIC-P5 stories are satisfied even partially by either.

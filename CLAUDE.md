## MANDATORY: two standing process rules, given directly by Avinash 2026-08-06 — read before building anything

These are not backlog items. They are how every future build in this codebase must happen, starting now.

**Rule 1 — Question before you build, not after.** Avinash's own words: "question before you build think through make sure no loose ends and then build dont just keep building and fixing it is causing more rework." For any non-trivial feature (a new workflow, a new agent, a new multi-step process — not a one-line bug fix), run a real interrogative session with Avinash FIRST: surface the full flow end-to-end, name every fork/decision point explicitly, ask rather than assume, and only start writing code once there are no open loose ends left unaddressed. Building first and patching gaps as they're discovered (what happened with the interview→feedback→hire flow, see below) is the exact failure mode this rule exists to stop — it isn't hypothetical, it already cost real rework this session.

**Rule 2 — Task-Driven Workflow Coverage, app-wide.** Avinash's own words: "entire application should have task validation thought process... Is my timesheet pending for this week to employee is there a invoice pending then to finance user and so on." Every state in this system where a human owes a real action must have a **live, visible Task** (or a genuinely scheduled recurring job) behind it — never just a data flag or a piece of business logic sitting there waiting for someone to remember to look. This applies retroactively (audit what's already built for gaps) and going forward (every new feature's design must answer "who owes an action here, and how do they find out without being told to check" before it's considered done).

**Two real, already-confirmed proof points found while investigating Avinash's live bug report (2026-08-06), not hypotheticals:**
1. **Interview feedback task exists but is functionally invisible.** `POST /interviews/create` correctly calls `sync_pending_feedback_tasks_for_interview()`, which creates a real `Task` per panelist with `due_date = interview.end_time`. But `get_daily_task_list()` (My Day) hard-filters to `due_date < tomorrow_start` (today/overdue only), and `get_upcoming_urgent_tasks()` only shows `priority == URGENT`. A MEDIUM-priority task due days from now is in **neither** bucket — it's invisible on the assigned interviewer's own dashboard until the day it's due. Root cause not yet fixed as of this entry — needs either an "Upcoming (all priorities)" bucket or a priority bump for feedback tasks as their due date nears; not decided yet, flagged not guessed.
2. **Timesheet Nag Cascade and AR Follow-up (both built 2026-08-05/06 under EPIC-16) were never registered in `app/core/scheduler.py`.** Checked directly: every other recurring domain job in this codebase (~30 of them — SLA monitoring, no-show detection, document reminders, campaign execution, etc.) is registered there with a real `scheduler.add_job(...)` cron/interval trigger. `scan_overdue_invoices()`/`trigger_ar_follow_up()`/`scan_missing_timesheets()`/`trigger_timesheet_nag()` have working logic and manual-trigger endpoints, but nothing calls them automatically — built, then never actually wired to run. Not yet fixed as of this entry, pending Avinash's go-ahead (see session log below).

**Going forward**: before marking any feature "Done" per this file's own Definition of Done (line 13), explicitly check it against Rule 2 — does every pending-human-action state it introduces have a Task or a scheduled job behind it, and is that Task actually visible to the person who owes the action (not just created and forgotten, per proof point #1 above)? The background orphan-code audit already running this session (frontend-connectivity gaps) is a *different* check from this one (task/schedule-coverage gaps) — both matter, neither substitutes for the other.

## BlitzenX Operating Model (v1.0) — read this before touching Partner/BU Head/revenue-visibility/resource-ownership work

Given directly by Avinash, 2026-08-05, as the formal baseline: "Based on all of our discussions over the past several months, below is the current operating model as I understand it. This should become the baseline for your Python project." Written here close to verbatim — this is architecture, not prose, and precision matters more than paraphrase for a spec like this. Treat every rule below as load-bearing for EPIC-02 (Revenue Visibility), EPIC-03 (Workforce Planning), EPIC-05 (Resource & Bench Management), and the Partner ROI Agent — not background color.

**Purpose**: BlitzenX is not a traditional consulting company — it's multiple independent business units (P&Ls) sharing one corporate platform. Goal: independent growth engines, independent delivery orgs, zero unnecessary overhead, repeatable scaling, minimal founder dependency.

**Enterprise structure**:
```
CEO
│
├── AXION (Guidewire Services Practice)
│     Partner: Troy
│     Offshore BU Head: Hemant
│
├── PRISM (Guidewire Innovation / Accelerator Practice)
│     Partner: Curtis
│     Offshore BU Head: Manian
│
├── Corporate — Finance, HR, Marketing, Recruiting
│
└── Future Business Units
```

**CEO owns**: enterprise vision, capital allocation, executive hiring, strategic partnerships, M&A, product strategy, AI, enterprise governance, corporate marketing, enterprise sales assistance when required.
**CEO does NOT own**: daily delivery, resource allocation, sprint execution, practice operations.

**Every BU operates like an independent company** — owns its own revenue, gross margin, delivery, hiring, bench, talent development, client success, P&L. The only shared layer is corporate services.

**AXION** ("Adaptive eXecution & Integrated Operations") — Partner: Troy. Guidewire System Integration, Guidewire Managed Services, net-new carriers, practice growth, AI-enabled managed services. Supported by Hemant.
**PRISM** ("Product Integration & Systems Management") — Partner: Curtis. Net-new business ($5M ARR target), existing customer/account expansion, product integration, production support. Supported by Manian.

**Each Partner has exactly one offshore BU Head** — this is a real 1:1 structural pairing (Troy↔Hemant, Curtis↔Manian), not a many-to-many relationship. Matters directly for the `PartnerGoal`/scoring design below: there's one Partner and one BU Head per BU, each answering for a different half of the same number, not multiple Partners splitting one BU's target.

**Partner responsibilities**: commercial, customers, revenue, P&L, executive relationships, growth, practice strategy.
**BU Head responsibilities**: delivery, resource planning, hiring, quality, training, forecasting, bench, utilization, employee development, escalations.

**Delivery ownership rule — one of the most important rules in this spec**:
- **US work** (US onsite, US client-facing, executive consulting, architecture, sales, executive relationship) → **Partner owns delivery directly**. Does NOT route through offshore BU Head. Example: a Carrier CIO meeting goes to Troy, never to Hemant.
- **India/offshore work** → **Partner depends on BU Head**. Example: customer asks for 10 developers → Troy → Hemant → team. Partner does not manage daily offshore delivery.
- One-line rule: **US = Partner. India = BU Head.**

**Resource ownership**: resources belong to their Business Unit, not a global BlitzenX pool. Example: a developer belongs to AXION → Hemant, not to a shared pool. *Flag for whoever next touches Resource Management (EPIC-05)*: the existing `EmployeeAllocation`/bench_pool build should be checked against this — confirm employees are BU-scoped as this model requires, not treated as globally poolable, before extending that system further.

**Talent Engine — each BU owns its own SPECIALITY, TIP, and HTD engine. No sharing across BUs.**
- **SPECIALITY**: generates billable talent, protects economics, ensures zero idle cost. Acts as the gateway until the company reaches 150 employees.
- **HTD** (Hire → Train → Deploy): Java Developer → Training → Guidewire → Billable → Graduate.
- **TIP** (Talent Incubation Program): ~60-day training period, then one year billable inside Speciality, then graduates to eligible for carrier projects.
- *Flag*: HTD/Speciality/Delivery-Engine concepts already exist in this codebase (S-353 Core-Pull, S-373 Specialty Pool Guard, Buddy Program, `delivery_engine` field) — worth an explicit reconciliation pass against this spec's BU-ownership model next time that area is touched, not assumed compatible by default.

**Hiring pipeline**: every hire → assigned to a Business Unit → assigned to Speciality → billable → available → deployed.

**Deployment logic — no hiring just because a customer needs a resource; resources already exist.** Customer demand → Partner → BU Head → resource selection → deployment. Example: Builders Insurance needs 10 developers — instead of hiring, move someone off PwC onto Builders, 2-week notice, immediate deployment.

**Bench philosophy**: bench is NOT idle — it's already billable, protected by Speciality. Zero economic drag by design.

**Revenue ownership**: every client belongs to exactly one Partner. Example: Builders → AXION → Troy. Never shared.

**Client attribution locking — "one more major law," given directly 2026-08-05, real enforcement not just a convention**: a client's BU is permanently locked to whichever Partner's own organizational tree sourced it — **never manually reassignable across that boundary**. A client coming from Curtis goes to PRISM, never AXION. A client from Troy goes to AXION, never PRISM. A client sourced by Avinash himself goes to **Corporate**, not to either BU. If Troy later hires his own sales org (Sales Director → BDRs → AEs, per the Sales Phases section above), every client that org sources still rolls up to AXION — **the tree never crosses group**, no matter how many layers get added under a Partner. This is the authoritative rule for `Client.business_unit_id` assignment at creation time: derived from the sourcing user's own position in the org (their Partner, or Corporate if the CEO sources it directly), not a freely-editable dropdown a user can pick.

**Resource requests**: Partner receives the work. Offshore → BU Head fulfills. Onsite → Partner fulfills directly. Example: carrier needs a developer → Troy → Hemant → developer. Carrier needs an executive architect → Troy → Troy (stays with Troy, no handoff).

**Sales phases**: Phase 1 — Founder sells, Partner assists. Phase 2 — Partner sells, Founder supports. Phase 3 — Partner's own organization sells (Troy → Sales Director → BDRs → AEs), Founder runs the enterprise.

**Executive philosophy**: every executive owns an economic engine, never overhead. Hemant owns delivery economics. Troy owns AXION practice economics. Curtis owns PRISM economics.

**Corporate functions remain centralized**: Finance, HR, Legal, Marketing, Recruiting, Payroll, Accounting, IT, corporate brand.

**Partner KPIs**: Revenue, Gross Margin, Net New Logos, Customer Satisfaction, Practice Utilization, Practice Growth, Thought Leadership, P&L.
**BU Head KPIs**: Utilization, Hiring Velocity, Delivery Quality, Bench Health, Attrition, Training, Forecast Accuracy, Delivery Margin.

*These two KPI lists are the real spec for what `get_revenue_position()`/the Partner ROI Agent's weekly scoring needs to gather from each side — Partner-side inputs map to the Partner KPI list (revenue/logos/P&L-facing), BU Head-side inputs map to the BU Head KPI list (headcount/delivery/hiring-facing). See the Revenue Visibility Agent design entry below for how these get combined into one weekly score.*

**Scaling strategy**: 75 → 150 → 300 → 500 → 1,000 → 2,000 employees. Each growth stage adds new Business Units, not a larger centralized organization.

**Long-term vision**: a federated enterprise, not a traditional consulting firm. Each BU behaves like a self-contained company with its own Partner, offshore delivery org, talent engine, customers, and P&L; corporate provides governance, capital, brand, finance, legal, HR, and strategic direction. End state: the CEO is no longer the operational bottleneck — Partners build and scale their own businesses within the BlitzenX platform, growing from ~75 employees today toward 2,000+ by 2030 while keeping accountability, financial discipline, and entrepreneurial ownership intact.

## Architectural decisions made this session — follow these, don't re-litigate them

- **Production database is SQL Server** (`mssql+pyodbc`), not PostgreSQL — despite every requirements doc being written in Postgres syntax (native `ENUM`, `JSONB`, `GIN` indexes). Translate every spec: `Enum(*values, native_enum=False, create_constraint=True)` for a portable VARCHAR+CHECK (note: `create_constraint=True` is required explicitly — SQLAlchemy 2.0 does NOT add the CHECK constraint by default even with `native_enum=False`), `Text` instead of `JSONB` (JSON-encoded strings), no GIN index (use a standard index on the realistic query column instead).
- **New Phase 2 entities use UUID primary keys as `String(36)`** (`str(uuid.uuid4())`), not SQL Server's native `UNIQUEIDENTIFIER` or Postgres's UUID type — a plain string round-trips identically on SQLite (every test in this repo runs against throwaway SQLite) and SQL Server. **Existing tables (`Candidate`, `Users`, `Jobs`) keep their original custom string IDs** — do not retrofit them to UUID, that was an explicit decision, not an oversight.
- **New tables (`employees`, `clients`, `demands`) are genuinely new**, linked to existing tables via FK (e.g. `employees.candidate_id` → `candidates.candidateID`), not retrofitted into `Candidate`/`Jobs`. Note: `demands` vs. the existing `Jobs` table is an **unresolved open question** — they serve overlapping purposes and haven't been reconciled. Don't silently pick a direction; flag it.
- **Every table gets `tenant_id`, nullable-for-now** (existing rows backfilled to a single "BlitzenX" tenant via migration `d6e7f8a9b0c1` — every *new* tenant-scoped table should follow the same nullable pattern, matching HRMS-0109's safe-upgrade precedent). Real tenant scoping is only wired into 6 high-risk list/search routes so far — see `docs/build-package/HRMS-0109-tenant-scoping-gap.md` for the ~180 remaining lower-priority (IDOR-shaped) call sites.
- **Testing convention, always**: throwaway SQLite (`tempfile.mkstemp`), never the real database. For anything touching JWT, generate a throwaway RSA key pair per-test and monkeypatch `app.core.security.PRIVATE_KEY`/`PUBLIC_KEY` — never rely on real signing keys in a test. For anything touching a real LLM (Gemini), mock the client — never make a real API call from a test.
- **MFA is fully built (TOTP, backup codes, enrollment/verify, pending-token isolation) but enforcement is OFF by default** (`MFA_ENFORCEMENT_ENABLED` env var). Do not turn it on until the frontend has a screen for it — there's no UI to complete a TOTP challenge yet, and flipping it on would lock out every `Super User`/`BU Head` account. Also: that role mapping (`Super User`/`BU Head` standing in for the docs' "Admin and Director") is this session's best-guess analog, not a confirmed decision — the real RBAC role list has neither name.
- **`AuthenticationMiddleware` and `RateLimitMiddleware`**: rate limiting IS enabled (`app/main.py`). Full JWT-enforcement middleware is NOT enabled — still per-route `Depends()` only. Two real bugs were found and fixed in `AuthenticationMiddleware` (a prefix-matching bug that would have made every route public if ever enabled, and a stale public-routes list) but it's still not wired into `app.main` — needs someone who can watch real production traffic after enabling it.

## R-07 — createCandidateSafe() now actually exists (2026-07-21)

CLAUDE.md's own non-negotiables list has said "createCandidateSafe() is the only path to create a candidate" all session — but the function itself was never built anywhere in this codebase until now (confirmed by grep while researching Sub-Vendor Portal: zero hits). `app/services/candidate_service.py` builds it for real: `find_duplicate_candidate()` checks email, phone, and LinkedIn **each independently** (added `Candidate.linkedin_url`, a genuinely new field — the Dev Review Standard's own worked example of this exact gap is "missing phone/LinkedIn"), and `create_candidate_safe()` is the one creation path, raising `DuplicateCandidateError` rather than inserting a second row.

**The two pre-existing direct-insert call sites were retrofitted, not left bypassing it**: `app/api/v1/endpoints/onboarding.py`'s HR candidate-creation endpoint and `app/api/v1/endpoints/create_job.py`'s public job-application endpoint both previously built `Candidate(...)` directly and deduped on email only via `app.core.database.check_candidate()` (exactly the gap the Dev Review Standard describes as its own example). ## Interview → Hire → Onboarding workflow — full interrogation session, 2026-08-06 (design only, NOT built)

Avinash's live bug report ("I scheduled an interview, it never showed as a task; submitted feedback, still no task") turned into a full requirements-discovery session per the mandatory Rule 1 above — this section is the output of that session: real findings from reading the code (not guesses) plus every design decision Avinash confirmed. **Nothing in this section has been built yet** — it's the complete brief for whoever picks this up next, specifically so building it doesn't repeat this session's own "build first, find the gaps after" mistake.

### Real findings (verified by reading code, not assumed)

1. **There are two parallel interview systems in this codebase, and the frontend only talks to the weaker one.** `app.models.user.Interview`/`InterviewPanel`/`InterviewFeedback`/`PanelMember` is what `/interviews/create`, `/interviews/panels/create`, `/interviews/panel-members/assign`, `/interviews/feedback/submit` actually touch (confirmed by grepping `services/api/interviews.js` — every call goes through this router). It has no L1/L2 concept (`round_name` is free text), no round-robin, and a single unstructured `recommendation` field. Separately, `app.models.interview_pipeline.SubmissionInterview`/`DemandInterviewPanel` (built under HRMS-0706/0448) already has real L1/L2 `level`, R-05 enforcement (L2 blocked until L1 `outcome=PASS`), genuine round-robin assignment (`get_assigned_interviewer()` — least-loaded active panelist, tie-broken by earliest `assigned_at`), reschedule chains, and the only real no-show detection in the codebase (`interview_no_show_service.py`). **It has zero frontend wiring — confirmed orphan code**, the same failure mode the audit above hunts for systematically.
2. **The interview feedback Task IS created correctly on the legacy system** — `POST /interviews/create` calls `sync_pending_feedback_tasks_for_interview()` (added 2026-08-05), which creates one real `Task` per panelist with `due_date = interview.end_time`. It's just **invisible**: `get_daily_task_list()` ("My Day") hard-filters to `due_date < tomorrow_start` (today/overdue only), and `get_upcoming_urgent_tasks()` only shows `priority == URGENT`. A MEDIUM-priority task due days out is in neither bucket — nowhere on the assignee's dashboard until the day it's due. **Root cause identified, fix NOT yet built** (needs either an "Upcoming, all priorities" bucket or a priority escalation as the due date nears — not decided, don't guess at which).
3. **Feedback submission already auto-closes its own Task** — `close_pending_feedback_task()` fires the moment an interviewer submits (`interviews.py:2083`). No manual task-closing burden exists today; confirmed correct, nothing to fix here.
4. **A no-show interview never leaves round-robin load, by construction** — `interview_no_show_service.py` (only wired to the orphan `SubmissionInterview` system) sets `no_show_confirmed_at` but deliberately never touches `outcome` (BR-02: "Thunder never auto-disqualifies, only a recruiter decides"), and `get_assigned_interviewer()` counts `outcome == PENDING` as load — so a no-show sits on that panelist's count indefinitely.

### Decisions confirmed directly with Avinash (all still need building)

1. **Panel selection**: system suggests panelists from skill/role match (Demand's `required_skills` against `Employee.current_skills` + past-interviewer history), BU Head/Partner confirms or overrides — not fully manual, not a rigid pre-set roster.
2. **L1 → L2 auto-trigger**: every submitted L1 panelist's recommendation must be positive before L2 auto-creates. One negative vote blocks the auto-trigger and instead creates a task for the hiring manager to decide manually (reject, or override and proceed).
3. **BU Head financial approval**: wires to the **real** EPIC-16 Hiring Affordability engine (`hiring_affordability_service.check_hiring_affordability()`, already built, currently orphaned per the audit above) — the approval task shows the candidate's actual fully-loaded cost against that BU's actual current P&L margin, not a rubber-stamp yes/no.
4. **Learning / "don't ask twice"**: lightweight, not ML — remember the last panel picked for a given role/skill combo (queryable from `InterviewPanel`/`DemandInterviewPanel` history) and pre-fill it as a one-click default next time a similar combo needs a panel.
5. **Panel escalation ceiling**: BU Head → Partner → if even the Partner can't identify a panel, the task escalates to CEO with `Task.is_escalated=True` — matches this codebase's existing escalation posture, never silently stuck.
6. **Onboarding trigger**: hire decision + BU Head financial approval = the trigger into the **existing** offer-letter/candidate-conversion/Buddy-Program pipeline already built this session — no new onboarding pipeline, just a new trigger point into it.
7. **Architecture consolidation**: migrate the live UI onto the mature `SubmissionInterview`/`DemandInterviewPanel` backend rather than keep patching the legacy `Interview` system — retire the legacy system's role as the UI's backing store once the migration is done. This is the single biggest piece of work in this backlog item; everything else above should be built against the mature system, not the legacy one, to avoid throwaway work.
8. **No-show + round-robin**: a no-show interview should drop out of a panelist's round-robin load count **immediately** once `no_show_confirmed_at` is set — they showed up, it isn't their fault, they shouldn't rank as busier than a peer with fewer no-shows.
9. **Only one Task exists per interview-scheduling event today, confirmed correct, not two**: `sync_pending_feedback_tasks_for_interview()` creates exactly one Task per panelist ("Submit feedback: ..."), and it's the same object `close_pending_feedback_task()` closes on submission — verified by re-reading the exact code path a second time after Avinash's follow-up question. There is no separate "informational: interview scheduled" Task anywhere in this codebase; the only other thing firing at scheduling time is a one-time email reminder (`_schedule_interview_reminder()`), not a Task row, so it can't go stale. Avinash confirmed this is the correct behavior, not a gap — no new informational-entry type needed.
10. **Outlook RSVP should never become a second manual task** — accepting/declining the calendar invite and submitting post-interview feedback are different actions at different times; a WROS task for "confirm you're coming" would duplicate Outlook's own native Accept/Decline button (real complaint risk: "this is more work"). Confirmed via grep that no code anywhere reads RSVP status back from Microsoft Graph today. **Added to scope**: read RSVP status back via Graph purely as an automated signal — a **decline** silently triggers the same round-robin reassignment logic (no human has to notice or act), never surfaced as a task to anyone. An **accept** does nothing (no task exists to close). This is net-new work (no existing polling/webhook for calendar responses) — needs its own scoping pass on top of the msgraph integration once the interview-system migration above is underway.
11. **A confirmed real gap even in the mature system: free/busy match ≠ explicit confirmation.** `calendar_matching_service.py`'s `attempt_calendar_match()`/`find_matching_slot()` already does a real match — candidate-submitted `CandidateAvailabilitySlot` rows crossed against the panelist's actual Outlook busy/free via Graph — and books automatically the moment a slot looks free on both calendars. It does **not** get an explicit yes from either side first; "shows free" isn't the same as "actually wants this slot" (unmarked PTO, personal conflicts, etc. — exactly the wasted-panel-time risk Avinash is flagging). **Avinash's proposed fix, confirmed as the direction**: before the real Outlook calendar invite goes out, send both the candidate and the matched panelist a Yes/No/propose-new-time confirmation (email or similar) for the matched slot; only send the actual calendar invite once both sides have said yes. A decline or a proposed alternate should feed back into re-matching (candidate proposes new time → re-run `find_matching_slot()`; panelist declines → round-robin reassign per decision #10 above), not silently stall. **Not built** — this replaces `attempt_calendar_match()`'s current "match and auto-book" behavior with "match, confirm both sides, then book," a real behavior change to an already-built engine, not just new UI on top of it.

### Resolved 2026-08-06, closing the "still open" list below before build starts

- **L2 panel selection**: same algorithm as L1 — skill/role-match suggestion, BU Head/Partner confirms/overrides, round-robin assignment. No separate seniority rule.
- **Explicit "No Hire"**: marked rejected for this specific role (not the general pool), **and the candidate gets a real rejection notice** via the existing Thunder-side send path — not internal-only.
- **BU Head declines financial approval** after a positive hire decision — refined same day to a specific 2-step flow, not just "returns to the hiring manager": (1) declining creates a task for **HR to negotiate with the candidate and confirm the best possible rate**, not the hiring manager; (2) the negotiated rate goes back to the BU Head for re-approval; (3) **if the BU Head declines a second time (after the negotiated rate), that is a real dead end** — the candidate gets a "no hire" email that specifically cites the financial/budget reason, not a generic rejection. Two decline points exist, not one; the first is a real negotiation attempt, only the second is terminal.

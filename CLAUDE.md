## Architectural decisions made this session — follow these, don't re-litigate them

- **Production database is SQL Server** (`mssql+pyodbc`), not PostgreSQL — despite every requirements doc being written in Postgres syntax (native `ENUM`, `JSONB`, `GIN` indexes). Translate every spec: `Enum(*values, native_enum=False, create_constraint=True)` for a portable VARCHAR+CHECK (note: `create_constraint=True` is required explicitly — SQLAlchemy 2.0 does NOT add the CHECK constraint by default even with `native_enum=False`), `Text` instead of `JSONB` (JSON-encoded strings), no GIN index (use a standard index on the realistic query column instead).
- **New Phase 2 entities use UUID primary keys as `String(36)`** (`str(uuid.uuid4())`), not SQL Server's native `UNIQUEIDENTIFIER` or Postgres's UUID type — a plain string round-trips identically on SQLite (every test in this repo runs against throwaway SQLite) and SQL Server. **Existing tables (`Candidate`, `Users`, `Jobs`) keep their original custom string IDs** — do not retrofit them to UUID, that was an explicit decision, not an oversight.
- **New tables (`employees`, `clients`, `demands`) are genuinely new**, linked to existing tables via FK (e.g. `employees.candidate_id` → `candidates.candidateID`), not retrofitted into `Candidate`/`Jobs`. Note: `demands` vs. the existing `Jobs` table is an **unresolved open question** — they serve overlapping purposes and haven't been reconciled. Don't silently pick a direction; flag it.
- **Every table gets `tenant_id`, nullable-for-now** (existing rows backfilled to a single "BlitzenX" tenant via migration `d6e7f8a9b0c1` — every *new* tenant-scoped table should follow the same nullable pattern, matching HRMS-0109's safe-upgrade precedent).

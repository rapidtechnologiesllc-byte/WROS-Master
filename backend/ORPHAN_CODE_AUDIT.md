# WROS Orphan Code Audit — Backend Endpoints vs Frontend Wiring

Generated by a full static cross-reference of every `@router` decorator in
`app/api/v1/endpoints/*.py` (backend) against every call in
`src/services/api/*.js` plus inline `fetch()` calls in `src/screens/*.js`
(frontend). Method + path shape matched (`{id}`-style params ignored on
both sides). This is a from-scratch retry of an earlier run that was
killed mid-task before producing output.

## 1. Summary

| Metric | Count |
|---|---|
| Total backend endpoints (`@router.get/post/put/patch/delete`) | **508** |
| Backend endpoints matched by at least one frontend call (method + path) | 408 |
| Backend endpoints with **no** matching frontend call at all — true orphans | **100** |
| Of the 408 "wired" endpoints, those wired **only** through a frontend service function that is itself never imported by any screen/component — effectively unreachable too | **33** |
| **Total endpoints not actually reachable from any screen** (100 + 33) | **133 / 508 (~26%)** |
| Frontend `services/api/*.js` exported functions that exist but are never imported by any screen/component/layout/page/route/util | **35** |

Methodology notes:
- Backend prefix resolution: each endpoint file's own `APIRouter(prefix=...)` was read from source (not assumed) — see `app/api/v1/routes.py`, which mounts every endpoint router with **no additional prefix** (`router.include_router(router=X_router)`, no `prefix=` kwarg anywhere), and `app/main.py` mounts the aggregate router with no prefix either. So an endpoint's live path is exactly `<file's APIRouter prefix> + <decorator path>`.
- Frontend paths were normalized by resolving `${...}` template expressions to a wildcard segment and stripping query strings, then matched against backend paths segment-by-segment (literal segments must match; `{param}`-shaped segments match anything).
- A handful of frontend calls route through small in-file wrapper functions (`_uploadDocument(path, ...)` in `documents.js`, `portalRequest(path, ...)` in `candidatePortal.js`) rather than calling `apiRequest`/`fetch` directly with a literal path. These were traced by hand and included in the match set.
- One frontend call (`preOnboarding.js` `managerReviewApprove`) posts to `record?.approval_endpoint` — a URL supplied by a prior API response, not a static string. It cannot be resolved by static analysis; see the false-positive notes.

## 2. Orphaned backend endpoints (no frontend call found), by domain

100 endpoints below have zero matching frontend call anywhere in `services/api/*.js`, inline `screens/*.js` `fetch()` calls, or the wrapper functions traced by hand. Grouped by domain; "UI work needed" is a rough sizing, not a spec. Several are flagged **DUPLICATE/LEGACY** or **NONE** — read those before scoping any build work, they are not real gaps.

### Notable clusters up front

- **Legacy `/hr/interviews/*` cluster (users.py, 6 endpoints)**: `POST /hr/interviews/create`, `POST /hr/panel-members/assign`, and `POST /hr/interviews/feedback` all appear to be superseded by actively-used equivalents in `interviews.py` (`POST /interviews/create`, `POST /interviews/panel-members/assign`, `POST /interviews/feedback/submit`, confirmed wired via `interviews.js`). `PUT /hr/update_interview/{id}` and `DELETE /hr/delete_interview/{id}` are likely the same story but weren't traced to a confirmed live equivalent — verify before deleting.
- **Duplicate Thunder tenant-config pair (ai_recruiter_assignment.py, 2 endpoints)**: `GET`/`PATCH /admin/tenant/ai-config` duplicate the already-wired `GET`/`PATCH /admin/ai-config` in `tenant_ai_config.py` (confirmed wired via `tenantAiConfig.js`). Likely dead code, not a UI gap.
- **Staff MFA has zero UI (mfa.py, 5 endpoints)**: `POST /auth/mfa/setup`, `/setup/confirm`, `/verify`, `/email/resend`, `/email/verify` — the entire staff/HR TOTP+email-OTP enrollment and login-challenge flow has no frontend at all. By contrast, the **candidate**-facing email-OTP flow (`/auth/mfa/candidate/*`) is fully wired via `auth.js`. This is a real security-feature gap, not a false positive.
- **Webhooks are not a UI gap**: `POST /ai-agent/webhook/email-reply`, `GET`/`POST /webhooks/whatsapp` are inbound webhooks called by the email provider / Meta's WhatsApp Cloud API respectively — they were never meant to have frontend UI.
- **`GET /msgraph/auth/signin` is a false positive**: it's genuinely used, just not via `fetch`/`apiRequest` — `AuthPage.js`, `InterviewSchedule.js`, and `InterviewStatus.js` all call `window.location.href = getAzureSigninUrl()` / `window.open(getMicrosoftSigninUrl())`, which the static scan can't see. `GET /msgraph/auth/callback` is the OAuth redirect target Azure AD sends the browser to directly — also not something app JS ever fetches.

## 5. False-positive / needs-manual-verification notes

- **`GET /msgraph/auth/signin`** — listed as orphan by the raw scan but genuinely wired via `window.location.href`/`window.open()` calls to `getAzureSigninUrl()`/`getMicrosoftSigninUrl()` (both of which just build a string, never call `fetch`). Confirmed used in `pages/AuthPage.js:357`, `screens/InterviewSchedule.js:335/422/502`, `screens/InterviewStatus.js:669`. **Not a real orphan** — corrected in Section 2's table but flagging again here since it's the clearest false positive found.
- **`preOnboarding.js` `managerReviewApprove(record, review)`** calls `apiRequest(record?.approval_endpoint, ...)` — the URL comes from a field on a previously-fetched record, not a literal string anywhere in the source. This could resolve to any backend path at runtime; it was **excluded entirely** from the frontend call inventory rather than guessed at. If `record.approval_endpoint` is always `/preonboarding/{id}/hiring-manager-approval`, that would explain the Section 2 orphan for that same path — worth checking directly rather than trusting either label.
- **4 inline `fetch()` calls in `screens/*.js`** (`CandidateSelfService.js:442`, `OfferListing.js:138`, `PreonboardingModal.js:354`, `PreviousOfferModal.js:31`) all fetch a `download_url` value returned by a prior API response (e.g. offer-letter generation), not a literal backend path. They represent real, working frontend-backend wiring but could not be resolved to a specific `@router` decorator by static analysis — not counted as orphan evidence either way.
- **Section 3's "effectively orphaned" list is a lower bound.** It only catches endpoints whose *sole* frontend match is a dead wrapper. If a screen calls a wired wrapper function but that screen itself is dead (unreachable from any route/nav), the endpoint would still show as "wired" here. Routing/reachability of screens themselves was out of scope for this pass — worth a follow-up if the UI cleanup pass turns up dead screens.
- **Duplicate-endpoint calls (e.g. the `/hr/interviews/*` vs `/interviews/*` cluster, `/admin/tenant/ai-config` vs `/admin/ai-config`)** were identified by manually reading both sides after the automated pass flagged them; there could be other near-duplicate pairs among the 100 orphans that weren't manually cross-checked — the "DUPLICATE/LEGACY" tags in Section 2 are the ones actually verified, not an exhaustive sweep.
- **`POST /portal/track`** and the `portal/conversations/*` messaging endpoints under Candidate Portal were flagged orphan by path matching, but candidate-portal code deliberately avoids the shared `apiRequest` helper (see `candidatePortal.js`'s own doc comment) and uses a local `portalRequest` wrapper — traced by hand for the functions that exist, but if `CandidatePortalScreen.js` (or similar) calls `fetch` directly inline for page-view tracking without going through `candidatePortal.js` at all, that would not have been caught. Worth a direct grep of the portal screen file(s) before treating this as confirmed.
- **Endpoint count (508) and file count (~40 → confirmed 79 files in the directory, most with 0 routes and just helpers)**: only files containing at least one `@router.` decorator contribute to the 508; the directory also holds `__pycache__`. No filtering ambiguity here, just noting the raw `ls` count includes non-route files.

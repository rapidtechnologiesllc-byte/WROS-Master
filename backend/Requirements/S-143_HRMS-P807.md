## Why — Business Rationale

- R-07 is absolute: one candidate, one record, dedup runs before every creation, no exceptions. Sub-vendor submissions are a second entry point into the same candidate pool a recruiter or Thunder might already be working — without a dedup check here, BlitzenX risks paying a vendor placement fee for a candidate already in an active internal pipeline, and risks the candidate getting two conflicting outreach messages from two different parts of the same company.

## What — Scope

- A dedup check against the internal candidate database (matching on email and phone) that runs on every sub-vendor submission, auto-rejecting any match before it reaches the recruiter review queue.

## Before — Prerequisites

- S-142 HRMS-P806 FT-Only Enforcement Engine must run first — dedup only applies to already-compliant submissions.

- createCandidateSafe()'s dedup sub-function must be callable independently of full candidate creation, matching the pattern used in HRMS-1103 LinkedIn Sourcing Agent Loop.

## Implementation Steps

## Step 1: Call the shared dedup check

- Use the same dedup sub-function createCandidateSafe() uses internally — not a second, independently-maintained matching implementation.

- Match on email and phone against the existing candidates table.

## Step 2: Handle a match

- Auto-reject the submission with the message: 'Candidate already in BlitzenX system.'

- Log the rejection reason distinctly from an FT-only violation — this is a dedup rejection, not a compliance violation, and should not count toward the S-142 three-strike threshold.

## Step 3: Handle no match

- Submission proceeds to S-144 recruiter review queue.

## Business Rules

BR: BR-0807-01 — Dedup uses the same matching logic as createCandidateSafe(), not a separate implementation

- Per R-07, there is one dedup path in the platform — this story calls it, it does not reimplement matching logic independently.

- Field: Dedup check is a direct call to createCandidateSafe()'s dedup sub-function

## BR: BR-0807-02 — Dedup rejection never reveals internal candidate details to the vendor

- The vendor learns only that the candidate is already in the system, never which recruiter, which pipeline stage, or any other internal detail — protects internal pipeline confidentiality.

- Field: Rejection message is a fixed string with no internal candidate data interpolated

BR: BR-0807-03 — Dedup rejections are tracked separately from FT-only compliance violations

- A dedup match is not a vendor compliance issue and must not count toward S-142's three-strike threshold — conflating the two would unfairly penalize a vendor for something outside their control.

- Field: sub_vendor_dedup_rejections is a separate table from sub_vendor_violations

## Acceptance Criteria

- AC-1: A submission matching an existing candidate's email or phone is auto-rejected before reaching the recruiter queue.

- AC-2: The vendor-facing rejection message contains no internal candidate details.

- AC-3: A dedup rejection does not increment the vendor's S-142 FT-compliance violation count.

- AC-4: A dedup-check service failure blocks the submission rather than allowing it through unchecked.

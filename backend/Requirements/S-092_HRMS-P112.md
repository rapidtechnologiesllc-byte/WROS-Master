## 2. WHY THIS EXISTS

Despite HRMS-P101 preventing duplicate creation at entry points, edge cases may create duplicates — manual imports, API calls bypassing validation, legacy data migration. The Dedup Audit Dashboard gives admins visibility into the identity state of the candidate database and tools to resolve any detected duplicates.

## 3. WHAT YOU ARE BUILDING

Build: (1) GET /api/admin/dedup-report — potential duplicate pairs. (2) Admin dedup dashboard at /admin/candidates/dedup. (3) Manual merge tool. (4) Not-a-duplicate marking. (5) Merge history view.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Build duplicate detection query

- Query: find candidate pairs sharing email OR phone within same tenant, where neither is status=MERGED

- SELECT DISTINCT c1.id, c1.name, c1.email, c1.phone, c2.id, c2.name, c2.email, c2.phone, 'EMAIL' as match_field FROM candidates c1 JOIN candidates c2 ON c1.email=c2.email AND c1.tenant_id=c2.tenant_id AND c1.id < c2.id AND c1.status != 'MERGED' AND c2.status != 'MERGED'

- UNION same query for phone match

- Filter out pairs already marked as 'not a duplicate' (candidate_dedup_ignored table)

## Step 2: Create candidate_dedup_ignored table

- CREATE TABLE candidate_dedup_ignored: id UUID PK, tenant_id UUID, candidate_id_a UUID, candidate_id_b UUID, ignored_by UUID, ignored_at TIMESTAMP, reason TEXT nullable

- When admin marks 'Not a Duplicate': INSERT this pair. Exclude from future dedup reports.

## Step 3: Build dedup dashboard UI

- Route: /admin/candidates/dedup. Auth: ADMIN role only.

- Header: 'Candidate Dedup Center — [N] potential duplicates detected'

- Table: Candidate A (name, email, phone, created_at, source) | Candidate B (same fields) | Match Field | Actions: [Merge] [Not a Duplicate] [View Both]

- [Merge] button: opens modal to select primary record. On confirm: calls mergeCandidate(primary_id, secondary_id).

- [Not a Duplicate]: calls /api/admin/candidates/dedup/ignore. Pair disappears from list.

- [View Both]: opens two candidate profile tabs side by side for comparison.

## Step 4: Build merge history tab on dashboard

- Second tab on dedup page: 'Merge History'

- Shows all past merges from candidate_identity_events WHERE event_type='MERGED_INTO'

- Per row: Primary candidate, Secondary candidate (now archived), merged_at, merged_by, match_field

- Allows admin to review past merges and identify any incorrect merges

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: Merge Is Irreversible — Confirmation Required

Merging two candidates is a significant data operation. Require admin confirmation in modal. After merge: secondary record status=MERGED, all references updated. Cannot be automatically undone — admin must manually re-split if needed.

↳ Triggered by field: Merge confirmation modal required

## BR-02: Merge History Is Read-Only

The merge history tab shows past merges for audit. No undo button. Historical merges cannot be reversed from this UI. Requires admin DB operation to split if needed (out of scope for this story).

↳ Triggered by field: Merge history read-only

## 2. WHY THIS EXISTS

When a candidate completes preboarding and joins BlitzenX, they must be converted from a candidates record into an employees record. This is the single most important data event in the candidate lifecycle — it marks the transition from recruiting to employment, triggers payroll setup, bench tracking, timesheet access, and closes the demand position.

## 3. WHAT YOU ARE BUILDING

Build convertCandidateToEmployee() — the atomic function that: validates all preboarding is complete, creates the employees record from candidate data, updates demand positions_filled, closes the candidate pipeline, triggers the JOINED stage on the Journey Dashboard, and creates the employee's WROS user account if needed.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Build pre-conversion validation

- validateReadyForConversion(candidate_id, tenant_id) → { ready: boolean, blockers: [] }

- Check 1: offers.status=ACCEPTED for this candidate

- Check 2: All preboarding_documents.status=RECEIVED (all required docs submitted)

- Check 3: offers.start_date <= today (joining date has arrived or passed)

- Check 4: No existing employees record for this candidate_id (idempotency check — don't double-convert)

- Return blockers list if any check fails.

## Step 2: Build convertCandidateToEmployee() atomic function

- convertCandidateToEmployee(candidate_id, tenant_id, converted_by) → employee_id

- Run validateReadyForConversion(). If not ready: throw ConversionNotReadyError with blockers.

- Load candidate + accepted offer + demand

- INSERT employees: { candidate_id, tenant_id, first_name, last_name, email, phone, joining_date=offers.start_date, employment_type=W2_FULLTIME, status=ACTIVE, current_title=demand.job_title, current_skills=candidates.skills, total_experience_months=candidates.total_experience_months, base_salary_usd_cents=offers.base_salary_usd_cents, billing_rate_usd_cents=demand.billing_rate_usd_cents, billing_classification=BENCH (starts on bench until first allocation), bu_id=demand.assigned_bu_id }

- employee_number auto-generated

- UPDATE candidates.status='CONVERTED_TO_EMPLOYEE'

- UPDATE demands.positions_filled = positions_filled + 1 (triggers auto-FILLED if headcount reached)

- UPDATE offers.status='COMPLETED'

- Call transitionState(conversation_id, 'COMPLETED', 'Candidate joined as employee', 'SYSTEM') from HRMS-0418

- Publish event: employee.created { employee_id, candidate_id, joining_date, bu_id }

- INSERT conversation_audit_log: CANDIDATE_CONVERTED_TO_EMPLOYEE { employee_id, candidate_id, converted_by }

- Return employee_id

## Step 3: Build POST /api/candidates/{id}/convert-to-employee endpoint

- Auth: HR or Admin role only.

- Calls convertCandidateToEmployee(). On success: returns { employee_id, employee_number }.

- On ConversionNotReadyError: HTTP 422 with blockers list.

## Step 4: Create WROS user account for new employee (optional)

- If the employee needs WROS access (Technical Interviewer, RM, etc.): HR can trigger account creation.

- POST /api/employees/{id}/create-wros-account: creates users record, sends welcome email with temporary password.

- Not all employees need WROS accounts — only those with interviewing or management roles.

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: Conversion Is Atomic — All or Nothing

convertCandidateToEmployee() runs within a single database transaction. If any step fails (employee INSERT, demand UPDATE, state transition): the entire transaction rolls back. No partial conversions. No orphaned employee records.

↳ Triggered by field: Transaction wraps all conversion steps

## BR-02: Joining Stage Only Shown After Conversion

HRMS-P059 Journey Dashboard JOINED stage turns green ONLY after employees record is created. The joined date comes from employees.joining_date, not from offers.start_date.

↳ Triggered by field: JOINED stage driven by employees record existence

## BR-03: Employee Starts on Bench After Conversion

All new employees start with billing_classification=BENCH and status=ACTIVE. They are moved to ALLOCATED only when HRMS-0507 assigns them to a project. This is the default state — no project = bench.

↳ Triggered by field: billing_classification=BENCH at conversion

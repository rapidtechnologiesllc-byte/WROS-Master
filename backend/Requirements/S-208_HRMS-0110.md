## Why — Business Rationale

- BlitzenX's hard business rules only mean something if every override, gate decision, and state change against them is provably recorded — not recorded, provably recorded, in a form nobody, including an Admin, can quietly edit after the fact. Section 7.1 promises an audit trail on every critical entity; this story is what actually makes that promise true rather than aspirational.

## What — Scope

- A single, immutable audit_log table and a write helper every other story calls instead of writing its own ad-hoc history table — one consistent shape for who changed what, from what value, to what value, when, and from where, across the entire platform.

## Before — Prerequisites

- HRMS-0109 Multi-Tenant Data Isolation must be live — audit rows are tenant-scoped like everything else.

## Implementation Steps

## Step 1: Create audit_log table

- Run CREATE TABLE per Data Mapping.

- Columns: entity_type, entity_id, user_id, old_value (JSON), new_value (JSON), timestamp, ip_address, tenant_id.

## Step 2: Build the writeAuditLog() helper

- Single shared function every mutating endpoint calls.

- Captures before/after state as JSON snapshots, not just a change description string.

## Step 3: Enforce append-only at the DB layer

- Database-level trigger or permission grant that blocks UPDATE and DELETE on audit_log for all roles including Admin.

- Only INSERT is permitted — no exceptions, no admin override path.

## Step 4: Wire into existing hard-rule override points

- R-01 through R-10 override actions (bench-first override, timesheet override, etc.) call writeAuditLog() as part of the override transaction, not as an afterthought.

## Business Rules

## BR: BR-0110-01 — audit_log is append-only, enforced at the database layer

- No role, including Admin, can UPDATE or DELETE an audit_log row — enforced by DB permission grants, not application-layer checks that could be bypassed.

- Field: DB-level GRANT excludes UPDATE/DELETE on audit_log for all application roles

BR: BR-0110-02 — Every hard-rule override writes an audit_log row as part of the same transaction

- The override action and its audit record are atomic — if the audit write fails, the override itself must not commit.

- Field: Override transactions wrap both the state change and writeAuditLog() call in one DB transaction

## Acceptance Criteria

- AC-1: An attempted UPDATE or DELETE against audit_log fails at the database level regardless of the calling role.

- AC-2: Every R-01 through R-10 override action produces exactly one audit_log row in the same transaction as the override.

- AC-3: A failed audit write rolls back the associated override transaction — verified by forcing an audit write failure.

- AC-4: Audit records capture full before/after JSON snapshots, not summary strings.

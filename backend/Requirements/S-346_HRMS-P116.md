## 2. WHY THIS EXISTS

WhatsApp and email are async — the candidate sends a message and waits hours for Thunder to respond. For candidates actively browsing the portal, that delay is a conversion killer. A real-time chat widget within the portal gives candidates immediate, synchronous responses from Thunder while they are actively engaged — when their attention and interest are at their peak.

CRITICAL DESIGN PRINCIPLE: The portal chat widget is not a separate conversation thread. Every message sent through the portal chat is stored in the SAME conversation_messages table with channel=PORTAL, under the SAME conversation_id as the candidate's WhatsApp and email exchanges. When Thunder responds in the portal chat, it has read the candidate's ENTIRE cross-channel history — their WhatsApp messages from last week, their email from yesterday, and the current portal session. The candidate never needs to repeat themselves.

This is also the richest behavioral intelligence source for HRMS-P117. What the candidate types in real-time chat, what questions they ask unprompted, what words they use — this is pure signal about their desires, fears, and motivations.

## 3. WHAT YOU ARE BUILDING

Build: (1) Floating chat widget in the candidate portal — persistent across all portal pages. (2) Real-time message exchange using WebSocket or long-polling. (3) Thunder responds using full cross-channel context (not just chat history). (4) Typing indicator when Thunder is generating a response. (5) Chat history loads the FULL conversation from all channels — not just previous chat messages.

The chat widget is Thunder's real-time presence in the portal. The candidate sees the same ⚡ Thunder avatar and the same conversation they have been having across all channels.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Build the chat widget frontend component

- Floating button in bottom-right corner of ALL portal pages: ⚡ with 'Chat with Thunder' label. Unread count badge if Thunder sent messages since last portal visit.

- Click opens a slide-up chat panel (mobile) or floating window (desktop). Does NOT navigate away from current page.

- Chat panel: header 'Thunder — BlitzenX Talent Scout'. Close button. Message thread. Input box at bottom.

- Message thread: shows ALL messages from this candidate's conversation — WhatsApp, email, AND portal — in chronological order. Same rendering as HRMS-P106 Messages page. This is NOT a separate chat — it is the same conversation.

- Candidate types message → sends via HRMS-0404 portal message endpoint → WebSocket/poll delivers Thunder's response in real time.

## Step 2: Build real-time response delivery (WebSocket or long-poll)

- Preferred: WebSocket connection at /ws/candidate/{conversation_id}/chat — candidate browser connects on chat open, disconnects on close.

- On new outbound message from Thunder (any channel): push to connected WebSocket clients for this conversation_id.

- Fallback (if WebSocket not available): long-poll at GET /api/portal/conversations/{id}/messages/poll?after={last_message_id} with 20-second timeout. Client re-polls immediately after response.

- Target: Thunder's response appears in chat within 5 seconds of candidate sending message.

## Step 3: Build Thunder typing indicator

- When Thunder starts generating a response: push event THUNDER_TYPING to the candidate's WebSocket connection.

- Show typing indicator in chat: '⚡ Thunder is typing...' with animated dots.

- When response is ready and sent: push THUNDER_RESPONSE event which replaces typing indicator with the message.

- If generation takes >8 seconds: update typing indicator to '⚡ Thunder is thinking... 🤔' (reassures candidate that something is happening).

## Step 4: Build full cross-channel context for chat responses

- When candidate sends a chat message: Thunder's response generation flow is IDENTICAL to WhatsApp/email response — it calls buildCandidateContext() which loads ALL channel messages.

- The context loaded for a chat response includes: last 15 messages from WhatsApp, email, AND portal. All memory facts. Current conversation state. Missing fields.

- Thunder's chat response must reflect the full relationship. If candidate answered their salary on WhatsApp last week, Thunder's chat response acknowledges this — it does NOT ask again.

- The chat widget is a window into the single unified conversation. It is not a new conversation.

## Step 5: Build chat behavioral signal emission

- Every chat interaction emits signals to HRMS-P117 Desire Intelligence Engine:

- chat.message_sent: { candidate_id, message_length, hour_of_day, portal_page_at_time (which portal page they were on), response_wait_seconds (how long they waited before asking again) }

- chat.session_opened: { candidate_id, time_on_portal_before_opening, portal_page }

- chat.session_closed: { candidate_id, session_duration_seconds, messages_sent_count }

- These signals feed the desire intelligence layer without affecting the chat experience.

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: Chat Widget Shows FULL Cross-Channel History — Not Chat-Only History

When a candidate opens the chat widget, the message thread shows ALL messages from their complete conversation — WhatsApp, email, and portal — not just previous chat session messages. This ensures the candidate sees their full relationship with Thunder and never feels like they are starting over.

↳ Triggered by field: conversation_messages (all channels) displayed in chat

## BR-02: Thunder's Chat Responses Use Full Cross-Channel Context

generateThunderResponse() for chat uses buildCandidateContext() which includes ALL channel messages. A chat response that ignores the candidate's WhatsApp history is a conversation failure. There is no such thing as 'chat-only context' in this system.

↳ Triggered by field: buildCandidateContext() always called — all channels

## BR-03: Real-Time Target: Response Within 5 Seconds

Thunder's chat response must appear in the candidate's chat within 5 seconds of sending. This requires: fast context build (<500ms), fast LLM call (<4s), fast delivery (<500ms). If LLM takes longer: typing indicator buys time. If >10 seconds: fallback response sent immediately, real response sent when ready.

↳ Triggered by field: 5-second response target

## BR-04: Chat Behavioral Signals Are Non-Blocking

Emitting behavioral signals (chat.message_sent, chat.session_opened) to HRMS-P117 must be non-blocking fire-and-forget. Signal emission failure must never slow down or break the chat experience.

↳ Triggered by field: behavioral signal emission is async fire-and-forget

## Why — Business Rationale

- Every open sourcing alert today waits for a recruiter to manually construct a Boolean search string, run it across LinkedIn, copy results into a spreadsheet, and deduplicate by hand. That's hours of mechanical work per demand that adds no judgment BlitzenX is actually paying a recruiter for. This agent removes the mechanical middle step entirely so the recruiter's time goes to evaluating candidates, not finding them.

## What — Scope

- A continuous loop that consumes open sourcing_alerts from HRMS-1102, generates an optimized Boolean search string per demand's required skills, executes it against the LinkedIn Recruiter API, deduplicates results against the existing candidate database via createCandidateSafe()'s dedup path, and stages the clean candidate list for HRMS-1104 outreach.

## How is Agentic AI Used in This

- Trigger cadence: consumes sourcing_alerts with status=OPEN as a queue, processes continuously (not batch).

- LLM call (claude-sonnet-4-6, max_tokens=800): given required_skills, seniority_level, and demand_type, generates an optimized Boolean search string plus 2-3 alternate phrasings for skill synonyms (leveraging the canonical skill-name synonym library referenced from HRMS-0429).

- Output schema: {boolean_query, alt_queries[], search_rationale, estimated_result_volume}.

- Pre-authorized action (LOW risk, auto-executes): running the generated query against LinkedIn Recruiter API and staging deduplicated results — this never creates a candidate record directly, it only stages for review.

- MEDIUM risk gate: candidate creation is NEVER performed by this agent directly — every staged result must pass through createCandidateSafe() with a human-visible review step before becoming a real candidate record, per R-07.

## Before — Prerequisites

- EPIC-P9 Boolean Search Engine core query-execution service must be live (this agent calls it, does not reimplement it).

- HRMS-0429 canonical skill synonym library must be queryable for skill-phrase expansion.

## Implementation Steps

## Step 1: Create sourcing_search_runs and staged_candidates tables

- Run CREATE TABLE statements in Data Mapping.

## Step 2: Build the alert-consumption loop

- Poll sourcing_alerts WHERE status=OPEN ORDER BY severity DESC, created_at ASC.

- Lock the row (status=PROCESSING) before starting to prevent duplicate processing by concurrent workers.

## Step 3: Generate Boolean query via LLM

- Fetch required_skills and demand context for the alert's demand_id.

- Call LLM with skill synonym library context injected into the prompt.

- Store boolean_query, alt_queries, rationale in sourcing_search_runs.

## Step 4: Execute search and deduplicate

- Call EPIC-P9 Boolean Search Engine execution endpoint with the generated query.

- For each result, call the dedup-check portion of createCandidateSafe() (read-only dedup check, does NOT create a record) to filter out existing candidates.

- Insert surviving results into staged_candidates with status=PENDING_REVIEW.

## Step 5: Hand off to Outreach Agent

- Publish agent.action.intent to Orchestration Router for entity_type=staged_candidate_batch.

- Mark sourcing_alerts row status=SOURCED, timestamp sourced_at.

## Business Rules

## BR: BR-1103-01 — This agent never calls createCandidateSafe()'s CREATE path

- Per R-07, only createCandidateSafe() creates candidate records, and this agent uses only its dedup-check sub-function. Staged candidates remain non-authoritative until a recruiter promotes them.

- Field: staged_candidates table is entirely separate from candidates table — no FK, explicit promotion step required

BR: BR-1103-02 — Recruiter promotion of a staged candidate is the only path to a real record

- A staged_candidates row becomes a candidates row only when a recruiter clicks Promote, which internally calls the full createCandidateSafe() creation path including consent capture.

- Field: staged_candidates.promoted_to_candidate_id set only via explicit recruiter action

## BR: BR-1103-03 — Duplicate alert processing is prevented by row locking

- A sourcing_alerts row moves to PROCESSING status atomically before any search executes, preventing two workers from double-sourcing the same demand.

- Field: sourcing_alerts.status transition OPEN->PROCESSING uses SELECT FOR UPDATE

## Integrations

| HRMS-1101 Orchestration Router | Outbound | Before staged batch handoff | entity_type=staged_candidate_batch | Internal service auth | On Failure: fail-open per BR-1101-06 |

## Acceptance Criteria

- AC-1: A new OPEN sourcing alert is picked up and moved to PROCESSING within one polling cycle (target: 2 minutes).

- AC-2: The generated Boolean query includes skill synonyms sourced from the HRMS-0429 library, verified against a known skill with multiple synonyms.

- AC-3: No candidates table row is ever created directly by this agent — verified by absence of INSERT into candidates outside the recruiter-promotion code path.

- AC-4: A CONFIRMED_DUPLICATE dedup result is excluded from staged_candidates.

- AC-5: Two concurrent workers processing the same alert never both execute a search — verified via row-lock test.

- AC-6: Search Boolean Search Engine failure after 2 consecutive attempts notifies the RM.

## Not In Scope

- No automatic candidate creation or automatic outreach — staging and query generation only, per R-07.

- No scraping of LinkedIn outside the official Recruiter API — no workarounds for rate limits or ToS boundaries.

- No cross-platform sourcing (Indeed, Naukri, etc.) in this story — LinkedIn only, other sources are separate future stories.

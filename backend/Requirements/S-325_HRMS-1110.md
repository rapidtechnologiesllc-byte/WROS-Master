## Why — Business Rationale

- Every agent in this epic is designed to act without a human present. That design only holds up if there is one reliable place, checked every single morning, where every autonomous action taken overnight is visible — every send, every allocation trigger, every blocked conflict, every escalation, and every near-miss. Without this, 'it works on its own while I'm sleeping' is a claim nobody can actually verify. This report is not a nice-to-have summary; it is the audit checkpoint the entire unattended-agent design depends on.

## What — Scope

- A job that runs at 06:00 daily, compiles every action taken by every agent in HRMS-1101-1108 during the prior 24 hours (LOW-risk auto-executed actions, MEDIUM/HIGH actions routed to human queues, every blocked or escalated conflict, every self-healed and every paged integration failure), and delivers a single consolidated report to the Director before the start of business.

## How is Agentic AI Used in This

- Like HRMS-1109, this is explicitly a scheduled reporting job, not a real-time autonomous agent — it takes no action and is excluded from Orchestration Router conflict monitoring for the same reason.

- LLM call (claude-sonnet-4-6, max_tokens=1000): given the full structured event log from the prior 24 hours across all 8 operational agents, produces a prioritized plain-language summary — leading with anything that needed and didn't get a timely human response, followed by a categorized tally of routine auto-executed actions.

- This report must be complete, not merely a highlight reel — every LOW-risk auto-executed action is counted even if not individually narrated, so nothing is silently omitted from the audit trail.

## Before — Prerequisites

- All of HRMS-1101 through HRMS-1108 must be emitting structured, queryable event logs — this story consumes those logs, it does not define new logging in each agent retroactively.

## Implementation Steps

## Step 1: Create daily_activity_reports table

- Run CREATE TABLE statement in Data Mapping.

## Step 2: Aggregate the prior 24 hours of agent activity

- Pull all agent.action.intent, agent.action.blocked, and agent.action.completed events from HRMS-1101's orchestration_events log.

- Pull all self-heal and page events from HRMS-1108's integration_health_checks log.

- Pull all sourcing, outreach, allocation, and monitoring actions from HRMS-1102-1107 respectively.

## Step 3: Categorize by outcome

- needs_attention: any MEDIUM/HIGH risk item still pending human review after 24 hours, any BLOCKED_OWNERSHIP outreach sequence, any unresolved integration page.

- auto_executed_summary: count of LOW-risk actions per agent, not individually listed.

- escalations_sent: full list of every HIGH severity page sent overnight, with response status.

## Step 4: Generate the narrative

- Call LLM with the categorized dataset — needs_attention items always listed individually with full context; auto_executed items summarized as counts.

## Step 5: Deliver

- Send via HRMS-0113 to Director at 06:00, before business hours, every day including weekends.

- Report remains accessible in-app indefinitely for audit purposes — not just delivered and discarded.

## Business Rules

## BR: BR-1110-01 — Every LOW-risk action is counted, none silently omitted

- Even routine auto-executed actions not individually narrated in the summary must appear in the count-by-agent breakdown — the report must be a complete audit trail, not a curated highlight reel.

- Field: auto_executed_summary counts must reconcile exactly against the underlying event log row counts

## BR: BR-1110-02 — Report generates every day without exception, including weekends

- Since agents run unattended every day, the audit checkpoint cannot skip weekends or holidays — a gap in the report series is itself a signal something is wrong.

- Field: daily_activity_reports has exactly one row per calendar date, enforced by unique constraint on report_date

## BR: BR-1110-03 — needs_attention items persist in the report until resolved

- An item that was needs_attention yesterday and remains unresolved today appears again today, not just once — so nothing pending quietly ages out of visibility.

- Field: needs_attention query includes items pending beyond 24 hours regardless of when originally flagged

## Acceptance Criteria

- AC-1: A report is generated and delivered every calendar day at 06:00, with zero gaps over a 30-day test window including weekends.

- AC-2: auto_executed_summary counts reconcile exactly against the underlying event log for that 24-hour window.

- AC-3: A needs_attention item still unresolved after 24 hours appears in the following day's report as well, not just the day it was first flagged.

- AC-4: An event-log source outage produces a partial report explicitly flagged incomplete, delivered on time, rather than a delayed or skipped report.

- AC-5: Failure to deliver the report itself pages on-call directly, distinct from the standard 3x-retry-then-email fallback used elsewhere.

## Not In Scope

- No automatic resolution of needs_attention items — this report only surfaces them, a human still has to act.

- No real-time streaming version of this report — it is explicitly a once-daily consolidated checkpoint, not a live feed (live visibility already exists per-agent).

- No agent scaffolding (action-intent events, Orchestration Router registration) — same reasoning as HRMS-1109, this job takes no action.

## Why — Business Rationale

- Recruiters currently notice a supply gap only after a demand has already been open for days and the bench search has already failed. By the time a human looks at the pipeline, BlitzenX has lost the head start needed to hit SLA. This agent's entire purpose is to compress the time between 'a gap is forming' and 'sourcing has started' from days to minutes, without waiting for a human to notice the trend first.

## What — Scope

- A continuously running agent that watches every open demand against current bench supply and in-flight submissions, computes a real-time gap score per skill/role combination, and — once bench insufficiency is confirmed per R-04 — automatically opens a sourcing alert that HRMS-1103 picks up. It does not source candidates itself; it decides WHEN sourcing needs to start and for WHAT.

## How is Agentic AI Used in This

- Trigger cadence: runs every 15 minutes against all demands with status=OPEN or status=IN_PROGRESS.

- LLM call (claude-sonnet-4-6, max_tokens=600): given a demand's required skills, current bench-matching candidate count, and days-open, the model returns a structured gap_severity (NONE/WATCH/ALERT/CRITICAL) and a one-line rationale — it does not decide to source, only how urgent the gap is.

- Pre-authorized action (LOW risk, auto-executes): for ALERT or CRITICAL severity, after confirming BenchFirstPolicyEngine.check() returns insufficient, the agent auto-creates a sourcing_alert row and publishes agent.action.intent to the Orchestration Router before HRMS-1103 acts on it.

- Escalation threshold: CRITICAL severity on a demand open for more than 5 days routes directly to the RM via HRMS-0113, in addition to the auto-created sourcing alert — this is a MEDIUM-risk notification, not an irreversible action, so it does not require human pre-approval to send.

## Before — Prerequisites

- HRMS-0228 BenchFirstPolicyEngine.check() must be callable synchronously with a demand_id and return a boolean plus supporting bench-candidate count.

- HRMS-1101 Orchestration Router must be live so sourcing alerts can be intent-checked before publish.

## Implementation Steps

## Step 1: Create demand_gap_scores table

- Run CREATE TABLE statement in Data Mapping.

- One row per (demand_id, scored_at) — full history retained, not overwritten, for trend analysis.

## Step 2: Build the 15-minute scan job

- Query all demands with status IN (OPEN, IN_PROGRESS) and demand_type = PLANNED or ADHOC.

- For each, count current bench candidates matching required_skills via existing skill-matching index.

- Call BenchFirstPolicyEngine.check(demand_id) — record result on the score row.

## Step 3: Call the gap severity classifier

- Build LLM prompt from: required_skills, bench_match_count, days_open, demand_type, p1_emergency flag.

- Parse structured JSON response: {gap_severity, rationale}. Reject and retry once on malformed JSON; on second failure, default gap_severity to WATCH and log llm_parse_failed=true.

## Step 4: Auto-create sourcing alerts for ALERT/CRITICAL

- Only if BenchFirstPolicyEngine.check() confirms insufficiency (R-04 hard gate — no override here).

- Publish agent.action.intent to Orchestration Router with risk_tier=LOW before creating the row.

- Insert sourcing_alerts row with status=OPEN, severity, rationale, demand_id.

## Step 5: Route CRITICAL + 5-day-open to RM directly

- Query RM assigned to the demand's account.

- Send HRMS-0113 notification with demand summary, gap history link, rationale.

## Business Rules

## BR: BR-1102-01 — R-04 Bench-First is the hard gate before any sourcing alert

- Sourcing alert can only be auto-created if BenchFirstPolicyEngine.check() returns insufficient. This agent has no authority to bypass R-04.

- Field: sourcing_alerts.created_at requires bench_first_check_passed=true

## BR: BR-1102-02 — Bench-first override requires 100+ char justification

- If an RM manually overrides bench-first via this screen, the justification field must be at least 100 characters, matching the platform-wide R-04 override rule.

- Field: Override Bench-First field, min length validation = 100

## BR: BR-1102-03 — CRITICAL severity always notifies the RM, regardless of time of day

- Unlike LOW-risk auto-actions, CRITICAL demand-gap notifications to the RM are not batched into the morning digest — they send immediately, 24/7.

- Field: gap_severity=CRITICAL AND days_open > 5 triggers immediate HRMS-0113 send

## BR: BR-1102-04 — Score history is append-only

- demand_gap_scores rows are never updated or deleted, only inserted, to preserve an accurate trend line for the Learning Optimisation job (HRMS-1109).

- Field: demand_gap_scores — INSERT only, no UPDATE/DELETE at application layer

## Acceptance Criteria

- AC-1: A demand with zero bench matches and required_skills populated produces a gap_severity of ALERT or CRITICAL within one scan cycle (15 minutes).

- AC-2: No sourcing_alerts row is created unless BenchFirstPolicyEngine.check() returned insufficient=true for that demand.

- AC-3: An RM override of bench-first is rejected by the UI if the justification is under 100 characters.

- AC-4: A CRITICAL severity demand open more than 5 days generates an HRMS-0113 notification to the assigned RM within the same scan cycle it crosses the threshold.

- AC-5: demand_gap_scores retains full history — no row is ever updated after insert, verified by absence of UPDATE statements in query logs.

- AC-6: LLM call failure defaults severity to WATCH and does not create a sourcing alert, verified by injected API failure in staging.

## Not In Scope

- No candidate sourcing execution — that is HRMS-1103's job, this agent only detects and flags the gap.

- No automatic override of the bench-first gate under any circumstance — only a human-entered, validated override is permitted.

- No predictive forecasting of FUTURE demand — that is EPIC-03 Workforce Planning territory, this agent only scores CURRENT open demands.

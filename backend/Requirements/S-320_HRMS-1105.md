## Why — Business Rationale

- The Core-pull rule itself (Section 4.3) is already a deterministic, non-negotiable code-level rule — it does not need an agent to decide that Core wins, that decision is already made by policy. What's missing is a continuous watcher that notices a Core-pull SITUATION exists before an RM has to go looking for it, and that keeps bench utilization visible in real time instead of relying on a recruiter running a report at the end of the week.

## What — Scope

- An agent that continuously monitors bench utilization and resource-allocation conflicts, detects when a Core demand and a Speciality demand are both eligible to claim the same bench resource, triggers the existing deterministic HRMS-0312 Core-pull engine (this agent does not itself decide Core wins — that logic already exists and is not duplicated here), and produces bench allocation recommendations for RM review.

## How is Agentic AI Used in This

- Trigger cadence: runs every 30 minutes against active bench pool and open demand matches.

- LLM call (claude-sonnet-4-6, max_tokens=700) — used ONLY for the advisory allocation recommendation, never for Core-pull detection (that is a deterministic lookup, not an LLM decision): given a bench candidate's skill profile and multiple eligible open demands, ranks the best-fit demand assignment with rationale and confidence_pct.

- Pre-authorized action (LOW risk, auto-executes): when a bench resource matches both a Core and a Speciality demand simultaneously, the agent calls the existing HRMS-0312 Core-pull engine — it does not make the Core-wins decision itself, it only detects the situation and invokes the rule that already exists.

- Advisory-only action (requires human approval, per Section 8.2): the bench allocation ranking for non-conflicting assignments is surfaced to the RM as a recommendation and never auto-assigns a resource to a project — allocation is an irreversible-enough action (it affects billing and utilization reporting) that it stays in the human queue.

## Before — Prerequisites

- HRMS-0312 Core-pull engine (delivery_engine reassignment logic) must already exist and be callable — this story does not rebuild it, only triggers it.

- HRMS-0510 Utilization Tracking must expose current bench-pool composition in near-real-time.

## Implementation Steps

## Step 1: Create bench_allocation_recommendations table

- Run CREATE TABLE statement in Data Mapping.

## Step 2: Build the 30-minute bench scan

- Query current bench pool from HRMS-0510.

- For each bench employee, find all open demands where skill match score exceeds threshold.

## Step 3: Detect Core-vs-Speciality simultaneous eligibility

- If a bench employee matches both a delivery_engine=CORE demand and a delivery_engine=SPECIALITY demand concurrently, call HRMS-0312's existing Core-pull trigger — do not implement new Core-wins logic here.

- Publish agent.action.intent to Orchestration Router before triggering (risk_tier=MEDIUM, since it affects allocation).

## Step 4: Rank non-conflicting allocation options

- For bench employees with only single-engine matches, call the LLM ranker for best-fit demand.

- Store ranking, rationale, confidence_pct in bench_allocation_recommendations with status=PENDING_RM_REVIEW.

## Step 5: Surface to RM queue

- RM views recommendations sorted by confidence_pct descending.

- RM action (approve/reject) is the only path that actually creates an employee_allocations row — this agent never writes to employee_allocations directly.

## Business Rules

## BR: BR-1105-01 — Core-pull decision logic is never duplicated here

- This agent detects simultaneous eligibility and CALLS HRMS-0312; it does not reimplement Section 4.3's Core-wins rule. Single source of truth for that rule remains HRMS-0312.

- Field: Core-pull trigger is a function call to HRMS-0312, not a local conditional

## BR: BR-1105-02 — Allocation recommendations are advisory only, per Section 8.2

- No employee_allocations row is ever created by this agent directly. Only an RM's explicit APPROVED status creates the allocation.

- Field: employee_allocations INSERT only occurs from RM-approval code path, never from agent scan

## BR: BR-1105-03 — Core-pull detection publishes MEDIUM risk_tier, not LOW

- Because triggering Core-pull affects live project staffing, it is classified MEDIUM risk in the Orchestration Router intent event, distinguishing it from the LOW-risk advisory ranking.

- Field: agent.action.intent risk_tier=MEDIUM for corepull_trigger action_type

## Acceptance Criteria

- AC-1: A bench employee matching both a CORE and SPECIALITY demand simultaneously triggers HRMS-0312 within one scan cycle, without this agent implementing its own Core-wins conditional.

- AC-2: No employee_allocations row is created directly by this agent under any condition — verified by code review and integration test.

- AC-3: A Core-pull trigger event publishes risk_tier=MEDIUM to the Orchestration Router, distinct from LOW-risk ranking events.

- AC-4: A single-engine-match bench employee receives a ranked recommendation with confidence_pct and rationale within one scan cycle.

- AC-5: Two consecutive HRMS-0510 scan failures generate an alert.

- AC-6: A Core-pull engine call failure alerts the BU Head immediately, not via next-morning digest.

## Not In Scope

- No reimplementation of the Core-wins policy logic — Section 4.3 lives in HRMS-0312 only, this agent is a detector and caller, not a decision-maker.

- No automatic allocation creation, ever — allocation is always an RM-approved action.

- No cross-BU bench pooling logic — this story respects existing BU-scoped access per Section 12.

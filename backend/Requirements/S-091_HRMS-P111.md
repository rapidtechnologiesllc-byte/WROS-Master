## 2. WHY THIS EXISTS

The candidate portal must never require a password. Candidates are not employees — creating an account and remembering a password adds friction that kills conversion. A magic link sent by Thunder via WhatsApp or email authenticates the candidate with one tap, creating a 7-day session. This is the standard authentication pattern for candidate-facing portals.

## 3. WHAT YOU ARE BUILDING

Build: (1) Magic link token generation and storage. (2) Link delivery via Thunder's WhatsApp and email. (3) Token validation endpoint. (4) Session management (httpOnly cookie). (5) Token revocation. (6) Expired link page.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Create candidate_auth_tokens table

- CREATE TABLE candidate_auth_tokens: id UUID PK, tenant_id UUID, candidate_id UUID FK→candidates.id, token VARCHAR(128) UNIQUE NOT NULL, expires_at TIMESTAMP NOT NULL, is_revoked BOOLEAN default false, created_at TIMESTAMP, last_used_at TIMESTAMP nullable, created_via ENUM('WHATSAPP','EMAIL','SYSTEM') default 'SYSTEM'

- Index on token. Index on (candidate_id, tenant_id).

## Step 2: Build generateMagicLink() function

- generateMagicLink(candidate_id, tenant_id, delivery_channel) → { token, url, expires_at }

- Generate cryptographically secure random token: 64-byte hex string (128 chars). Use crypto.randomBytes(64).toString('hex') or equivalent.

- INSERT candidate_auth_tokens: token, expires_at=NOW()+7 days, created_via=delivery_channel

- Return URL: https://{portal_domain}/candidate/{token}

- Revoke any existing active tokens for this candidate before creating new one (one active token per candidate)

## Step 3: Build GET /api/candidate-auth/validate endpoint

- GET /api/candidate-auth/validate?token={token}

- SELECT * FROM candidate_auth_tokens WHERE token=X AND is_revoked=false AND expires_at > NOW()

- If not found or expired: return HTTP 401 { error: 'LINK_EXPIRED', message: 'This link has expired. Ask Thunder for a new link.' }

- If valid: UPDATE last_used_at=NOW(). Set httpOnly session cookie (secure, SameSite=Strict, maxAge=7 days). Response: { candidate_id, candidate_name, tenant_id, expires_at }

## Step 4: Build link delivery via Thunder

- sendPortalLink(candidate_id, tenant_id) — called when: (1) candidate requests portal access, (2) Thunder determines portal is needed for an action (e.g. offer viewing)

- Generate magic link via generateMagicLink()

- WhatsApp: 'Here is your personal BlitzenX portal link: [URL]. It's valid for 7 days and gives you access to your conversation, profile, and any interview or offer details. Tap to open ⚡'

- Email: same message with HTML button 'Open My Portal'

- Store as conversation_messages (channel=WHATSAPP / channel=EMAIL)

## Step 5: Build token revocation and expiry handling

- POST /api/candidate-auth/revoke — requires valid session. Sets is_revoked=true. Used when candidate explicitly logs out.

- GET /candidate/{expired_token}: validate call returns 401 → portal shows expired page: 'This link has expired. Reply to Thunder's WhatsApp message to get a new link.' No login page. No password field. Just one sentence with instructions.

- TokenCleanupJob: daily, DELETE tokens WHERE expires_at < NOW() - 30 days (soft cleanup, keep recent expired for audit).

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: One Active Token Per Candidate

Before creating a new token: revoke all existing non-expired tokens for this candidate+tenant. A candidate can only have one valid portal link at a time. If Thunder sends a new link: the old one stops working.

↳ Triggered by field: is_revoked=true on previous tokens before new generation

## BR-02: Token Is 128-Character Cryptographically Random Hex

Never use sequential IDs, candidate_id, or guessable values as tokens. Minimum 128-character cryptographically random hex. This prevents token guessing attacks.

↳ Triggered by field: crypto.randomBytes(64).toString('hex')

## BR-03: Never Store Token in URL After Validation

After the token is validated at /candidate/{token}: redirect to /candidate/portal/home with session cookie. Do not keep the token in the URL bar. Token in URL = visible in browser history, server logs, referrer headers.

↳ Triggered by field: Redirect after validation — token not in subsequent URLs

## Why — Business Rationale

- The explicit vision for WROS is that recruiting, HR, finance, and consultants work inside one system — not WROS for records and Outlook/Teams for everything that actually happens day to day. But rebuilding email and chat from scratch would be years of work duplicating something Microsoft already does well, and BlitzenX already pays for. The right answer, and the one explicitly directed, is architectural: WROS becomes the single place employees start their day, with Outlook and Teams embedded inside it as tabs rather than separate destinations — the same login, the same window, no app-switching, but WROS remains the home screen rather than one more icon on a taskbar.

## What — Scope

- Single sign-on between WROS and Microsoft 365 (Outlook, Teams, SharePoint) via Azure AD/Entra ID, plus the embedding shell infrastructure — an in-app tab framework and a persistent bottom-dock region — that S-380 (Outlook) and S-381 (Teams) render inside. This story is the plumbing; it renders nothing user-visible on its own beyond the SSO handshake and the empty tab/dock framework.

## Before — Prerequisites

- HRMS-0111 Core Navigation & Search Shell must be live — the embedded tabs and dock render inside that existing shell, not a separate frame.

- BlitzenX's Azure AD/Entra ID tenant must be configured to trust WROS as a registered application with the necessary Graph API scopes (Mail.Read, Chat.ReadWrite, Files.ReadWrite for SharePoint) pre-approved by IT.

## Implementation Steps

## Step 1: Implement Azure AD/Entra ID SSO

- OAuth2/OIDC flow: a WROS login also silently establishes a Microsoft Graph API session token, stored server-side, never exposed to the browser.

- One login, one session — a user never separately authenticates to Outlook or Teams once inside WROS.

## Step 2: Build the embedded tab framework

- A tab region in the WROS nav shell (per HRMS-0111) that can host an embedded Microsoft application view — this story builds the generic tab container; S-380 and S-381 are the first two tabs to actually use it.

- Tabs persist across WROS navigation — switching from the Candidates screen to the Email tab and back doesn't reload either.

## Step 3: Build the persistent bottom dock

- A collapsible dock region, positioned per Riya's direction ('like the taskbar at bottom'), reserved for the Teams chat launcher (S-381) and future quick-access tools.

## Step 4: Build the notification bridge

- Microsoft Graph webhook subscription for new Teams messages and calendar invites, surfaced as WROS-native pop-up notifications (bottom-right, matching HRMS-0113's existing in-app notification pattern) rather than requiring the user to have the dock open to notice activity.

## Business Rules

## BR: BR-1401-01 — One login covers both WROS and the embedded Microsoft 365 surfaces

- A user must never see a second login prompt for Outlook or Teams after authenticating to WROS — the whole point of embedding is eliminating app-switching friction, and a second login defeats that.

- Field: Graph API session token is silently established as part of the WROS login flow, stored server-side

## BR: BR-1401-02 — Graph API tokens are never exposed client-side

- The embedded tabs render via server-brokered content, not by handing the browser a raw Microsoft token — keeps the same security discipline as every other credential in the platform (secrets manager pattern used throughout Section 11's integrations).

- Field: All Graph API calls proxy through the WROS backend; the browser never holds a Microsoft access token directly

BR: BR-1401-03 — This story renders no content of its own — it is pure shell and auth infrastructure

- Keeps this story's scope honestly separated from S-380 and S-381, which are the actual visible features users interact with.

- Field: No Outlook or Teams content rendering logic exists in this story's codebase — only the tab/dock container and SSO bridge

## Integrations

| System / API | Direction | Trigger | Payload | Auth | Notes |
|---|---|---|---|---|---|
| Azure AD / Entra ID | Bidirectional | On every WROS login | OAuth2/OIDC token exchange | Registered app credentials, IT-approved scopes | On Failure: WROS login itself must still succeed — Graph API session establishment failure degrades gracefully to 'Reconnect Required' rather than blocking WROS access entirely |
| Microsoft Graph API | Inbound (webhook) | New Teams message, new calendar invite | notification payload | Server-side Graph session token | On Failure: notification bridge silently misses that event; user still sees it when they open the Teams dock directly, no data loss, just delayed visibility |

## Acceptance Criteria

- AC-1: A user logging into WROS never sees a separate Outlook or Teams login prompt during the same session.

- AC-2: No Microsoft Graph API token is ever present in any client-side (browser) network request or storage — verified by inspecting network traffic.

- AC-3: A Graph API session failure degrades to a 'Reconnect Required' indicator without blocking the user's access to the rest of WROS.

- AC-4: A new Teams message triggers a WROS-native pop-up notification within the standard notification SLA.

## Not In Scope

- No native email or chat client — this is an embedding/SSO framework, not a Microsoft 365 replacement, matching the explicit direction to integrate rather than rebuild.

- No offline/disconnected mode for the embedded tabs — they require an active Graph API session, same as using Outlook or Teams directly would.

## Why — Business Rationale

- Nearly every hard rule and every agent in this platform ends the same way: someone needs to be told something happened. Without one shared notification backbone, every story that needs to alert a human would build its own bespoke send logic — meaning inconsistent delivery, no single place to see what fired and whether it was actually read, and a maintenance nightmare the moment WhatsApp's API changes. This is infrastructure exactly one other agentic story (HRMS-1108 Integration Health) is responsible for keeping alive.

## What — Scope

- A single notification dispatch service supporting in-app, email, and WhatsApp channels, with a priority tier (P0 immediate page / P1 same-day / P2 digest) that every other story calls instead of implementing its own send logic.

## Before — Prerequisites

- HRMS-0109 and HRMS-0103 must be live for tenant/role-scoped delivery.

- WhatsApp Business API and SMTP credentials must be provisioned per Section 11.

## Implementation Steps

## Step 1: Create notifications table

- Run CREATE TABLE per Data Mapping.

- One row per notification instance: recipient, channel, priority, payload, sent_at, read_at, delivery_status.

## Step 2: Build the sendNotification() dispatch function

- Single entry point: recipient_id, priority_tier, message, channel_preference.

- P0: immediate send, SMS+WhatsApp fallback if primary channel fails within 60 seconds.

- P1: same-day send, standard channel.

- P2: queued into next digest batch.

## Step 3: Build channel fallback logic

- If WhatsApp delivery fails or is unconfirmed within the SLA window for the priority tier, fall back to SMS (P0 only) or email (P1/P2).

## Step 4: Build the in-app notification center

- Bell icon in nav shell (depends on HRMS-0111), unread count badge, mark-as-read on open.

## Business Rules

BR: BR-0113-01 — P0 priority always attempts a fallback channel if primary is unconfirmed within 60 seconds

- A P0 notification (e.g., Director page for a CRITICAL agent alert) cannot silently fail on a single channel — matches the pattern required by EPIC-11's HRMS-0113 P0 channel usage.

- Field: notifications.delivery_status transitions to FALLBACK_SENT if primary unconfirmed at 60s for P0 only

## BR: BR-0113-02 — Every notification is tenant and role scoped at dispatch time

- sendNotification() validates the recipient belongs to the same tenant as the calling context before dispatch — prevents cross-tenant notification leakage.

- Field: Dispatch function checks recipient.tenant_id == calling_context.tenant_id before send

## BR: BR-0113-03 — Non-P0 notifications respect the recipient's local business hours

- A P1 or P2 notification does not send at the literal moment its trigger condition is met — it queues and releases at the next point the recipient's local time (per HRMS-0121's timezone configuration) falls within a configured business-hours window (default 08:00-20:00). P0 is the sole exception and fires immediately regardless of local time, since a P0 by definition represents something urgent enough that delaying it would be the bigger problem. This applies uniformly to every story that calls sendNotification() — including HRMS-1601's timesheet nag cascade and HRMS-1604's AR follow-up agent — without any of them needing to implement their own timezone logic.

- Field: notifications.scheduled_release_at (nullable) — if set, the notification is held until this computed business-hours release time rather than sent immediately; null for P0

## Acceptance Criteria

- AC-1: A P0 notification with an unconfirmed primary channel automatically attempts SMS fallback within 60 seconds.

- AC-2: A notification to a recipient outside the calling context's tenant is rejected before dispatch.

- AC-3: The in-app notification bell shows an accurate unread count and marks items read on open.

- AC-4: A P2 notification is queued into the next digest rather than sent immediately, verified by timestamp comparison.

- AC-5: A P1 notification triggered outside the recipient's local business-hours window (e.g., 3am their time) is held and released at the next in-window moment, never delivered at the literal trigger time.

- AC-6: A P0 notification bypasses business-hours gating entirely and sends immediately regardless of the recipient's local time.

## Not In Scope

- No message content generation or templating engine beyond simple variable substitution — content is the calling story's responsibility.

- No push notification / native mobile SDK integration in this story — in-app, email, WhatsApp, SMS only.

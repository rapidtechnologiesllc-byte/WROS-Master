## Why — Business Rationale

- Revenue trajectory deviation against plan is a well-understood, well-bounded number — Section 13 already defines the target (<10% variance by Q3). This does not need a judgment-making agent; it needs a reliable watcher that checks the deviation against a known threshold and tells the right person immediately when it's crossed, so a Director isn't discovering a revenue miss for the first time in a monthly review.

## What — Scope

- A deterministic threshold-monitoring job that compares actual revenue against plan per BU on a daily cadence, flags variance breaches and margin drops, and routes alerts by severity — no LLM judgment is used to detect the breach itself, only to write a plain-language summary of what changed.

## How is Agentic AI Used in This

- This is a monitor-and-flag agent, not a decision-making agent — breach detection is pure threshold arithmetic against HRMS-0313 data, deliberately kept deterministic so the trigger for a revenue alert is always explainable without needing to inspect an LLM's reasoning.

- LLM call (claude-sonnet-4-6, max_tokens=400), used only AFTER a deterministic breach is detected: summarizes which line items or clients are driving the variance, in plain language, for the alert body — it never decides whether a breach occurred.

- All actions here are LOW risk (notification only, no state-changing writes) and auto-execute — there is nothing to gate behind human approval since the agent takes no action beyond alerting.

## Before — Prerequisites

- HRMS-0313 Plan vs Actuals must expose daily variance_pct and margin_pct per BU.

## Implementation Steps

## Step 1: Create revenue_variance_checks table

- Run CREATE TABLE statement in Data Mapping.

## Step 2: Build the daily threshold check

- Pull variance_pct and margin_pct per BU from HRMS-0313, once daily at 06:00.

- Compare against thresholds: WATCH at >5% variance, ALERT at >10% variance (per Section 13 target), CRITICAL at >20% variance or any margin drop >5 percentage points week-over-week.

## Step 3: Generate plain-language summary for ALERT/CRITICAL

- Call LLM with the driving line items and clients behind the variance.

- Store summary in revenue_variance_checks.

## Step 4: Route by severity

- WATCH: logged only, visible on BU dashboard.

- ALERT: HRMS-0113 notification to BU Head, next business day if detected after hours.

- CRITICAL: immediate HRMS-0113 notification to BU Head AND Director, any time of day.

## Business Rules

## BR: BR-1106-01 — Breach detection is deterministic threshold arithmetic, not LLM judgment

- WATCH/ALERT/CRITICAL classification is computed from fixed numeric thresholds against HRMS-0313 data — the LLM is only used post-detection for summary text.

- Field: revenue_variance_checks.severity computed in application code, not from LLM response

## BR: BR-1106-02 — CRITICAL always pages immediately regardless of hour

- Unlike ALERT, a CRITICAL variance or margin drop notifies the Director immediately, 24/7, matching the pattern used for CRITICAL demand gaps in HRMS-1102.

- Field: severity=CRITICAL bypasses next-business-day batching

## Acceptance Criteria

- AC-1: A BU with variance_pct exceeding 10% is classified ALERT the same day the threshold is crossed.

- AC-2: A CRITICAL classification notifies the Director within the same check cycle, regardless of time of day.

- AC-3: Severity classification matches a fixed lookup table for a given variance_pct — no severity ever varies for identical numeric input.

- AC-4: An HRMS-0313 fetch failure retries once at 07:00 and alerts Integration Health if it still fails.

## Not In Scope

- No LLM-based breach detection — thresholds are fixed, numeric, and auditable without inspecting model output.

- No automatic corrective action (e.g., auto-adjusting billing rates) — this agent only observes and alerts.

- No forecasting or prediction of future variance — that is EPIC-03/EPIC-02 territory, this is a current-state monitor.

## 2. WHY THIS EXISTS

Recruiters, HR, and RMs receive important alerts in different contexts — SLA breaches, offer decisions, joining readiness drops, L1/L2 outcomes. Currently these go via WhatsApp and email. The in-app Notification Center creates a persistent, searchable log of all notifications so nothing is missed even if the WhatsApp message was buried under other chats.

## 3. WHAT YOU ARE BUILDING

Build the in-app Notification Center accessible from any portal page. Bell icon in header showing unread count. Click opens slide-out panel with all notifications, filterable by type, with read/unread state and direct action links.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Create portal_notifications table

- CREATE TABLE portal_notifications: id UUID PK, tenant_id UUID, user_id UUID, notification_type VARCHAR(100), title VARCHAR(200), body TEXT, action_url TEXT nullable (deep link to relevant page), priority ENUM('CRITICAL','HIGH','MEDIUM','LOW') default 'MEDIUM', is_read BOOLEAN default false, created_at TIMESTAMP, read_at TIMESTAMP nullable

- Index on (user_id, tenant_id, is_read, created_at DESC)

## Step 2: Build NotificationDelivery service

- On every notification from HRMS-0113: INSERT into portal_notifications AND send WhatsApp/email (existing behavior unchanged).

- Types to create portal notifications for: SLA_BREACH, ESCALATION, HIGH_DROP_RISK, CRITICAL_DROP_RISK, OFFER_COUNTER, OFFER_ACCEPTED, OFFER_DECLINED, INTERVIEW_NO_SHOW, DOCUMENT_OVERDUE, L1_FAIL, L2_FAIL, HIRING_DECISION_APPROVED, JOINING_READINESS_ALERT, COMPETING_OFFER_DETECTED.

- Title and body generated from notification type + candidate name.

- action_url points to the most relevant page (candidate MESSAGES tab, hr dashboard, etc.).

## Step 3: Build Notification Center UI

- Bell icon (🔔) in header of all portal pages. Unread count badge. Updates via 30-second poll or WebSocket push.

- Click opens slide-out panel from right edge (300px wide on desktop, full-screen on mobile).

- Panel header: 'Notifications (12 unread)'. Filter tabs: All / Unread / CRITICAL.

- Each notification: priority color strip (red=CRITICAL, amber=HIGH, blue=MEDIUM), title bold, body text (truncated 80 chars), relative timestamp, read/unread indicator.

- Click notification: marks as read + navigates to action_url.

- 'Mark all as read' button at top. 'Clear all' (removes read notifications from panel, not from DB).

## Step 4: Build GET /api/notifications endpoint

- GET /api/notifications?is_read={bool}&priority={X}&page=1&per_page=20

- Auth: current user session (shows only their notifications).

- Response: { notifications: [...], unread_count, total }

- PATCH /api/notifications/{id}/read — marks single as read.

- PATCH /api/notifications/read-all — marks all for this user as read.

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: CRITICAL Notifications Never Auto-Clear

Notifications with priority=CRITICAL remain in the panel until explicitly marked read by the user. They cannot be cleared by 'Clear all'. The user must consciously dismiss CRITICAL notifications.

↳ Triggered by field: CRITICAL = never auto-cleared

## BR-02: Notifications Retained 30 Days

portal_notifications older than 30 days are archived (moved to archive table, not deleted). Panel shows last 30 days by default.

↳ Triggered by field: 30-day retention in panel

## Why — Business Rationale

- Today's org structure is 9 levels; tomorrow's might be different, and a check-in system hardcoded to 'BU Head talks to direct reports quarterly, Principal Architect monthly' breaks the moment a title changes or a new level is inserted. What actually needs to be built is a system that reads the reporting chain itself — who reports to whom — and derives each employee's level from their position in that chain, so a structural reorganization is a configuration change, not a code change.

## What — Scope

- An engine that walks the employee reporting chain (via reporting_manager_user_id, already on the employee entity per S-363) and computes each employee's hierarchy depth and resolved level name from a configurable level-title list — not the current 9 titles hardcoded, but whatever list is currently configured, recalculated whenever the org structure changes.

## Before — Prerequisites

- S-363 HRMS-0101-REV must be live — reporting_manager_user_id must exist on the employee entity for this engine to have a chain to walk.

## Implementation Steps

## Step 1: Build the configurable level list

- Stored in HRMS-0115 system config, not hardcoded: an ordered list of level names from lowest to highest — e.g., Senior Consultant, Lead Consultant, Technical Manager, Senior Technical Manager, Associate Director, Principal Architect, BU Head, Partner, CEO — but stored as data, so adding, removing, or reordering a level is an Admin config change, not a deploy.

- Each employee's job_title maps to one entry in this ordered list.

## Step 2: Build the hierarchy chain walker

- For any employee, walk reporting_manager_user_id upward until reaching an employee with no manager (the CEO, or whoever sits at the top of the configured list).

- Compute hierarchy_depth (how many steps from the top) for every employee in the tenant.

## Step 3: Build the level resolution

- Cross-reference each employee's job_title against the configured level list to resolve their level — this is title-driven, not depth-count-driven, since two people at the same depth could legitimately hold different levels (e.g., a flat reporting line doesn't always mean identical seniority).

- Flag any employee whose job_title doesn't match any entry in the configured level list, for Admin resolution rather than silently defaulting to an incorrect level.

## Step 4: Build the recalculation trigger

- Any change to reporting_manager_user_id or job_title, or any change to the configured level list itself, triggers recalculation for the affected employee(s) — not a nightly batch alone, since a same-day promotion or reorg should be reflected immediately for S-384's scheduling to act on correctly.

## Business Rules

BR: BR-1404-01 — The level list is configuration data, never hardcoded in application code

- This is the entire point of the story — if today's 9 levels change to a different structure tomorrow, that's an Admin editing a config list, not a code change and redeploy.

- Field: Level list lives in system_config (HRMS-0115), read at resolution time, never a hardcoded enum in application logic

BR: BR-1404-02 — An employee whose title doesn't map to a configured level is flagged, never silently defaulted

- Guessing a level for an unmapped title risks assigning the wrong check-in cadence to the wrong person — an explicit Admin resolution step is safer than a silent best-guess.

- Field: unmapped_title_flag=true blocks level resolution for that employee until Admin maps the title or corrects it

BR: BR-1404-03 — Hierarchy recalculation is triggered by the specific change, not only a nightly batch

- A same-day reporting-line change or promotion must be reflected immediately, since S-384's scheduler acts on the resolved level and a stale level could schedule the wrong cadence.

- Field: Recalculation fires synchronously on write to reporting_manager_user_id, job_title, or the level list config

## Acceptance Criteria

- AC-1: Adding a new level to the configured list (e.g., inserting a level between two existing ones) correctly re-resolves affected employees without any code change.

- AC-2: An employee whose title has no matching level list entry is flagged for Admin resolution, never silently assigned a guessed level.

- AC-3: A same-day change to an employee's reporting manager triggers immediate recalculation, verified by checking resolved_level updates within the same request cycle.

## Not In Scope

- No org-chart visualization UI in this story — that would be a separate future story if needed; this is the resolution engine only.

## Why — Business Rationale

- BlitzenX likely has historical candidate data trapped in whatever ATS it used before WROS — Greenhouse or Lever. That history has real value (prior interview outcomes, past interest) that shouldn't be abandoned just because the platform changed. A one-time (or periodic) migration path preserves it, but only if it respects the exact same dedup and creation discipline as any other candidate entry.

## What — Scope

- A data import pipeline pulling candidate records from Greenhouse or Lever, deduplicating against the existing WROS candidate pool, mapping external fields to WROS's schema, and preserving the original source as a tag.

## Before — Prerequisites

- HRMS-0705 Candidate Profile base must be live — this is an import path into the existing schema, not a new one.

## Implementation Steps

## Step 1: Build the Greenhouse/Lever API connection

- Read-only pull of candidate records via each platform's export/API access.

## Step 2: Build the field mapping layer

- Map each external platform's candidate fields (name, contact, resume, stage history) to WROS's candidate schema — field names and structures differ between Greenhouse, Lever, and WROS.

## Step 3: Run every imported record through createCandidateSafe()

- Same R-07 dedup discipline as any other entry point — a historical record matching an existing WROS candidate is deduplicated, not duplicated.

## Step 4: Preserve source tagging

- source_channel=GREENHOUSE_IMPORT or LEVER_IMPORT, similar pattern to S-152's sub-vendor source tagging, so historical origin remains visible to internal analytics without being client or candidate visible.

## Business Rules

## BR: BR-1307-01 — Imported records go through createCandidateSafe(), no bulk direct insert

- A historical data migration is still a candidate creation event and must respect R-07's single creation path and dedup discipline — bulk import doesn't earn an exception.

- Field: Import pipeline calls createCandidateSafe() once per record, not a batch INSERT statement

## Acceptance Criteria

- AC-1: An imported record matching an existing WROS candidate is deduplicated, not created as a second record.

- AC-2: Every imported record's creation goes through createCandidateSafe(), verified by audit trail.

- AC-3: A failure importing one record doesn't halt the rest of the migration batch.

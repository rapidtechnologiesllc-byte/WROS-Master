## Why — Business Rationale

- AI confidence thresholds, SLA timings, and channel preferences currently live as hardcoded constants scattered across the codebase — meaning a BU Head who wants to tighten the Curtis Rule's 95% confidence threshold, or change the P1 emergency SLA from hours to minutes, needs a code deploy to do it. This story moves those knobs into a config table an Admin can actually turn, with an audited history of every change.

## What — Scope

- A tenant-and-BU-scoped configuration table plus an Admin Settings screen covering AI thresholds, SLA timings, channel preferences, and continent/currency defaults — one place to tune platform behavior without a deploy.

## Before — Prerequisites

- HRMS-0107 BU Context Switching must be live — config is BU-scoped, not just tenant-scoped, since different BUs may run different SLA targets.

- HRMS-0103 RBAC — only Admin role can write config.

## Implementation Steps

## Step 1: Create system_config table

- Run CREATE TABLE per Data Mapping — key/value pairs scoped by tenant_id + business_unit_id (nullable BU = tenant-wide default).

## Step 2: Seed default config values

- AI thresholds (e.g., Curtis Rule confidence floor), SLA timings (P1 emergency response window), channel preferences, continent/timezone/currency defaults.

## Step 3: Build the Admin Settings UI

- Grouped by category (AI Thresholds / SLA / Channels / Locale).

- Every change requires confirmation and writes to audit_log per HRMS-0110.

## Step 4: Build the config read API for agentic stories

- Cached read with short TTL (60s) so agent stories don't hit the config table on every single evaluation cycle, but changes propagate within a minute.

## Business Rules

## BR: BR-0115-01 — Only Admin role can write configuration

- Read access may be broader for relevant roles, but write access is Admin-only, matching Section 12's access model.

- Field: Permission middleware (HRMS-0114) requires Admin permission on config write endpoints

## BR: BR-0115-02 — Every config change is audit logged with before/after value

- Config changes directly affect hard-rule-adjacent behavior (AI thresholds feed Curtis Rule, SLA timings feed P1 emergency handling) so they get the same audit rigor as any other critical change.

- Field: Config write endpoint calls writeAuditLog() per HRMS-0110 on every change

## BR: BR-0115-03 — BU-specific config overrides tenant default, never the reverse

- Config resolution checks BU-scoped value first, falls back to tenant-wide default only if no BU-specific override exists.

- Field: Config read function: COALESCE(bu_specific_value, tenant_default_value)

## Integrations

## Acceptance Criteria

- AC-1: A non-Admin role attempting to write config is rejected by the permission middleware.

- AC-2: Every config change produces exactly one audit_log entry with old and new values.

- AC-3: A BU-specific config override is used in preference to the tenant default when both exist for the same key.

- AC-4: An agentic story reading config sees a change reflected within 60 seconds of it being saved.

## Not In Scope

- No per-user configuration in this story — config is tenant/BU scoped only, not personal preferences (those live in user profile settings).

- No config versioning/rollback UI — audit log provides history, but restoring a prior value is a manual re-entry, not a one-click revert.

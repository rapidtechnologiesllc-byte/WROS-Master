## Why — Business Rationale

- BlitzenX operates multiple Business Units, and a Director or cross-BU RM needs to move between them without logging out and back in. Today that means either a second browser tab with a second login, or a support ticket asking someone to widen access. Neither scales past a handful of people, and neither gives a clean audit trail of which BU a given action actually happened under. This story is the single foundation every other BU-scoped screen in the platform depends on — if BU context isn't right here, every downstream revenue number, resource count, and dashboard filter built on top of it is wrong too.

## What — Scope

- A Business Unit entity (multiple BUs live under one tenant) plus a context switcher in the nav bar that lets a user with multi-BU access change which BU's data they're viewing. Once switched, every subsequent screen, query, and action is scoped to the selected BU until they switch again or log out.

## Before — Prerequisites

- HRMS-0109 Multi-Tenant Data Isolation must be live — BU scoping is a layer inside tenant scoping, not a replacement for it.

- HRMS-0103 Role Based Access Control must define which roles are allowed cross-BU access at all (default: single-BU scoped, per Section 12 Role & Access Model).

## Implementation Steps

## Step 1: Create business_units table

- Run CREATE TABLE per Data Mapping — includes tenant_id, bu_name, continent, region, is_active.

- Seed existing BUs from current operational structure.

## Step 2: Add bu_access mapping

- Junction table: user_id, business_unit_id, is_default.

- Default: one row per user matching their home BU. Cross-BU users get multiple rows.

## Step 3: Build the BU context switcher UI

- Dropdown in the top nav bar, visible only to users with more than one bu_access row.

- Single-BU users see their BU name as a static label, not a dropdown — no false affordance.

## Step 4: Wire session-level BU context

- Selected business_unit_id stored in session, not just client-side state.

- Every API request after switch includes active business_unit_id; backend validates it against the user's bu_access rows on every request, not just at switch time.

## Step 5: Scope all BU-aware queries

- Any table with a business_unit_id column filters on the active session BU by default.

- Director role is the one exception: can view an unscoped 'All BUs' aggregate — explicitly logged when active, per Section 12 access model.

## Business Rules

BR: BR-0107-01 — BU context is validated server-side on every request, not trusted from client state

- The active business_unit_id is re-checked against the user's bu_access rows on every API call, not just cached from the switch action — prevents a stale or tampered client session from leaking cross-BU data.

- Field: Every BU-scoped API endpoint re-validates business_unit_id against bu_access before querying

## BR: BR-0107-02 — Director unscoped view is explicitly logged

- When a Director activates the 'All BUs' aggregate view, that action is written to the audit trail per Section 7.1 — cross-BU visibility is a privileged, tracked action, not a silent default.

- Field: audit_log entry created on every 'All BUs' view activation, actor + timestamp recorded

## BR: BR-0107-03 — Single-BU users never see a switcher

- Rendering a dropdown with one option is a false affordance that implies choice where none exists — single-BU users see a static label instead.

- Field: UI conditionally renders dropdown vs label based on COUNT(bu_access) for the user

| Source Field | Source Table | Target Field | Target Table | Notes |

| business_unit_id | business_units | business_unit_id | bu_access, all BU-scoped tables | UUID PK, FK everywhere |
| tenant_id | business_units | tenant_id | business_units | Every BU belongs to exactly one tenant |
| active_bu_session | session store | business_unit_id | N/A — session only, not persisted to DB | Cleared on logout |

## Acceptance Criteria

- AC-1: A user with access to 2+ BUs sees a functioning dropdown; a single-BU user sees a static label, never a dropdown.

- AC-2: Switching BU context immediately re-scopes all visible data on the current screen without requiring logout.

- AC-3: An API request with a tampered business_unit_id not in the user's bu_access rows is rejected, verified by a direct API test bypassing the UI.

- AC-4: Director 'All BUs' view activation creates exactly one audit_log entry per activation.

- AC-5: Deactivating a BU preserves all historical records tied to it — verified by querying old allocations after deactivation.

## Why — Business Rationale

- Nine agents now run unattended, several of them overnight. If two agents act on the same entity in the same window — for example the Outreach Agent starts a sequence with a candidate at the exact moment the Resource Management Agent flags that same person for a Core-pull — nobody notices until the morning, and by then the wrong message has already been sent. BlitzenX evaluated giving one agent full authority to arbitrate every cross-agent conflict using LLM judgment at 2am with no human to check its reasoning. That was rejected: an unsupervised judgment-making layer sitting above every other agent is the single biggest point of overnight failure in the whole system, and its decisions would be the hardest to audit after the fact. Instead this story builds a much narrower, deterministic router: it watches for a known list of conflict patterns and either blocks the lower-priority action or pages a human — it does not reason its way to a resolution.

## What — Scope

- A rule-table-driven router that subscribes to the action-intent event stream published by every other agent in EPIC-11 before that action executes. It checks the intended action against a static conflict table (entity + action-type pairs known to conflict), blocks or delays the lower-priority action when a match is found, and routes every HIGH-severity match to the on-call Director via the escalation channel defined in HRMS-0113. It maintains no independent judgment about what SHOULD happen — only whether two known actions collide.

## How is Agentic AI Used in This

- This is intentionally NOT an LLM-based agent. It is a deterministic rules engine — every conflict pattern it recognizes is enumerated in the conflict_rules table below, not inferred at runtime.

- The only AI-adjacent behavior is severity classification of NEW, previously-unseen conflict patterns: when two agents act on the same entity_id within the same 5-minute window and no existing rule matches, a single classification call (claude-sonnet-4-6, max_tokens=300) labels the pattern LOW/MEDIUM/HIGH severity for human triage — it never decides the resolution, only the urgency of the page.

- Every LLM-classified novel conflict is queued for the on-call Director to review and, if it's a recurring pattern, converted into a permanent deterministic rule — the rule table is meant to grow and the LLM's role shrinks over time.

## Before — Prerequisites

- HRMS-1102 through HRMS-1108 must publish action-intent events (not just action-completed events) before this story can intercept anything — verify each agent story's event contract includes a pre-execution intent publish step.

- HRMS-0113 Notification Engine must support a P0 paging channel (SMS + WhatsApp) distinct from the standard in-app notification queue.

## Implementation Steps

## Step 1: Create the conflict_rules and orchestration_events tables

- Run the CREATE TABLE statements in the Data Mapping section below.

- Seed conflict_rules with the six known patterns listed in Business Rules (BR-1101-01 through BR-1101-06).

## Step 2: Build the action-intent event listener

- Subscribe to the internal event bus topic `agent.action.intent` published by HRMS-1102-1108.

- Each event carries: agent_id, entity_type, entity_id, action_type, proposed_at, risk_tier.

- On receipt, query conflict_rules for any active rule matching (entity_type, action_type) pairs within the configured collision_window_minutes for that rule.

## Step 3: Implement block/delay/escalate resolution

- If a rule match is found: apply the rule's resolution_action (BLOCK, DELAY, or ESCALATE_ONLY).

- BLOCK: publish `agent.action.blocked` back to the originating agent; agent must not proceed.

- DELAY: hold the action for delay_minutes, re-check, then release or re-block.

- ESCALATE_ONLY: allow the action to proceed AND page the Director simultaneously.

## Step 4: Implement novel-pattern classification fallback

- If no rule matches but two events share entity_id within 5 minutes from different agent_id values, call the LLM classifier with both event payloads.

- Store the classification result in orchestration_events with llm_classified=true.

- Route MEDIUM/HIGH classifications to the Director's daily conflict review queue (does not block the action — novel patterns are never auto-blocked, only flagged for rule-table growth).

## Step 5: Wire escalation delivery

- HIGH severity → HRMS-0113 P0 channel (SMS + WhatsApp), immediate.

- MEDIUM severity → next-morning digest, included in HRMS-1110 Daily System Activity Report.

- LOW severity → logged only, visible in orchestration_events audit view.

## Business Rules

## BR: BR-1101-01 — Outreach vs. Core-Pull collision blocks outreach

- If HRMS-1105 flags an employee/candidate for Core-pull within 60 minutes of HRMS-1104 initiating outreach to that same entity_id, the outreach action is BLOCKED.

- Field: Resolution Action = BLOCK, triggered by entity_id match across agent_id 1104 and 1105

## BR: BR-1101-02 — Thunder conversation ownership overrides all agents

- Per R-08, if a recruiter has sent the most recent message in a candidate conversation, no agent (1103, 1104) may initiate any send action to that candidate — this is enforced independently by sendThunderMessage() but is also checked here as a second gate.

- Field: conflict_rules row: action_type=any_send, resolution=BLOCK, triggered_by=conversation_ownership_lock

## BR: BR-1101-03 — Novel conflicts are never auto-blocked

- Only enumerated rules in conflict_rules can trigger BLOCK or DELAY. LLM-classified novel patterns can only ESCALATE_ONLY — the router has no authority to invent a new block.

- Field: llm_classified=true rows are hard-coded to resolution_action=ESCALATE_ONLY

## BR: BR-1101-04 — HIGH severity pages within 5 minutes

- Any HIGH severity classification or rule match must reach the Director's P0 channel within 5 minutes of detection — measured and alerted on if breached.

- Field: orchestration_events.escalated_at - orchestration_events.detected_at <= 300 seconds

## BR: BR-1101-05 — Rule changes require Admin role and are logged

- Only Admin role can create/edit/deactivate conflict_rules rows; every change is written to the standard audit trail per Section 7.1.

- Field: conflict_rules table — write access gated by role=Admin

## BR: BR-1101-06 — Router failure fails open with alert, never fails closed silently

- If the router process itself is down, agents must NOT be blocked from acting (fail open) but a CRITICAL alert fires immediately — silent blocking of all agent activity is worse than an occasional missed collision check.

- Field: Integration Health Agent (HRMS-1108) monitors router liveness specifically

## Acceptance Criteria

- AC-1: A BLOCK-resolution conflict rule prevents the lower-priority agent action from executing, verified by absence of the corresponding action-completed event.

- AC-2: A DELAY-resolution rule holds the action for exactly delay_minutes and re-evaluates before release.

- AC-3: An ESCALATE_ONLY match allows the action to proceed AND generates exactly one HRMS-0113 escalation.

- AC-4: A HIGH severity page reaches the Director's P0 channel within 5 minutes of detection, measured end-to-end.

- AC-5: A novel (unruled) conflict pattern never blocks an action — only enumerated rules can BLOCK or DELAY.

- AC-6: Router process downtime does not halt any other agent's actions (fail-open verified) and fires a CRITICAL alert within 60 seconds.

- AC-7: Only Admin role can create, edit, or deactivate a conflict_rules row; attempted access by any other role is rejected and logged.

## Not In Scope

- No LLM-based resolution or arbitration logic — the router only classifies severity for novel patterns, it never decides what should happen.

- No general-purpose workflow engine — this is a narrow collision-detection service, not a BPM platform.

- No UI for agents to negotiate with each other — conflicts are resolved by static rule, not by inter-agent messaging.

- No automatic rule-table self-editing — rule changes always require an Admin action, even after repeated novel-pattern escalations.

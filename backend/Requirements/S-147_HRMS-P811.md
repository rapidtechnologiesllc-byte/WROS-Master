## Why — Business Rationale

- Deadline enforcement, compliance-violation escalation, and vendor notifications were originally three separate stories — but they're the same underlying pattern EPIC-11 already proved out: a monitor-and-flag agent watching deterministic thresholds and routing alerts by severity. Building three near-identical threshold watchers instead of one agent with three rule sets adds maintenance surface with no corresponding benefit, exactly the lesson from HRMS-1106/1107.

## What — Scope

- One agent covering three related governance functions: (1) tracks request deadlines and auto-closes late requests, (2) tracks FT-only and dedup violations per vendor and escalates at 3 and 5 strikes, (3) dispatches all vendor-facing notifications — new request, submission outcome, deadline reminder, compliance warning, account status change.

## Before — Prerequisites

- S-139 HRMS-P803 must produce requests with a deadline field this agent can monitor.

- S-142 HRMS-P806 must be writing to sub_vendor_violations for this agent's compliance tracking to have data to watch.

## Implementation Steps

## Step 1: Build the deadline monitor (runs hourly)

- For each open request, check days_remaining.

- 1 day before deadline: auto-reminder notification to vendor.

- At deadline: request status auto-transitions to CLOSED; any submission after this point is auto-rejected as late.

- Recruiter notified of the vendor's response rate for that request (submissions received / max candidates requested) as part of the close event.

## Step 2: Build the compliance violation tracker

- Aggregates sub_vendor_violations (from S-142) per vendor over a rolling 90-day window.

- 3 violations: auto-flag for compliance review, notify Admin — matches S-142's BR-0806-02.

- 5 violations: auto-suspend the vendor account PENDING Admin confirmation — this is the one action in this story that is not fully auto-executed; suspension requires an Admin to confirm before the account actually goes inactive, since account suspension affects an active business relationship and warrants a human check.

## Step 3: Build the unified notification dispatcher

- Single dispatch point for all vendor-facing events: new request, submission accepted/rejected, deadline reminder, compliance warning, account status change.

- Email always sent; portal notification always created; WhatsApp sent if the vendor has opted in.

## Business Rules

## BR: BR-0811-01 — Deadline closure and late-submission rejection are fully automatic

- No human approval needed to close an already-expired request — this is a LOW-risk, easily reversible administrative action (a request can be manually reopened by a recruiter if needed).

- Field: Request status auto-transitions to CLOSED at deadline with no approval gate

BR: BR-0811-02 — Account suspension at 5 violations requires Admin confirmation before taking effect

- Unlike deadline closure, suspending a vendor account affects an active business relationship — this is deliberately the one action in this agent that is not auto-executed.

- Field: 5th violation sets status=SUSPENSION_PENDING, not SUSPENDED — Admin confirmation transitions to actual SUSPENDED

## BR: BR-0811-03 — This agent is the single dispatch point for all vendor notifications

- Consolidating three originally-separate stories' notification logic into one place prevents drift between deadline reminders, compliance warnings, and status-change messages using inconsistent formats or channels.

- Field: All vendor-facing HRMS-0113 calls for Sub-Vendor Portal route through this agent's dispatcher

## Acceptance Criteria

- AC-1: A request one day from deadline triggers exactly one reminder notification to the vendor.

- AC-2: A request past deadline auto-closes and any subsequent submission is auto-rejected as late.

- AC-3: A vendor's 5th violation within 90 days sets status to SUSPENSION_PENDING, not SUSPENDED, until an Admin confirms.

- AC-4: Every vendor-facing notification type (new request, outcome, reminder, warning, status change) routes through this agent's single dispatcher.

## Not In Scope

- No LLM-generated messaging — all vendor communications are templated, since these are structured status events, not open-ended narrative summaries.

- No automatic account suspension without Admin confirmation — this is the one deliberate exception to full automation in this agent.

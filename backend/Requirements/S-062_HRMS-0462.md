## 2. WHY THIS EXISTS

Thunder is autonomous but not infallible. There will always be candidates who need a human touch — escalations, high drop risk, complex objections, SLA breaches. The Recruiter Intervention Queue is the prioritized list of 'candidates that need you right now'. It replaces manual scanning of all candidate profiles with a ranked, actionable list.

This queue is Thunder's handoff mechanism to the human recruiter. When Thunder determines a human should take over, this is where the handoff appears.

## Step 1: Create recruiter_intervention_queue table

- CREATE TABLE recruiter_intervention_queue: id UUID PK, tenant_id UUID, candidate_id UUID FK→candidates.id, candidate_name VARCHAR(200), queue_reason ENUM('ESCALATION','HIGH_DROP_RISK','CRITICAL_DROP_RISK','SLA_BREACH','HIGH_ABANDONMENT','NO_SHOW','OFFER_COUNTER','DOCUMENT_OVERDUE') NOT NULL, reason_detail TEXT, priority INTEGER (1=CRITICAL, 2=HIGH, 3=MEDIUM), status ENUM('OPEN','IN_PROGRESS','RESOLVED') DEFAULT 'OPEN', assigned_to_user_id UUID nullable, added_at TIMESTAMP, resolved_at TIMESTAMP nullable, resolved_by UUID nullable, resolution_note TEXT nullable

- Index on (tenant_id, status, priority, added_at)

## Step 2: Build addToQueue() function

- addToQueue(candidate_id, tenant_id, queue_reason, reason_detail, priority) → queue item

- Check dedup: if OPEN item already exists for same candidate_id + queue_reason: UPDATE reason_detail (refresh) but do NOT create duplicate

- INSERT if no existing OPEN item for this combination

- Publish event: intervention_queue.item_added { candidate_id, queue_reason, priority }

- Called by: HRMS-0435 (escalation), HRMS-0460 (drop risk >= 70), HRMS-0420 (SLA breach), HRMS-0446 (abandonment >= 70), HRMS-0452 (no-show), HRMS-0456 (offer counter), HRMS-0457 (doc overdue)

## Step 3: Build the Intervention Queue UI

- Route: /recruiter/intervention-queue (standalone page, also accessible from dashboard)

- Dashboard widget: shows count of OPEN items by priority. 'Needs Attention: 3 Critical | 5 High | 2 Medium'. Click opens full queue page.

- Queue table: columns = Priority badge, Candidate Name, Reason, Added, Time Since Added, Actions

- Sorted: CRITICAL first, then HIGH, then MEDIUM. Within same priority: oldest first (longest waiting).

- Priority badges: CRITICAL=red pulsing, HIGH=red solid, MEDIUM=amber

- Actions column: 'Take Over' button (one-click triggers HRMS-0410 takeover), 'Mark Resolved' button, 'View Messages' link

- 'Take Over' button: immediately transfers ownership to clicking recruiter AND marks queue item as IN_PROGRESS

## Step 4: Build queue resolution flow

- 'Mark Resolved' button: opens small modal asking for resolution note (optional). On confirm: UPDATE status=RESOLVED, resolved_at=NOW(), resolved_by=recruiter_id, resolution_note=text.

- If the underlying issue is resolved (candidate responds, risk drops): auto-resolve the queue item. Logic: when drop_risk_score drops below 50 → resolve any HIGH_DROP_RISK items. When escalation is de-escalated → resolve ESCALATION items.

- Resolved items stay in queue for 7 days (historical reference) then auto-archive

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: CRITICAL Items Must Show Immediately Regardless of Queue Length

CRITICAL priority items (drop risk >= 80, escalations with legal keywords) always appear at the top of the queue. They do not wait behind a long list of HIGH items. The recruiter must see CRITICAL items the moment they open the queue.

↳ Triggered by field: priority=1 (CRITICAL) sorts first always

## BR-02: Deduplication — One Open Item Per Candidate Per Reason

If a candidate already has an OPEN item with reason=HIGH_DROP_RISK and their risk increases further: UPDATE the existing item's reason_detail. Do NOT create a second item. The queue must not become cluttered with duplicates for the same candidate.

↳ Triggered by field: UNIQUE OPEN item per (candidate_id, queue_reason)

## BR-03: Auto-Resolve When Underlying Issue Resolves

When the system detects the root cause is resolved (drop risk drops, escalation de-escalated, candidate responds): automatically set queue item status=RESOLVED. Recruiters should not manually close items that have self-resolved.

↳ Triggered by field: auto-resolve trigger

## 2. WHY THIS EXISTS

Thunder is designed to handle 60+ simultaneous candidate conversations. Before going live, we must verify the system can handle this load without degrading performance or failing. A WhatsApp API call that takes 200ms in isolation might take 3 seconds under concurrent load — causing SLA breaches. Load testing identifies these bottlenecks before real candidates experience them.

## 3. WHAT YOU ARE BUILDING

Design and execute load tests for: (1) 100+ simultaneous conversation initializations. (2) WhatsApp API throughput under concurrent load. (3) LLM API concurrent call performance. (4) DB query performance under load. (5) Supervisor Agent under full candidate load. All must pass defined thresholds.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Define performance thresholds (BA and tech lead must agree before testing)

- First contact SLA: 95% of new candidates must receive first WhatsApp within 60 seconds under load of 100 simultaneous creations

- API response time: POST /api/candidates, POST /api/webhooks/whatsapp must return < 500ms at P95 under 50 concurrent requests

- LLM call latency: callLLM() must complete < 5 seconds at P95 under 30 concurrent calls (Anthropic rate limit dependent)

- DB query performance: buildCandidateContext() must complete < 500ms at P95 under 100 concurrent calls

- Supervisor cycle: SUPERVISOR_AGENT_JOB must complete full cycle for 100 candidates within 15 minutes (its own run interval)

- Error rate: < 1% error rate on all API endpoints under sustained load

## Step 2: Write load test scripts

- Use k6 or locust for API load testing

- Test scenarios:

- Scenario 1 — Burst creation: create 100 candidates in 60 seconds. Measure: first contact SLA compliance, error rate, DB response time.

- Scenario 2 — Concurrent WhatsApp: 50 simultaneous inbound WhatsApp webhooks. Measure: response time (<3s required), processing accuracy.

- Scenario 3 — LLM concurrent load: 30 simultaneous generateThunderResponse() calls. Measure: latency, error rate, fallback activation rate.

- Scenario 4 — Supervisor cycle: 100 active candidates, run supervisor cycle. Measure: total cycle time, agent dispatch accuracy.

- Scenario 5 — Sustained load: 10 candidates per minute for 30 minutes. Measure: SLA compliance over time, memory leaks, connection pool exhaustion.

## Step 3: Execute tests and document results

- Run each scenario 3 times. Record P50, P95, P99 latencies, error rates, and SLA compliance percentage.

- Document: PASS if all thresholds met. FAIL with specific bottleneck identified if any threshold missed.

- For each FAIL: identify root cause. Fix. Re-test.

- Load test report must be signed off by lead BA and tech lead before go-live checklist begins.

## Step 4: Performance optimizations (if needed)

- Common bottlenecks to check: database connection pool size (increase if needed), Redis cache hit rates (ensure context caching is working), LLM call parallelization (ensure batch calls don't queue), WhatsApp webhook queue depth (ensure async processing is not backing up)

- Do NOT optimize prematurely — run tests first, optimize based on actual bottlenecks found

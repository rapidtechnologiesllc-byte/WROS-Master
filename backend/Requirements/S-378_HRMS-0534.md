## Why — Business Rationale

- When a Core-Certified employee in Specialty is selected for a Core or direct client engagement, the current Specialty client (PwC, EY, etc.) must be informed and must agree to the release — or at least be given a professional handover timeline. Notifying PwC abruptly that their resource is leaving tomorrow is damaging to a relationship that generates Specialty revenue. This workflow ensures: the Specialty client is notified professionally, with a handover timeline, at the right moment (after SOW confirmed and both parties agree), and their release response is documented.

## What — Scope

- Build Specialty client release workflow: triggered after SOW confirmed and both employee+BU Head fit confirmed. RM notifies Specialty client via structured communication. Client acknowledges and provides release date or negotiates notice period. Release approval logged. Allocation created only after release confirmed.

## Before — Prerequisites

- HRMS-0528 confirmation_status=CONFIRMED and both fit confirmations logged. HRMS-0529 pool guard check passed. HRMS-0102 Specialty client contact details.

## Implementation Steps

## Step 1: Create specialty_client_releases table

- CREATE TABLE specialty_client_releases: id UUID PK, tenant_id UUID, employee_id UUID FK, current_project_id UUID FK, current_si_partner ENUM, new_demand_id UUID FK, notified_at TIMESTAMP nullable, notified_by UUID nullable, client_response ENUM('APPROVED','NEGOTIATING','DECLINED') nullable, agreed_release_date DATE nullable, negotiation_notes TEXT nullable, status ENUM('PENDING_NOTIFICATION','NOTIFIED','APPROVED','NEGOTIATING','BLOCKED'), created_at TIMESTAMP.

## Step 2: Build notification flow

- On trigger (from HRMS-0528): create specialty_client_releases record with status=PENDING_NOTIFICATION.

- RM uses structured notification template: 'Hi [Client Contact], I am writing to inform you that [Employee Alias — first name only] has been selected for a new engagement starting [date]. We plan to transition them on [proposed_date]. We would like to discuss the handover plan and ensure continuity for your project. [RM Name] — BlitzenX'

- RM sends via email + logs in WROS. Status → NOTIFIED.

## Step 3: Build client response tracking and gate

- Client acknowledges via email (RM logs response manually) OR via client portal message.

- RM updates status: APPROVED (client agrees to release date), NEGOTIATING (client wants longer notice), BLOCKED (client refuses release — legal/contractual).

- APPROVED or agreed NEGOTIATING (with agreed date): creates employee_allocations record for new Core engagement with start_date=agreed_release_date.

- BLOCKED: RM and BU Head escalate. If contractually blocked: demand must source alternative candidate. Employee stays at Specialty client per contract terms.

## Business Rules

## BR: Specialty Client Is Always Notified Before New Allocation Is Created

- The employee_allocations record for the new Core or direct engagement cannot be created until specialty_client_releases.status=APPROVED or NEGOTIATING (with agreed_release_date confirmed). This is a hard sequence gate. Creating the new allocation before the Specialty client agrees is a contractual and relationship risk.

- Field: New allocation blocked until specialty_client_releases.status=APPROVED or agreed NEGOTIATING

## BR: BLOCKED Release Means Alternative Candidate — Not Forced Transfer

- If the Specialty client says no and has contractual grounds (the employee's contract with that client has not expired), BlitzenX does not force the transfer. The employee stays. A different Core-Certified candidate is sourced for the Core demand. Forcing contractual breaches damages Specialty relationships BlitzenX depends on for revenue.

- Field: BLOCKED = alternative candidate sourcing. No forced contractual breach.

## Acceptance Criteria

- AC-1: Release workflow triggered only after SOW confirmed and both parties agree

- AC-2: RM sends structured notification to Specialty client

- AC-3: Client response tracked (APPROVED/NEGOTIATING/BLOCKED)

- AC-4: New allocation created only after release APPROVED or agreed date confirmed

- AC-5: BLOCKED: alternative candidate sourcing triggered, employee stays at Specialty client

- AC-6: Release record retained permanently for contractual audit trail

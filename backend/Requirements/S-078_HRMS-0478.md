## 2. WHY THIS EXISTS

Events are currently published ad-hoc by individual services — some services emit events, others don't, event names are inconsistent, event payloads vary in structure. This story standardizes the event emission layer: every significant Thunder action emits a well-structured, versioned event. This is the foundation EPIC-11 agents and the webhook engine (HRMS-1310) will build on.

## 3. WHAT YOU ARE BUILDING

Build: (1) event_definitions catalog — all event types with their payload schemas. (2) EventEmitter service — standardized emit function with validation, versioning, and guaranteed delivery. (3) event_log table for all emitted events. (4) Retry queue for failed deliveries.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Define event catalog (all standard events)

- Document in code as constants: EVENT_DEFINITIONS = { event_type: { version, description, payload_schema } }

- Key events: candidate.created, candidate.engaged, candidate.qualified, candidate.fully_qualified, candidate.ghosted, candidate.reactivated, candidate.resume_uploaded, candidate.resume_parsed, candidate.skills_extracted, candidate.availability_provided, candidate.high_abandonment_risk, candidate.negative_sentiment_trend, conversation.state_changed, conversation.ownership_transferred, message.received, message.delivery_failed, interview.confirmed, interview.rescheduled, interview.no_show, offer.released, offer.accepted, offer.declined, onboarding.complete, sla.breach_detected, supervisor.cycle_completed

- Each event has: version (e.g. v1), created_at, tenant_id, candidate_id (when applicable), payload (event-specific data)

## Step 2: Create event_log table

- CREATE TABLE event_log: id UUID PK, tenant_id UUID, event_type VARCHAR(100), event_version VARCHAR(10), payload JSONB, emitted_at TIMESTAMP default NOW(), delivery_attempts INTEGER default 0, delivered_at TIMESTAMP nullable, delivery_failed BOOLEAN default false, subscriber_count INTEGER default 0

- Index on (tenant_id, event_type, emitted_at DESC)

- Retention: 30 days of events (archive older)

## Step 3: Build EventEmitter service

- EventEmitter.emit(event_type, payload, tenant_id, candidate_id) → event_id

- Validate: event_type exists in EVENT_DEFINITIONS. payload matches schema. tenant_id and candidate_id are valid UUIDs.

- INSERT into event_log

- Publish to internal message bus / subscribers

- If publish fails: insert into event_retry_queue. RetryJob picks up failed events every 5 minutes. Max 3 retry attempts.

- Return event_id immediately (async delivery — do not wait for subscribers)

## Step 4: Build event_retry_queue and RetryJob

- CREATE TABLE event_retry_queue: id UUID PK, event_log_id UUID FK→event_log.id, retry_count INTEGER default 0, next_retry_at TIMESTAMP, last_error TEXT nullable

- RetryJob runs every 5 minutes: SELECT events WHERE retry_count < 3 AND next_retry_at <= NOW(). Retry publish. On success: remove from queue. On 3rd failure: mark event_log.delivery_failed=true. Alert system admin.

## Step 5: Replace all ad-hoc event publishes with EventEmitter.emit()

- Go through all EPIC-04 stories that publish events and replace direct message-bus publishes with EventEmitter.emit()

- This ensures all events are logged in event_log, validated, versioned, and retry-enabled

- Any event not going through EventEmitter is a bug — enforce via code review checklist

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: All Thunder Events Must Go Through EventEmitter

No direct message bus publishes allowed in EPIC-04 code. Every event must go through EventEmitter.emit() so it is logged, versioned, and retry-enabled. Enforce via PR checklist item: 'All event publishes use EventEmitter.emit()'

↳ Triggered by field: EventEmitter.emit() for all events

## BR-02: Event Payload Must Include tenant_id and candidate_id

Every event must include tenant_id in the payload. Events that are candidate-specific must also include candidate_id. These are mandatory fields validated by EventEmitter before emit.

↳ Triggered by field: tenant_id and candidate_id mandatory

## BR-03: Event Delivery Is Async — Emitter Does Not Wait

EventEmitter.emit() returns immediately after inserting into event_log and publishing to bus. It does not wait for subscribers to process. This ensures emitting an event never blocks the action that triggered it.

↳ Triggered by field: async emit — return immediately

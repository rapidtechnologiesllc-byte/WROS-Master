## 2. WHY THIS EXISTS

Some candidates are unreachable via text. They are not on WhatsApp actively, they ignore emails, but they pick up the phone. A future version of Thunder will be able to make AI phone calls to candidates. This story builds the foundational architecture — call logging schema, transcription hooks, call state management — without actually building live calling. The framework makes AI calling an implementation detail rather than a redesign when the time comes.

## 3. WHAT YOU ARE BUILDING

Build the foundational schema and interfaces for AI voice calling: (1) call_sessions table for tracking call state. (2) call_transcriptions table for storing call content. (3) CallAgentInterface — the abstract interface that future voice implementations will implement. (4) Integration hooks for the call to become part of the conversation timeline.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Create call_sessions table

- CREATE TABLE call_sessions: id UUID PK, tenant_id UUID, candidate_id UUID FK→candidates.id, conversation_id UUID FK→candidate_conversations.id, call_direction ENUM('OUTBOUND','INBOUND'), call_status ENUM('INITIATED','RINGING','CONNECTED','COMPLETED','FAILED','NO_ANSWER','BUSY'), initiated_at TIMESTAMP, connected_at TIMESTAMP nullable, completed_at TIMESTAMP nullable, duration_seconds INTEGER nullable, call_provider VARCHAR(50) (e.g. 'twilio', 'aws_connect', 'mock'), provider_call_id VARCHAR(200) nullable, recording_url TEXT nullable (S3 URL), created_at TIMESTAMP

## Step 2: Create call_transcriptions table

- CREATE TABLE call_transcriptions: id UUID PK, call_session_id UUID FK→call_sessions.id, tenant_id UUID, candidate_id UUID, turn_index INTEGER, speaker ENUM('AI','CANDIDATE'), text TEXT, confidence DECIMAL(3,2), started_at_seconds DECIMAL(6,2), ended_at_seconds DECIMAL(6,2)

- Each row = one speaker turn in the call

## Step 3: Define CallAgentInterface (abstract)

- Define the interface/abstract class that future voice implementations must implement:

- initiateCall(candidate_id, tenant_id, script_type) → call_session_id

- hangup(call_session_id) → void

- handleTranscription(call_session_id, transcription_turn) → void

- getCallStatus(call_session_id) → call_status

- Build a MockCallAgent that implements this interface (returns mock status, logs fake transcriptions) — used for testing

## Step 4: Build call-to-conversation-timeline integration

- When a call completes: create a conversation_messages record for the call:

- direction=OUTBOUND, channel=PHONE (add to ENUM), sender_type=AI, message_body='[Phone call — [duration] seconds. Transcript available.]', sent_at=initiated_at

- This makes completed calls appear in the HRMS-0405 conversation timeline

- Link call_session_id in a new column on conversation_messages so recruiters can view call details

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: This Story Builds Framework Only — No Live Calls

This story creates schemas, interfaces, and mock implementations. No real phone calls are made. The MockCallAgent returns fake call sessions with mock transcriptions. Live provider integration (Twilio, AWS Connect) is a future story that implements CallAgentInterface.

## BR-02: Call Recordings Stored in S3 — Never in DB

call_sessions.recording_url stores an S3 URL only. Raw audio is never stored in the database. S3 recordings have a 90-day retention policy (configurable in S3 lifecycle rules).

↳ Triggered by field: recording_url = S3 URL only

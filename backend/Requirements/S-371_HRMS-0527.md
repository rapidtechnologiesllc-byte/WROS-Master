## Why — Business Rationale

- Partners like Curtis should never be asked the same question twice. If Curtis has raised 23 demands in 18 months and every single one has been a direct Core client requirement, asking him 'is this direct or subcontractor?' on demand 24 is insulting to his intelligence and wastes his time. The Partner Intent ML Engine learns from every historical demand — who raised it, what client, what type, what delivery engine — and builds a partner profile that lets Thunder ask only what it genuinely does not know.

## What — Scope

- Build the Partner Intent ML Engine: learns per-partner historical patterns (demand type, client type, delivery engine, experience level preferences, billing range). When a partner raises a new requirement, Thunder is pre-loaded with inferred intent. Questions are only asked for genuinely unknown dimensions. Engine improves with every new demand.

## Before — Prerequisites

- demands table with history. HRMS-0102 client records with engagement type. Thunder conversation logs. Minimum 3 historical demands per partner for meaningful patterns.

## Implementation Steps

## Step 1: Build partner_intent_profiles table and batch learner

- CREATE TABLE partner_intent_profiles: id UUID PK, tenant_id UUID, partner_user_id UUID UNIQUE, demand_count INTEGER, core_demand_pct DECIMAL (% of demands that were Core/direct client), specialty_demand_pct DECIMAL, avg_experience_level DECIMAL (avg min_experience_years requested), typical_billing_range_min_usd_cents BIGINT, typical_billing_range_max_usd_cents BIGINT, typical_skills JSONB (most frequently requested skills), last_updated TIMESTAMP.

- Nightly batch job: recalculates all partner_intent_profiles from full demands history.

## Step 2: Build IntentInferenceEngine

- IntentInferenceEngine.infer(partner_user_id, new_requirement_text): reads partner_intent_profile. Returns: { inferred_delivery_engine: CORE|SPECIALTY|UNKNOWN, confidence: 0-100, inferred_experience_level: N|UNKNOWN, inferred_billing_range: {min,max}|UNKNOWN, questions_to_skip: [], questions_to_ask: [] }.

- Rule: if core_demand_pct >= 95% AND demand_count >= 5: inferred_delivery_engine=CORE with confidence=97%. Skip the 'direct or subcontractor' question entirely.

- Rule: if avg_experience_level is consistent (std_dev < 1 year across last 10 demands): infer experience level. Skip experience question.

- Rule: if billing range consistently in $110-$125 range: infer billing range. Do not ask.

## Step 3: Build Thunder integration — pre-loaded intent

- On demand message received from a partner: Thunder calls IntentInferenceEngine.infer() before generating its qualification questions.

- Thunder only asks questions where confidence < 80%. High-confidence inferences are pre-populated on the demand record and confirmed in Thunder's summary to the partner: 'I'm setting this as a direct Core client requirement at senior level — let me know if that's different from what you need.'

- Partner can correct any inference. Correction feeds back into the model.

## Step 4: Build new client detection flow

- If client_name in partner message does not match any existing clients.company_name (fuzzy match): Thunder asks exactly ONE question: 'I don't have [Client Name] on file. Is this a direct BXUS partner client or going through another prime?' Creates client record with status=PENDING_VERIFICATION while sourcing proceeds in parallel — no stalling.

## Business Rules

## BR: Minimum 3 Historical Demands for Pattern Activation

- IntentInferenceEngine only makes inferences if partner_intent_profiles.demand_count >= 3. For partners with fewer than 3 demands: Thunder asks all standard qualification questions. The engine never infers from insufficient data.

- Field: demand_count >= 3 required for inference — below threshold = full qualification

## BR: Partner Can Always Correct an Inference — Correction Updates Model

- If Thunder's inferred intent is wrong (e.g. Curtis has a new subcontractor requirement for the first time): partner corrects Thunder in the conversation. Correction is logged and the nightly batch updates the partner profile. The model learns from corrections and adjusts confidence accordingly.

- Field: Corrections feed back into model nightly — adaptive learning

## BR: New Client Always Triggers One Specific Question — Never Silent Creation

- A client not in the database is never silently auto-created as Core or Specialty. Thunder always asks exactly one question to determine client type. The PENDING_VERIFICATION status allows sourcing to proceed while classification is confirmed.

- Field: New client = one question + PENDING_VERIFICATION — no silent creation

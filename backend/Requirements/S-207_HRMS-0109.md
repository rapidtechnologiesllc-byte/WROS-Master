## Why — Business Rationale

- WROS is built to eventually serve more than one staffing organization on shared infrastructure. A single missed tenant_id filter on one query is the difference between a clean multi-tenant platform and a data breach where one client sees another's candidates, revenue, or employees. This is not a feature — it is the guarantee every other feature in the platform is allowed to assume is already true.

## What — Scope

- A tenant_id column enforced on every business-entity table, validated at the API middleware layer on every single request — not left to individual endpoint authors to remember to add a WHERE clause.

## Before — Prerequisites

- None — this is the first story in the build sequence per Section 10.1 Build Order.

## Implementation Steps

## Step 1: Add tenant_id to every business-entity table

- UUID, NOT NULL, indexed, on candidates, employees, clients, demands, projects, submissions, and every table listed in Section 7.2 Key Entity Relationships.

## Step 2: Build the tenant-scoping middleware

- Every API request resolves tenant_id from the authenticated session — never from a client-supplied parameter.

- Middleware injects a mandatory tenant_id filter into every query before it reaches the handler — handler code cannot opt out.

## Step 3: Add a CI-level guard against unscoped queries

- Static analysis check that fails the build if a query against a tenant-scoped table is written without going through the middleware's scoped query builder.

## Step 4: Build the cross-tenant access test suite

- Automated test: create data under Tenant A, authenticate as a Tenant B user, attempt every read/write pattern, assert zero results and zero writes succeed.

## Business Rules

## BR: BR-0109-01 — tenant_id is never accepted from client input

- Even if a client request includes a tenant_id parameter, it is ignored — the middleware always resolves tenant_id from the server-side session, never trusting anything the caller sends.

- Field: Middleware overwrites any client-supplied tenant_id before query construction

## BR: BR-0109-02 — No raw/unscoped query path exists in the codebase

- There is no sanctioned way to query a tenant-scoped table without going through the scoped query builder — enforced by the CI static-analysis guard, not just code review discipline.

- Field: CI pipeline fails the build on any detected unscoped query against a tenant-scoped table

## BR: BR-0109-03 — Isolation failure fails closed

- If tenant resolution fails for any reason (session corruption, missing claim), the request is rejected outright rather than falling back to an unscoped or default-tenant query.

- Field: Middleware returns 401/403 on tenant resolution failure — never proceeds with a null tenant_id

## Acceptance Criteria

- AC-1: Every business-entity table listed in Section 7.2 has a NOT NULL, indexed tenant_id column.

- AC-2: A cross-tenant read attempt (Tenant B user querying Tenant A data) returns zero rows in every tested endpoint.

- AC-3: A cross-tenant write attempt is rejected outright, not silently scoped or ignored.

- AC-4: The CI static-analysis guard fails a build containing a newly-introduced unscoped query against a tenant-scoped table.

- AC-5: A client-supplied tenant_id parameter has zero effect on query results — verified by sending a forged tenant_id and confirming results still match the session's real tenant.

## Not In Scope

- No per-tenant database instances or schema separation — this is row-level isolation within shared tables, not physical database sharding.

- No tenant self-signup or tenant management UI in this story — tenant provisioning is a separate, later concern.

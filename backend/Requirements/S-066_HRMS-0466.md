## 2. WHY THIS EXISTS

Thunder is not a single AI — it is a team of specialized agents: QualificationAgent, FollowUpAgent, SchedulingAgent, OfferAgent, DocumentCollectionAgent, SentimentAgent, RiskAgent. Without a coordinator, these agents could conflict: the FollowUpAgent sends a follow-up to a candidate the QualificationAgent is already actively engaging. The Supervisor Agent orchestrates all sub-agents, maintains shared execution state, and prevents conflicts.

This is the architecture that enables the <20% human dependency target. Every agent runs, every 15 minutes, evaluating every candidate and taking the right action — without stepping on each other.

## 3. WHAT YOU ARE BUILDING

Build: (1) SupervisorAgent that runs every 15 minutes. (2) Evaluates each active candidate's current state and determines which agent(s) should act. (3) Dispatches actions with locking to prevent conflicts. (4) Maintains agent execution memory. (5) Produces system health metrics.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Create agent_execution_log table

- CREATE TABLE agent_execution_log: id UUID PK, tenant_id UUID, candidate_id UUID, agent_name VARCHAR(100), action_taken VARCHAR(200), action_data JSONB, execution_at TIMESTAMP, duration_ms INTEGER, success BOOLEAN, error_message TEXT nullable

- Index on (tenant_id, candidate_id, execution_at)

- Every agent action — whether it sends a message, updates a score, or makes a decision — is logged here

## Step 2: Build SupervisorAgent execution loop

- Runs every 15 minutes as a scheduled job: SUPERVISOR_AGENT_JOB

- For each tenant: load all active candidates (conversation.status NOT IN COMPLETED, WITHDRAWN)

- For each candidate: evaluate state and determine required agent actions (Step 3)

- Dispatch actions with distributed locking (Step 4)

- Log to agent_execution_log. Publish event: supervisor.cycle_completed { tenant_id, candidates_evaluated, actions_dispatched, cycle_duration_ms }

## Step 3: Build state evaluation matrix

- For each candidate, evaluate in priority order:

- 1. isAIOwner()=false: SKIP all agents. Recruiter owns — Thunder is silent.

- 2. state=ESCALATED: SKIP all agents. Human is handling it.

- 3. state=QUALIFYING AND completeness < 100%: RUN QualificationAgent (if no outbound in last 2h and no PENDING follow-up)

- 4. state=QUALIFYING AND completeness = 100%: RUN state transition to QUALIFIED

- 5. state=QUALIFIED AND interview not scheduled: RUN SchedulingAgent

- 6. state=INTERVIEW_SCHEDULED AND interview_date < 25h away: RUN ReminderAgent

- 7. state=OFFER_SENT AND offer not answered: RUN OfferFollowUpAgent (max 1 nudge per 48h)

- 8. state=PREBOARDING: RUN DocumentCollectionAgent (if pending docs and last reminder > 48h)

- 9. ALL states: RUN RiskAgent (recalculate scores every 4h if not recalculated recently)

- 10. ALL qualifying states with no response in SLA window: RUN FollowUpAgent

## Step 4: Build distributed action locking

- Before any agent acts on a candidate: acquire Redis lock key: agent_lock:{tenant_id}:{candidate_id}, TTL=5 minutes

- If lock already held (another agent is acting on same candidate): skip this candidate this cycle, retry next cycle

- After agent completes action: release lock

- This prevents two agents from both deciding to send a message to the same candidate in the same 15-minute window

## Step 5: Build agent execution metrics

- After each supervisor cycle: calculate metrics for HRMS-P612 Human Dependency Tracker: { actions_by_thunder, actions_by_recruiter, thunder_pct }

- Publish event: supervisor.metrics { tenant_id, thunder_actions_today, human_actions_today, thunder_autonomy_pct }

- Target: thunder_autonomy_pct >= 80% by Month 6

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: Supervisor Never Acts on Recruiter-Owned Conversations

First check in every candidate evaluation: isAIOwner(). If false: skip entirely. The supervisor has zero authority over conversations owned by recruiters.

↳ Triggered by field: isAIOwner() check is always first

## BR-02: Distributed Locking Is Mandatory

Never allow two supervisor cycles to act on the same candidate simultaneously. Redis lock with 5-minute TTL is mandatory. Without locking: candidate could receive two messages in rapid succession from different agents within the same cycle.

↳ Triggered by field: Redis lock per candidate per action

## BR-03: Maximum One Proactive Message Per Candidate Per 2 Hours

Even if multiple agents determine they should act on the same candidate: only ONE agent sends a message per 2-hour window. The supervisor enforces this global rate limit. Agents that 'want' to act but hit the rate limit are deferred to the next cycle.

↳ Triggered by field: message rate limit: 1 per candidate per 2h

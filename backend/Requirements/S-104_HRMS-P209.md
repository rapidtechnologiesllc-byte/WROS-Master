## 2. WHY THIS EXISTS

BlitzenX has 6 distinct roles: Recruiter, HR, Resource Manager, Client Services, Technical Interviewer, BU Head, Director/Admin. Each role has a different portal home — a recruiter who lands on the HR dashboard is confused and cannot do their job. Role-based routing ensures every user lands on the right page the moment they log in.

## 3. WHAT YOU ARE BUILDING

Build: (1) WROS user roles definition and assignment table. (2) Role-based login redirect. (3) Route guards that enforce role access. (4) Admin role management UI. (5) Multi-role support (a user can have multiple roles).

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Define WROS roles and their home routes

- RECRUITER: home = /recruiter/dashboard (HRMS-P201). Access: recruiter-facing APIs. Block: /hr/*, /rm/*, /bu/*, /admin/*

- HR: home = /hr/dashboard (HRMS-P202). Access: HR APIs. Block: /rm/*, /bu/*

- RM: home = /rm/dashboard (HRMS-P203). Access: RM APIs. Block: /hr/*, /bu/*

- CLIENT_SERVICES: home = /cs/dashboard (HRMS-P204). Access: CS APIs.

- TECHNICAL_INTERVIEWER: home = /technical/interview-queue (HRMS-P205). Access: /technical/* only.

- BU_HEAD: home = /bu/hiring-oversight (HRMS-P208). Access: BU APIs + read-only access to recruiter views for their BU.

- DIRECTOR: home = /recruiter/dashboard with full read access to all dashboards. Can view all.

- ADMIN: home = /admin/ai-config (HRMS-0477). Access: all routes.

## Step 2: Create wros_user_roles table

- CREATE TABLE wros_user_roles: id UUID PK, tenant_id UUID, user_id UUID FK→users.id, role ENUM('RECRUITER','HR','RM','CLIENT_SERVICES','TECHNICAL_INTERVIEWER','BU_HEAD','DIRECTOR','ADMIN') NOT NULL, bu_id UUID nullable (for BU_HEAD and TECHNICAL_INTERVIEWER scoping), is_active BOOLEAN default true, assigned_at TIMESTAMP, assigned_by UUID

- UNIQUE constraint: (tenant_id, user_id, role) — one record per user per role. A user can have multiple roles (multi-row).

## Step 3: Build login redirect logic

- On successful login: load wros_user_roles for this user. Determine primary role (priority: ADMIN > DIRECTOR > BU_HEAD > HR > RM > CLIENT_SERVICES > RECRUITER > TECHNICAL_INTERVIEWER).

- Redirect to primary role's home route.

- Role picker: if user has multiple roles — show role picker modal before redirect: 'You have multiple roles. Which would you like to use? [RECRUITER] [HR] [BU_HEAD]'. Store choice in session.

## Step 4: Build route guards on all portal routes

- Middleware on every protected route: check auth session + role access for this route.

- If user does not have required role for the route: redirect to their correct home with toast: 'You do not have permission to access that page.'

- API level: all dashboard endpoints check role via getRolesForUser(user_id, tenant_id) before returning data.

## Step 5: Build Admin Role Management UI

- Route: /admin/users. Auth: ADMIN only.

- Table: Name, Email, Roles (badges), Last Login, Actions ([Edit Roles]).

- [Edit Roles]: opens modal with checkboxes for each role. BU_HEAD and TECHNICAL_INTERVIEWER: also select BU from dropdown.

- Save: updates wros_user_roles records. Immediately applies (no restart needed).

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: Role Changes Take Effect on Next Login — Not Immediately

If an admin removes a role while the user is logged in: the change takes effect on their next login. Current session continues with old roles until session expires. This prevents disrupting an active user mid-task.

↳ Triggered by field: Role changes: next session only

## BR-02: Every User Must Have At Least One Role

The admin cannot remove all roles from a user. At minimum one role must remain. If the last role is removed: show error 'A user must have at least one role.'

↳ Triggered by field: Minimum one role per user

## 2. WHY THIS EXISTS

When the LinkedIn Sourcing Agent (HRMS-P401) finds a Guidewire candidate on LinkedIn, it has limited data: name, LinkedIn ID, headline, current title, location. Creating a full candidate record with mostly null fields and immediately triggering Thunder's engagement sequence is wrong — the candidate has no email or phone yet, so Thunder cannot contact them.

The Skeleton Profile is the solution: a lightweight candidate record in status='SKELETON' that holds only LinkedIn data. Thunder does not engage until the skeleton is upgraded to a full profile with contact info. This preserves data integrity and prevents blank engagement.

## 3. WHAT YOU ARE BUILDING

Build: (1) SKELETON profile status for candidates. (2) createSkeletonProfile() function that creates minimal LinkedIn-sourced records. (3) upgrade flow when contact info is obtained. (4) LinkedIn-specific fields on candidates table.

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Add SKELETON status and LinkedIn fields to candidates table

- Add to candidates.status ENUM: 'SKELETON' (before NEW — the entry state for LinkedIn-sourced candidates)

- ALTER TABLE candidates: ADD COLUMN linkedin_id VARCHAR(200) nullable, ADD COLUMN linkedin_headline VARCHAR(500) nullable, ADD COLUMN linkedin_profile_url TEXT nullable, ADD COLUMN source ENUM('MANUAL','LINKEDIN','WHATSAPP','EMAIL','SUBVENDOR','PORTAL') default 'MANUAL', ADD COLUMN skeleton_created_at TIMESTAMP nullable

- Add UNIQUE constraint on (tenant_id, linkedin_id) when linkedin_id is not null

## Step 2: Build createSkeletonProfile() function

- createSkeletonProfile(linkedin_data, tenant_id) → { candidate_id, is_new: boolean }

- linkedin_data: { linkedin_id, name, headline, current_title, location, profile_url, continent }

- First: call checkForDuplicate(null, null, linkedin_id, tenant_id)

- If duplicate found: return { candidate_id: existing_id, is_new: false }. Update existing record with LinkedIn data if any fields are empty.

- If no duplicate: INSERT candidates with status='SKELETON', source='LINKEDIN', skeleton_created_at=NOW(), all LinkedIn fields. email=null, phone=null.

- Do NOT trigger HRMS-0401 ConversationInitializationService for SKELETON profiles. No conversation workspace yet.

- INSERT candidate_identity_events: event_type='CREATED', contact_channel='LINKEDIN'

## Step 3: Build skeleton upgrade flow

- When a SKELETON candidate's email or phone is obtained (from InMail reply, recruiter manual addition, sub-vendor submission):

- UPDATE candidates SET email=X (or phone=X), status='NEW'

- THEN: trigger ConversationInitializationService (HRMS-0401) — now the candidate has contact info and can be engaged

- upgradeSkeletonProfile(candidate_id, { email, phone }, tenant_id) → updated candidate record

- This upgrade is called by: HRMS-P403 LinkedIn InMail (when candidate replies with contact), HRMS-P404 Human Recruiter Queue (when recruiter manually adds contact)

## Step 4: Build skeleton profile list for recruiter view

- GET /api/candidates?status=SKELETON — returns all skeleton profiles for this tenant with LinkedIn data

- Recruiter can view: LinkedIn name, headline, location, profile link

- Actions: 'Add Contact Info' (opens form to add email/phone → triggers upgrade), 'Send InMail' (routes to HRMS-P403)

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: Thunder Never Engages SKELETON Profiles

ConversationInitializationService is never triggered for candidates with status='SKELETON'. Thunder needs a contact channel (email or phone) to send messages. A skeleton with neither is not yet ready for engagement.

↳ Triggered by field: status='SKELETON' blocks HRMS-0401

## BR-02: Skeleton Upgrade Is Automatic When Contact Info Added

The moment email or phone is added to a SKELETON profile: status automatically changes to 'NEW' and Thunder engagement triggers. The recruiter does not need to manually start engagement.

↳ Triggered by field: upgradeSkeletonProfile() triggers HRMS-0401

## BR-03: LinkedIn ID Is Globally Unique Per Tenant

Two SKELETON records cannot have the same linkedin_id for the same tenant. UNIQUE constraint enforced. On duplicate linkedin_id: return existing skeleton rather than creating duplicate.

↳ Triggered by field: linkedin_id UNIQUE per tenant

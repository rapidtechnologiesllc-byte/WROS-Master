## Why — Business Rationale

- Candidate-demand matching, submission win-probability, candidate dropout risk, and bench utilization prediction were originally four separate stories, but they're the same underlying pattern applied to four related questions: given a person and a situation, what's the likely outcome. Building four near-identical LLM-scoring stories instead of one framework with four configurations is exactly the kind of avoidable duplication EPIC-11's redesign already proved out — one engine, several model configs, is more maintainable and more consistent than four independently-drifting implementations.

## What — Scope

- A single prediction framework covering four talent-signal outputs: (1) rank internal employees against an opportunity's demand on skill+experience+domain+availability+continent fit, (2) estimate a submission's win probability, (3) estimate a candidate's dropout risk mid-pipeline, (4) predict near-term bench utilization trends per skill category — each a distinct model configuration within one shared engine, not four separate services.

## Before — Prerequisites

- HRMS-0509 Match Bench Resources to Opportunity must be live — this engine's matching config extends that existing capability with AI ranking rather than replacing its underlying data access.

- At least 90 days of historical submission/placement outcome data should exist for win-probability and dropout-risk configs to have meaningful training signal — running this on a brand-new tenant with no history will produce low-confidence outputs, which the confidence_pct field should make visible rather than hide.

## Implementation Steps

## Step 1: Build the shared prediction engine scaffolding

- One service with four named configurations (matching, win_probability, dropout_risk, bench_utilization), each defining its own prompt template and input data query, sharing common LLM call handling, retry logic, and output parsing.

## Step 2: Implement the matching configuration

- Input: opportunity/demand requirements + candidate bench pool.

- Output: ranked list with fit rationale per candidate — skill, experience, domain, availability, continent all named explicitly in the rationale, not just a bare score.

## Step 3: Implement the win-probability configuration

- Input: submission details + historical outcomes for similar submissions (same client, similar role, similar candidate profile).

- Output: win_probability_pct with confidence based on how much comparable historical data exists.

## Step 4: Implement the dropout-risk configuration

- Input: candidate's engagement pattern (response times, Thunder conversation sentiment where available, time-in-stage).

- Output: dropout_risk_pct, surfaced to the owning recruiter as an early-warning signal, not an automatic removal.

## Step 5: Implement the bench-utilization configuration

- Input: current bench composition by skill category + historical demand patterns.

- Output: predicted utilization trend per skill category over the next 30/60/90 days, feeding into S-374's dashboard forecast section.

## Business Rules

## BR: BR-1001-01 — All four prediction types are advisory only, no autonomous action

- Matching surfaces a ranked list for RM review; win-probability and dropout-risk inform recruiter prioritization; bench utilization informs planning — none of the four ever auto-assigns, auto-submits, or auto-removes anyone.

- Field: No prediction output has a direct write path to employee_allocations, submissions, or candidate pipeline stage — only to advisory display fields

## BR: BR-1001-02 — Confidence scoring reflects actual data volume, not a fixed default

- A prediction made from 3 historical data points should visibly show lower confidence than one made from 300 — this transparency is what lets a human correctly weight the signal.

- Field: confidence_pct is computed from the volume/recency of comparable historical data feeding the prediction, not a static value

## BR: BR-1001-03 — All four configurations share one engine, not four independent services

- Prevents four near-identical LLM integration points from drifting apart in error handling, retry logic, or output format over time.

- Field: One shared service module with four named configs, not four separate deployed services

## Acceptance Criteria

- AC-1: A matching request returns a ranked candidate list with named rationale factors, not a bare score.

- AC-2: A win-probability estimate for a submission with no comparable historical data shows visibly low confidence rather than a falsely confident number.

- AC-3: No prediction output anywhere writes directly to an allocation, submission, or pipeline-stage table.

- AC-4: An LLM call failure for one prediction type does not affect the availability of the other three configurations.

## Not In Scope

- No autonomous candidate submission, allocation, or pipeline-stage change based on any prediction — every output is advisory, reviewed by a human.

- No single unified 'talent score' blending all four signals into one number — each prediction type answers a distinct question and stays distinct in its output.

## 2. WHY THIS EXISTS

Candidates access the portal via a WhatsApp link tap on their mobile phone — not a desktop browser. Every single portal page must be fully functional on a 375px wide screen with a mobile keyboard and one thumb. A portal that works perfectly on desktop but breaks on mobile is a failed portal.

This is a quality assurance and optimization story that runs AFTER all portal pages are built. It identifies mobile-specific issues and fixes them systematically.

## 3. WHAT YOU ARE BUILDING

Build: (1) Mobile testing checklist for all portal pages. (2) Fix all mobile layout issues identified. (3) Touch target audit (minimum 48x48px). (4) Performance optimization for mobile networks. (5) iOS and Android browser compatibility testing.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Run mobile audit on all portal pages

- Test on: 375px, 390px, 412px widths. iOS Safari + Chrome for Android.

- Audit checklist per page: (1) No horizontal scrolling. (2) All text readable without zooming (min 14px). (3) All buttons/links at least 48x48px. (4) Forms usable with mobile keyboard (inputs scroll into view). (5) Images do not overflow. (6) Navigation tabs visible without scrolling.

- Document every issue found with screenshot and page name.

## Step 2: Fix layout issues found in audit

- Common fixes: replace fixed-width elements with 100% width. Add max-width containers. Use flexbox column layout on mobile. Remove horizontal padding that pushes content off-screen.

- Forms: inputs must trigger correct mobile keyboard type (type=tel for phone, type=email for email, type=number for salary). Labels must be above inputs (not beside) on mobile.

- Tables: replace horizontal tables with card layouts on mobile (one row per card). Horizontal scrolling on tables is not acceptable.

## Step 3: Touch target audit

- Every tappable element must be minimum 48x48px. Check: all buttons, links, tab navigation items, file upload areas, toggle controls.

- Common violations: small 'Why?' explainability links, small badge tags, pagination controls.

- Fix by adding padding or minimum height/width to affected elements.

## Step 4: Mobile performance optimization

- Target: first meaningful paint on 3G in under 3 seconds.

- Measures: (1) Lazy load images. (2) Single API call per page (already built in portal APIs). (3) Compress JS/CSS bundles. (4) Use loading skeletons (already in HRMS-P105/P106).

- Test with Chrome DevTools throttled to 'Slow 3G'. Record time to first interactive.

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: Zero Horizontal Scrolling on Any Portal Page at 375px

No portal page at 375px width may produce a horizontal scrollbar or require horizontal scrolling. This is a binary pass/fail criterion. Any page with horizontal scrolling fails this story's acceptance criteria.

↳ Triggered by field: 375px width — zero horizontal scroll

## BR-02: All Touch Targets Minimum 48x48px

Any element that can be tapped (buttons, links, tabs, toggles, file upload zones) must have a touch target of at least 48x48px. This is the WCAG 2.5.5 minimum for touch interfaces.

↳ Triggered by field: 48x48px minimum touch target

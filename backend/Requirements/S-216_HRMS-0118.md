## Why — Business Rationale

- Almost every entity in WROS needs the same two things: a chronological "what happened" feed and the ability to attach a file. Building both fresh for candidates, then again for projects, then again for employees is exactly the kind of repeated-pattern work that should be one reusable framework — not five subtly-different implementations that drift apart over time.

## What — Scope

- A generic, polymorphic activity_timeline table (attachable to any entity_type + entity_id) and a shared file_uploads system with S3-backed storage, virus scanning, and multi-region support — both consumed by any story that needs a history feed or an attachment, without rebuilding the plumbing.

## Before — Prerequisites

- HRMS-0109 Multi-Tenant Data Isolation — both tables are tenant-scoped like everything else.

- S3 (or equivalent) storage backend and virus-scanning service must be provisioned per Section 11.

## Implementation Steps

## Step 1: Create activity_timeline table

- Polymorphic: entity_type + entity_id + tenant_id + actor + action + description + timestamp.

- Any story writes to this table instead of building its own history table.

## Step 2: Create file_uploads table and storage pipeline

- S3-backed (or equivalent), presigned URL access control per Section 7.1.

- Multi-region storage bucket selection based on the uploading tenant's continent.

## Step 3: Build virus scanning on upload

- Every file passes through a scan before being marked available — infected files are quarantined, not silently accepted.

## Step 4: Enforce size and type limits

- Configurable per file category (resume vs invoice vs compliance PDF) via HRMS-0115 system config.

## Step 5: Build the shared timeline + attachment UI components

- Reusable frontend components any entity detail screen can drop in, rather than each screen building its own feed/upload widget.

## Business Rules

BR: BR-0118-01 — All entity history goes through this shared table, no per-entity custom history tables

- Consistency across the platform depends on every entity's activity feed having the same shape — a bespoke history table for one entity type breaks that consistency and duplicates the plumbing.

- Field: activity_timeline is polymorphic (entity_type, entity_id) — the sanctioned pattern for any new story needing a history feed

## BR: BR-0118-02 — A file is never accessible until it passes virus scanning

- Files sit in a QUARANTINE state until scan completion — download/preview links are not generated for unscanned or infected files.

- Field: file_uploads.scan_status must equal CLEAN before presigned access URLs are issued

## BR: BR-0118-03 — Storage region follows the uploading tenant's continent

- Supports data residency expectations per Section 6.3 platform vision — files aren't defaulted to a single global bucket regardless of origin.

- Field: file_uploads.storage_region set from tenant.continent at upload time

## Integrations

| System / API | Direction | Trigger | Payload | Auth | Notes |
|---|---|---|---|---|---|
| S3 (or equivalent object storage) | Outbound | Every file upload | file bytes, metadata | Presigned URL, per Section 7.1 | On Failure: upload marked FAILED, user notified to retry |
| Virus scanning service | Outbound | Every upload before availability | file bytes | Internal service call | On Failure: file stays QUARANTINED, never auto-approved on scan-service failure |

## Acceptance Criteria

- AC-1: Any entity type can write to activity_timeline without a schema change, verified by writing timeline entries for two unrelated entity types.

- AC-2: A file with no successful scan result is never issued a presigned access URL.

- AC-3: A scan-service failure leaves the file in QUARANTINED, not auto-approved.

- AC-4: An uploaded file's storage_region matches the uploading tenant's configured continent.

## Not In Scope

- No entity-specific timeline tables, ever — this is the one sanctioned pattern.

- No client-side virus scanning or scan bypass for 'trusted' file types — every file scans, no exceptions.

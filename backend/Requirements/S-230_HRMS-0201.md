## Why — Business Rationale

- Every dollar BlitzenX tracks, every project it delivers, and every opportunity it pursues traces back to a client record. If that record is thin — no multi-currency support, no contact history, no notes timeline — every downstream revenue calculation inherits that weakness. This is the single master entity the entire Revenue Visibility Engine is built on top of.

## What — Scope

- The client master entity — name, industry, country, currency, account manager, contacts, and a notes timeline — with full create/update/list/detail views and multi-currency support baked in from day one, not retrofitted later.

## Before — Prerequisites

- HRMS-0109 Multi-Tenant Data Isolation must be live — clients are tenant-scoped like every other entity.

## Implementation Steps

## Step 1: Create clients table

- Run CREATE TABLE per Data Mapping — name, industry, country, default_currency, account_manager_id, tenant_id.

## Step 2: Build Create/Update client screens

- Standard form, default_currency drives every downstream monetary display for that client per HRMS-0121's convertFromUSD() pattern.

## Step 3: Build the client list and detail views

- List: filterable by industry, account manager, BU. Detail: single-page view with tabs for Contacts and Notes.

## Step 4: Build client contact management

- Multiple contacts per client, each with role (Decision Maker / Day-to-Day / Finance), primary contact flag.

## Step 5: Build the client notes timeline

- Uses the shared HRMS-0118 Activity Timeline framework rather than a bespoke client-specific history table — this is exactly the reuse pattern that framework exists for.

## Business Rules

BR: BR-0201-01 — Client notes use the shared Activity Timeline framework, not a bespoke table

- Per HRMS-0118's BR-0118-01, any story needing an entity history feed reuses the polymorphic activity_timeline table.

- Field: Client notes write to activity_timeline with entity_type='client'

## BR: BR-0201-02 — Exactly one contact per client is marked Primary at any time

- Prevents ambiguity about who the default point of contact is for automated communications.

- Field: Setting a new Primary contact automatically unsets the previous one, enforced transactionally

## Acceptance Criteria

- AC-1: A client can be created with at least one contact and exactly one marked Primary.

- AC-2: Client notes appear in the same Activity Timeline component used by other entities, verified against HRMS-0118's shared table.

- AC-3: Setting a new Primary contact automatically unsets the prior primary, verified with a two-contact test.

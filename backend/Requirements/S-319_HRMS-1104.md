## Why — Business Rationale

- Once a candidate is promoted from staged to real, the very next mechanical step — the first outreach touch — is still manual today. That first-touch delay is the single biggest driver of losing a candidate to a competing offer before BlitzenX even makes contact. This agent's only job is to close that gap between promotion and first message, using the same governed send path Thunder already uses so none of the existing safety rules are bypassed.

## What — Scope

- An agent that watches for newly-promoted candidates and newly-created demand-matched submissions, sequences a personalized multi-channel outreach touch (WhatsApp primary, LinkedIn InMail secondary, email fallback), and sends the first message via the existing sendThunderMessage() path — it composes and times messages, it never bypasses Thunder's send governance.

## Before — Prerequisites

- S-318 HRMS-1103 must be producing promoted candidates with populated consent_given fields.

- sendThunderMessage() must expose a channel parameter (whatsapp/linkedin/email) and return a structured rejection reason when it blocks a send.

## Implementation Steps

## Step 1: Create outreach_sequences table

- Run CREATE TABLE per Data Mapping.

## Step 2: Build the promotion/match event listener

- Subscribe to candidate.promoted and submission.matched events.

- Debounce: if a candidate has an active outreach_sequence within the last 24 hours, do not start a second one for the same demand.

## Step 3: Compose the message

- Call LLM with candidate profile, matched demand summary, and any prior channel history.

- Store message_text, primary_channel, fallback_sequence in outreach_sequences.

## Step 4: Check business-hours and consent gates

- send_after_hours_check must confirm current time is within the candidate's inferred timezone business hours (08:00-20:00) OR the demand is p1_emergency=true.

- Confirm candidate.consent_given=true before proceeding — if false, do not send, log and stop.

## Step 5: Send via sendThunderMessage()

- Publish agent.action.intent to Orchestration Router (risk_tier=LOW) before send.

- Call sendThunderMessage() with primary_channel and message_text.

- On rejection due to R-08 lock: log rejection, mark sequence status=BLOCKED_OWNERSHIP, do NOT auto-switch channel — escalate to recruiter queue instead.

## Step 6: Advance the fallback sequence on non-response

- If no candidate response within 48 hours, move to next channel in fallback_sequence.

- Cap at 3 total touches across all channels before marking sequence COMPLETE_NO_RESPONSE.

## Business Rules

## BR: BR-1104-01 — sendThunderMessage() is the only send path, no exceptions

- This agent never sends via a raw WhatsApp/email API call — every send goes through sendThunderMessage() so R-08 ownership and consent checks apply uniformly.

- Field: outreach_sequences.sent_via always = 'sendThunderMessage'

## BR: BR-1104-02 — R-08 rejection does not trigger automatic channel switching

- If Thunder is locked because a recruiter owns the conversation, this agent must not silently try LinkedIn or email instead — that would defeat the purpose of the ownership lock. It escalates to the recruiter queue.

- Field: sequence status=BLOCKED_OWNERSHIP halts fallback_sequence progression until recruiter releases lock

## BR: BR-1104-03 — Consent is a hard gate

- No message is composed or sent for a candidate with consent_given=false, matching platform-wide consent policy.

- Field: candidate.consent_given checked before message composition, not just before send

## BR: BR-1104-04 — Maximum 3 touches across the full sequence

- To avoid candidate fatigue and spam-like behavior, no more than 3 total outreach touches are sent per demand match, across all channels combined.

- Field: outreach_sequences.touch_count capped at 3, enforced at insert

## Acceptance Criteria

- AC-1: A newly promoted candidate with consent_given=true receives a first outreach touch within 5 minutes during business hours.

- AC-2: A candidate with consent_given=false never receives a composed or sent message from this agent.

- AC-3: An R-08 conversation-ownership rejection halts the sequence and routes to the recruiter queue, without a fallback-channel send occurring.

- AC-4: No outreach_sequences row exceeds touch_count=3.

- AC-5: Every send in outreach_sequences shows sent_via='sendThunderMessage' — no direct channel API calls exist in the codebase for this agent.

- AC-6: Outside business hours (candidate timezone) and demand not p1_emergency, send is deferred, not dropped.

## Not In Scope

- No direct channel API integrations (raw WhatsApp Business API calls, raw email send) — sendThunderMessage() only.

- No automatic escalation past 3 touches into cold-calling or other channels — sequence simply completes as NO_RESPONSE.

- No A/B message testing framework in this story — single LLM-composed message per touch, optimization is a future story.

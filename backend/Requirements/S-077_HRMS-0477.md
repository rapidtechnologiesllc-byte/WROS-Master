## 2. WHY THIS EXISTS

Thunder's behavior is currently controlled by scattered system_configuration records, hardcoded constants, and per-story config keys. A recruiter admin cannot easily see or change Thunder's settings. This story builds a unified AI Configuration page where tenant admins can control all Thunder settings from one place: agent name/persona, engagement SLA thresholds, follow-up timing, digest schedule, and global pause.

## 3. WHAT YOU ARE BUILDING

Build: (1) Unified tenant_ai_config table that consolidates all Thunder settings. (2) Admin UI at /admin/ai-config with all configurable parameters. (3) Config versioning so changes can be reviewed and rolled back.

## 4. BEFORE YOU START

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Create tenant_ai_config table

- CREATE TABLE tenant_ai_config: id UUID PK, tenant_id UUID UNIQUE, ai_agent_name VARCHAR(100) default 'Thunder', ai_agent_persona TEXT, greeting_channel ENUM('WHATSAPP_FIRST','EMAIL_FIRST','BOTH_PARALLEL') default 'BOTH_PARALLEL', whatsapp_followup_hours INTEGER default 24, email_followup_hours INTEGER default 48, max_followup_count INTEGER default 3, ghosting_reactivation_days INTEGER default 14, sla_first_contact_seconds INTEGER default 60, sla_no_contact_hours INTEGER default 24, digest_enabled BOOLEAN default true, digest_send_time VARCHAR(5) default '08:00', thunder_enabled BOOLEAN default true, qualification_field_order JSONB (array of field_names in custom order, or null for default), escalation_keywords JSONB (array of custom escalation trigger keywords), updated_at TIMESTAMP, updated_by UUID

- Migrate all existing config from system_configuration to this table for BlitzenX tenant

## Step 2: Build config read/write functions

- getTenantAIConfig(tenant_id) → tenant_ai_config record. Cache in Redis for 5 minutes.

- updateTenantAIConfig(tenant_id, updates, updated_by) → updated record

- Log every config change in conversation_audit_log: actor_type=ADMIN, event_type=AI_CONFIG_UPDATED, before_state + after_state

- Invalidate Redis cache on every update

## Step 3: Build /admin/ai-config UI page

- Route: /admin/ai-config. Auth: ADMIN role only.

- Sections: IDENTITY (agent name, persona), ENGAGEMENT TIMING (follow-up hours, max follow-ups, reactivation days), SLA SETTINGS (first contact, no contact alert), DAILY DIGEST (enabled toggle, send time), GLOBAL CONTROLS (thunder enabled/disabled, escalation keywords)

- Each section: read mode with edit button. Click edit: form opens for that section only. Save / Cancel.

- Change confirmation for critical settings (ai_agent_name change, thunder_enabled change): 'Are you sure? This will affect all active conversations.'

- Show last updated by and timestamp for each section

## Step 4: Wire all existing config reads to getTenantAIConfig()

- Replace all system_configuration lookups for Thunder settings with getTenantAIConfig() calls

- HRMS-0411: reads ai_agent_name + ai_agent_persona from here

- HRMS-0441: reads whatsapp_followup_hours + email_followup_hours

- HRMS-0465: reads digest_enabled + digest_send_time

- HRMS-0475: reads thunder_enabled

- HRMS-0435: reads escalation_keywords (adds to rule-based trigger list)

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: AI Agent Persona Changes Require BA Sign-Off Before Save

When persona field is changed: show warning 'The AI persona change requires Lead BA written approval before it goes live. Please confirm BA has approved this change.' Checkbox required to confirm before Save button enables.

↳ Triggered by field: ai_agent_persona

## BR-02: Disabling Thunder Is Reversible — But Not Instant

Setting thunder_enabled=false stops Thunder within one Supervisor cycle (15 minutes). In-flight messages currently being sent complete. No new messages are sent after the next Supervisor cycle.

↳ Triggered by field: thunder_enabled=false

## Why — Business Rationale

- A client relationship deteriorating shows up in a dozen small signals before it shows up as a lost account — slow approvals, terse rejection feedback, vague RFPs. This composite score gives CS leadership the same early-warning pattern EPIC-11's Project Health Monitoring Agent gives to project delivery, applied to the client relationship itself.

## What — Scope

- An internal-only, 0-100 composite Client Health Score computed from four weighted signals — approval speed (25%), submission response rate (25%), communication responsiveness (20%), rejection feedback quality (15%), RFP clarity (15%) — with a CS manager alert when a client's score drops below 40.

## Before — Prerequisites

- S-184, S-193, S-178, and S-187 must all be live and producing the underlying signal data.

## Implementation Steps

## Step 1: Build the four sub-score calculations

- approval_speed_score: derived from S-184's SLA data (faster approval = higher score).

- response_rate_score: derived from S-193's message response timing.

- communication_responsiveness_score: derived from overall thread engagement pattern.

- rejection_feedback_quality_score: derived from S-178's structured rejection data — presence of detailed free-text feedback vs. minimal boilerplate.

- rfp_clarity_score: derived from S-187 — how often an RFP required a clarification (S-191) before sourcing could begin; more clarifications needed lowers this score.

## Step 2: Compute the weighted composite

- health_score = approval_speed*0.25 + response_rate*0.25 + communication*0.20 + feedback_quality*0.15 + rfp_clarity*0.15.

## Step 3: Wire the alert

- health_score < 40 triggers an HRMS-0113 alert to the CS manager — this is the internal early-warning equivalent of HRMS-1107's AT_RISK flag.

## Business Rules

## BR: BR-0730-01 — Health score is a deterministic weighted formula, not LLM-derived

- Matches the reasoning behind HRMS-1107's identical design choice — the score must be reproducible and explainable, not a black-box judgment.

- Field: health_score computed in application code from the fixed 25/25/20/15/15 weighting

## BR: BR-0730-02 — Score is strictly internal, never visible to the client

- This is a BlitzenX-side relationship management tool, not a client-facing metric — showing a client 'you scored 38' would be actively counterproductive to the relationship it's meant to protect.

- Field: health_score field is excluded from every client-facing API response and portal view

## Acceptance Criteria

- AC-1: A client with slow approvals, low response rate, and vague RFPs produces a health_score reflecting all three factors, verifiable by manual recalculation of the weighted formula.

- AC-2: A score below 40 triggers exactly one CS manager alert per breach event, not a repeated daily alert for the same ongoing low score.

- AC-3: The health_score field never appears in any client-facing API response or UI.

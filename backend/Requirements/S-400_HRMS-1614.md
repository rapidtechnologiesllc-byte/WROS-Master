The dashboard itself adds no new calculation logic; its entire job is presenting already-correct numbers clearly, which means getting the block structure and color-coding exactly right matters more here than anywhere else in this epic — this is the one screen where a subtle display bug looks exactly like a real financial problem to whoever's looking at it.

## What — Scope

## Before — Prerequisites

## Implementation Steps

## Step 1: Build Block 1 — the 5 big metrics

- Revenue, Gross Profit, EBITDA, Net Profit (all YTD, USD, combined BXIN+BXUS), and Reserve (current, combined) — full width, top of screen, exactly matching your layout.

## Step 2: Build Block 2 — by location

- India (BXIN) vs. US (BXUS): Revenue YTD, Expense YTD, Net Profit %, Target (25%), Status (GREEN/RED), Reserve Balance with 12-month status — reads directly from HRMS-1607 and HRMS-1612, no recalculation.

## Step 3: Build Block 3 — by BU

- Axion vs. PRISM: Revenue YTD, Expense YTD, Net Profit % — this requires BU-level scoping within each entity's P&L, not just entity-level, so confirm HRMS-1607's calculation supports a BU dimension, not only an entity dimension, before this block can populate correctly.

## Step 4: Build Block 4 — headcount

- Total, Billable/Non-Billable per entity, Bench Alerts (>45 days) — reads from the existing Resource & Bench Management data (Phase 4) rather than computing headcount independently here.

## Step 5: Build Block 5 — HTD hiring analysis

- Current BXIN Net Profit % vs. 25% target, the gap in dollars, HTD hires needed to close it, and ROI vs. lateral hiring — this block has real calculation logic of its own (translating a margin gap into a hiring-count recommendation) that doesn't exist yet in any other story; build it here as this block's own scoped logic, referencing HRMS-1608's cost figures for the ROI comparison.

## Step 6: Build Block 6 — key unit economics

- Blended Delivery Rate per entity and org-wide, Revenue per Employee, Contribution Margin % — each a straightforward aggregation over already-computed per-employee and per-entity figures.

## Step 7: Build Block 7 — partner revenue traffic lights

- Per partner: Revenue, Expense, Ratio, and a colored status cell — reads from HRMS-1611's incentive calculation for the revenue basis and applies the workbook-wide color rules below.

## Step 8: Apply the workbook-wide color coding consistently

- Exceeding: Revenue ≥ 2.0× Expense (GREEN #70AD47). On Track: ≥1.5× (LIGHT GREEN #A9D18E). Safe Mode: ≥1.25× (gradient light green to yellow). At Risk: <1.25× (RED #FF0000).

- Applied identically across Partner Revenue, P&L margins, Reserve health, and BU/Location P&L — one shared color-calculation function, not four independently-implemented versions of the same four thresholds.

- Color is set on the status cell's background itself, not a separate color-indicator column, per your explicit dashboard-clarity decision.

## Business Rules

BR: BR-1614-01 — Every figure on this dashboard is read from its source engine, never recalculated here

- This story has no independent P&L, Reserve, or incentive logic — its entire job is correct, consistent presentation of numbers computed elsewhere, so a discrepancy is always traceable to exactly one source engine, never ambiguous between 'the dashboard's math' and 'the engine's math.'

- Field: Every dashboard widget's data query is a direct read against HRMS-1607/1608/1611/1612/1613's output tables, no local computation beyond simple sums for the org-rollup display

BR: BR-1614-02 — Color coding is one shared function applied identically everywhere it's used

- Four independently-implemented copies of the same four thresholds is exactly the kind of drift this platform has already been burned by (see: LinkedIn sourcing built three times) — this rule prevents that happening to something as visible as dashboard color coding.

- Field: calculateStatusColor() is called by every block that needs it (1, 2, 3, 7), none reimplement the threshold logic locally

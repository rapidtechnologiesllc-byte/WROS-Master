## 2. WHY THIS EXISTS

A candidate named John Smith applies via LinkedIn, then messages on WhatsApp from the same phone, then emails from the same address. Without identity resolution, WROS creates THREE candidate records for one person. Thunder sends the same person the same qualification questions three times, from three different AI sessions, with three different context memories. This is catastrophic for the candidate experience and data integrity.

One person = one record. Always. This is HRMS Business Rule #7 and the foundation of the entire candidate relationship.

## 3. WHAT YOU ARE BUILDING

Build: (1) Identity dedup engine that checks email+phone+LinkedIn ID on every inbound contact. (2) Identity merge function that consolidates duplicate records. (3) Source attribution tracking (which channel each contact came from). (4) Conflict resolution rules for when data from multiple sources differs. (5) Admin dedup dashboard.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Build dedup check function

- checkForDuplicate(email, phone, linkedin_id, tenant_id) → { existing_candidate_id: UUID | null, match_reason: string | null }

- Check in order: (1) email exact match AND tenant_id. (2) phone E.164 match AND tenant_id. (3) linkedin_id exact match AND tenant_id.

- Return first match found. Log which field triggered the match.

- If no match: return { existing_candidate_id: null }

- This function is called BEFORE every new candidate INSERT anywhere in the system

## Step 2: Update POST /api/candidates to check dedup first

- Before inserting new candidate: call checkForDuplicate(email, phone, linkedin_id, tenant_id)

- If duplicate found: do NOT create new record. Return existing candidate_id. Log DUPLICATE_PREVENTED.

- Update the existing record with any new information from this contact (if new email/phone/linkedin_id available on existing record)

- If no duplicate: create new candidate normally (HRMS-0401 flow)

## Step 3: Build mergeCandidate() function for manual resolution

- mergeCandidate(primary_id, secondary_id, tenant_id, merged_by) → merged candidate record

- KEEP: primary_id record (this becomes the canonical record)

- MERGE: copy any non-null fields from secondary that are null on primary

- REASSIGN: all foreign key references to secondary_id → update to primary_id: conversation_messages, candidate_conversations, candidate_missing_fields, candidate_memory_facts, candidate_skill_tags, candidate_job_scores, preboarding_documents, interviews, offers

- MARK: secondary record status='MERGED', merged_into=primary_id, merged_at=NOW()

- LOG: conversation_audit_log entry for the merge

## Step 4: Build candidate_identity_events table for source tracking

- CREATE TABLE candidate_identity_events: id UUID PK, tenant_id UUID, candidate_id UUID, contact_channel ENUM('WHATSAPP','EMAIL','LINKEDIN','PORTAL','SUBVENDOR','MANUAL'), contact_identifier VARCHAR(500) (phone/email/linkedin_id that was matched), event_type ENUM('CREATED','MATCHED_EXISTING','MERGED_FROM','MERGED_INTO'), created_at TIMESTAMP

- Insert on: new candidate creation (CREATED), duplicate match prevented (MATCHED_EXISTING), manual merge (MERGED_FROM, MERGED_INTO)

## Step 5: Build admin dedup dashboard

- GET /api/admin/dedup-candidates — returns potential duplicates not yet resolved: pairs of candidates sharing email or phone within same tenant

- UI at /admin/dedup — shows pairs with: candidate A details, candidate B details, merge button, ignore button

- Merge button: calls mergeCandidate(primary_id, secondary_id). Admin selects which is primary.

- Ignore button: marks the pair as 'not a duplicate' — suppresses from future dedup suggestions

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: One Candidate One Record — Enforced at Every Entry Point

Every point where a candidate enters the system (API create, WhatsApp inbound, email inbound, LinkedIn import, sub-vendor submission, portal registration) must call checkForDuplicate() before creating a new record. No exceptions.

↳ Triggered by field: checkForDuplicate() called at every entry point

## BR-02: Email Match Takes Precedence Over Phone Match

If email matches candidate A and phone matches candidate B: the email match wins (email is more reliable for identity). Resolve email match first.

↳ Triggered by field: match priority: email > phone > linkedin_id

## BR-03: Merge Preserves the Primary Record ID

When merging: the primary_id candidate record is preserved with all its data and ID. The secondary record is archived (status=MERGED). All references update to primary_id. Never delete either record.

↳ Triggered by field: mergeCandidate() preserves primary_id

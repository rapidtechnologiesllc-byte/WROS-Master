## Why — Business Rationale

- Every other agent in this epic runs unattended overnight and depends on external integrations (WhatsApp, LinkedIn, Outlook, DocuSign) staying up. If WhatsApp Business API silently degrades at 1am, every downstream agent that depends on sendThunderMessage() fails quietly until a human notices candidates stopped hearing back. This agent exists specifically so a token expiring or a rate limit being hit doesn't take eight hours to surface.

## What — Scope

- A continuous health-check agent that pings every external integration listed in Section 11 on a fixed cadence, distinguishes self-healable failures (token refresh, transient retry) from failures requiring a human, auto-remediates the former, and pages for the latter — including monitoring the liveness of the Orchestration Router (HRMS-1101) itself, per BR-1101-06.

## How is Agentic AI Used in This

- Trigger cadence: health check every 5 minutes per integration; deeper diagnostic check every 30 minutes.

- This agent's core loop is deterministic (HTTP health check, response code, latency) — no LLM is needed to detect that an integration is down.

- LLM call (claude-sonnet-4-6, max_tokens=300), used only when a failure is NOT one of the known self-healable patterns: given the error response and recent failure history, classifies whether this looks like a transient issue (auto-retry) or a structural one (needs human), and drafts the page summary.

- Pre-authorized self-heal actions (LOW risk, auto-execute): OAuth token refresh (Outlook), exponential backoff retry (LinkedIn rate limits), Redis connection pool reset. These are the ONLY three self-heal actions authorized — nothing else auto-remediates.

- Any failure outside the three self-heal patterns is MEDIUM/HIGH risk by default and always pages a human — this agent does not attempt novel remediation.

## Before — Prerequisites

- Every integration in Section 11 must expose a lightweight health-check endpoint or an equivalent low-cost probe call.

## Implementation Steps

## Step 1: Create integration_health_checks table

- Run CREATE TABLE statement in Data Mapping.

## Step 2: Build the 5-minute probe loop

- For each integration in Section 11 (Outlook, LinkedIn, WhatsApp, DocuSign, S3, Redis, SMS Gateway) plus HRMS-1101 Orchestration Router, execute the defined health-check call.

- Record status_code, latency_ms, success boolean.

## Step 3: Apply self-heal rules

- Outlook 401 → attempt OAuth token refresh once, re-check immediately.

- LinkedIn 429 → apply exponential backoff (per existing rate-limit handling), no immediate re-check.

- Redis connection error → reset connection pool, re-check immediately.

- Any other failure type → do NOT self-heal, proceed to classification.

## Step 4: Classify non-self-healable failures

- Call LLM with error payload and recent failure history for that integration.

- Output: {is_transient, recommended_action, page_summary}.

## Step 5: Page or log

- Self-healed successfully: log only, visible in health dashboard.

- Non-self-healed, classified transient: log + WATCH status, re-check next cycle before paging.

- Non-self-healed, classified structural, OR transient that persists 3 consecutive cycles: page on-call via HRMS-0113 P0 channel immediately.

## Step 6: Monitor the Orchestration Router itself

- Include HRMS-1101 in the probe list — its downtime triggers the fail-open CRITICAL alert defined in BR-1101-06.

## Business Rules

## BR: BR-1108-01 — Only three self-heal actions are authorized

- OAuth token refresh, exponential backoff retry, and Redis pool reset are the entire self-heal action set. Any other failure type always requires human paging — this agent does not improvise remediation.

- Field: self_heal_action enum constrained to exactly these three values

## BR: BR-1108-02 — Persistent transient failures escalate after 3 cycles

- A failure classified transient that has not resolved after 3 consecutive 5-minute checks (15 minutes total) is paged even though it was initially classified as non-urgent — this prevents an LLM misclassification from suppressing a real outage indefinitely.

- Field: consecutive_failures >= 3 forces page regardless of is_transient classification

## BR: BR-1108-03 — This agent monitors the Orchestration Router's liveness specifically

- Per BR-1101-06, Orchestration Router downtime must trigger a CRITICAL alert within 60 seconds — this agent is the mechanism that detects that downtime.

- Field: HRMS-1101 included in the probe list with a shortened 60-second check interval, distinct from the standard 5-minute cadence

## Acceptance Criteria

- AC-1: An Outlook 401 response triggers an automatic token refresh and immediate re-check, with no human paged if the refresh succeeds.

- AC-2: A failure type outside the three authorized self-heal actions never attempts remediation and always proceeds to classification.

- AC-3: A transient-classified failure that persists 3 consecutive cycles pages on-call even though it was not initially classified urgent.

- AC-4: HRMS-1101 Orchestration Router downtime is detected within 60 seconds via this agent's shortened check interval.

- AC-5: An LLM classification failure defaults to structural (page-worthy), never silently suppressing a real outage.

## Not In Scope

- No self-heal actions beyond the three explicitly authorized — no generic 'restart the service' automation.

- No automatic integration reconfiguration (changing endpoints, credentials rotation beyond token refresh).

- No customer-facing status page in this story — internal health dashboard only.

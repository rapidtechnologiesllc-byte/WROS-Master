## Why — Business Rationale

- Section 12's role table (Admin, Director, BU Head, RM, Recruiter, CS, Technical Manager, Practice Head, Client Contact, Sub-Vendor) is only a real guarantee if it's enforced identically on every single endpoint, not re-checked by hand in each controller where a developer might forget one. This story turns Section 12 from a table in a document into something the API physically cannot violate.

## What — Scope

- Backend middleware that validates the authenticated user's role and tenant against every API endpoint's declared permission requirements, before any handler code runs.

## Before — Prerequisites

- HRMS-0103 RBAC must define the permission-to-role mapping this middleware reads.

## Implementation Steps

## Step 1: Define endpoint permission declarations

- Every route declares its required permission(s) in a manifest, not scattered inline checks.

- Missing declaration = deny by default, not allow by default.

## Step 2: Build the middleware

- Runs before every handler: resolves user role + tenant from session, checks against the route's declared permission, checks tenant/BU scope per HRMS-0109/0107.

## Step 3: Build the deny-by-default guard

- Any route without an explicit permission declaration is rejected at startup with a build-time error, not silently left open.

## Step 4: Add permission audit logging for denials

- Every 403 denial is logged with user, route, and required-vs-actual permission — useful both for security review and for catching legitimate access gaps.

## Business Rules

## BR: BR-0114-01 — Deny by default, not allow by default

- Any endpoint without an explicit permission declaration fails to start the application at all — an undeclared route is treated as a bug, not an open door.

- Field: Application startup check scans all routes for permission declarations, fails build if any is missing

## BR: BR-0114-02 — Permission checks happen before handler code executes

- No handler function ever runs before the middleware has confirmed the caller is authorized — this is enforced by middleware ordering, not by convention.

- Field: Middleware registered globally, first in the request pipeline, before any route-specific logic

## Acceptance Criteria

- AC-1: The application fails to start if any route lacks an explicit permission declaration.

- AC-2: A request from a user lacking the required permission is rejected before any handler logic executes, verified by a handler-side side-effect (e.g., a DB write) never occurring on a denied request.

- AC-3: Every denial is logged with user, route, and permission gap.

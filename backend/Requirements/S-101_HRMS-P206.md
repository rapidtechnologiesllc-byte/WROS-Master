## 2. WHY THIS EXISTS

Interview feedback is currently unstructured — interviewers type free-form notes in email or Slack. This makes it impossible to compare candidates consistently, derive a score, or enforce the L1-PASS-required-for-L2 rule. The structured feedback form creates a consistent, scorable record for every interview — enabling data-driven hiring decisions and compliance with BlitzenX's interview rules.

## 3. WHAT YOU ARE BUILDING

Build the Interview Feedback Form at /technical/feedback/{interview_id}. Fields: skill ratings per required skill (1-5), overall technical rating (1-10), recommendation (PASS/FAIL/STRONG_PASS), free-text notes, strengths, concerns. On submit: update interview.outcome, trigger HRMS-0453 readiness check update.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Create interview_feedback table

- CREATE TABLE interview_feedback: id UUID PK, interview_id UUID UNIQUE FK→interviews.id, tenant_id UUID, candidate_id UUID, submitted_by UUID (interviewer user_id), skill_ratings JSONB (array of {skill_canonical, rating_1_to_5, notes}), overall_rating INTEGER CHECK(1-10), recommendation ENUM('STRONG_PASS','PASS','BORDERLINE','FAIL') NOT NULL, strengths TEXT, concerns TEXT, red_flags TEXT nullable, submitted_at TIMESTAMP, last_updated_at TIMESTAMP

## Step 2: Build feedback form UI

- Route: /technical/feedback/{interview_id}

- Header: 'L1/L2 Interview Feedback — [Candidate Name] — [Job Title]'

- Section 1 — Skill Ratings: for each skill in job.required_skills, show: skill name, 5-star rating (1=Poor to 5=Excellent), small text input for skill-specific notes. Pre-populate with job's required_skills from job record.

- Section 2 — Overall Technical Rating: slider or radio 1-10. Labels: 1-3=Not meeting bar, 4-6=Partially meeting bar, 7-8=Meeting bar, 9-10=Exceeding bar.

- Section 3 — Recommendation: 4 clear radio buttons: STRONG PASS / PASS / BORDERLINE / FAIL. Must select one. FAIL = red highlight.

- Section 4 — Qualitative notes: Strengths textarea (required, min 50 chars), Concerns textarea (optional), Red Flags textarea (optional — shown if FAIL or BORDERLINE selected).

- Submit button: disabled until all skill ratings + overall rating + recommendation + strengths are filled.

## Step 3: Build feedback submission and outcome update

- POST /api/technical/feedback — body: { interview_id, skill_ratings, overall_rating, recommendation, strengths, concerns, red_flags }

- Auth: Technical Interviewer who owns this interview (interviewer_user_id must match).

- Validate: recommendation required. strengths min 50 chars. Overall rating 1-10.

- INSERT interview_feedback

- Map recommendation to interview outcome: STRONG_PASS or PASS → outcome=PASS. BORDERLINE or FAIL → outcome=FAIL.

- UPDATE interviews SET outcome=mapped_outcome, outcome_recorded_by=interviewer_id, outcome_recorded_at=NOW()

- If L1 outcome=FAIL: trigger check — if L2 is scheduled → auto-cancel L2 interview (HRMS-P608 rule: L1 FAIL blocks L2). Notify recruiting team.

- Publish event: interview.feedback_submitted { interview_id, outcome, recommendation }

## Step 4: Build feedback draft save

- Interviewers may not complete feedback in one session. Auto-save draft every 60 seconds to interview_feedback_drafts table.

- On form load: check if draft exists. If yes: restore draft values with notice 'Restoring your draft from [time].'

- On final submit: delete draft.

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: L1 FAIL Auto-Cancels Any Scheduled L2 — Immediate

When interview_feedback with recommendation=FAIL is submitted for an L1 interview: immediately check if L2 interview is scheduled for this candidate+job. If yes: cancel L2 (interviews.status=CANCELLED). Notify candidate via Thunder and notify recruiting team. This is HRMS-P608 hard rule.

↳ Triggered by field: L1 FAIL → L2 auto-cancelled

## BR-02: Strengths Field Required — Min 50 Characters

Interviewers must provide substantive feedback. 'Good candidate' does not meet the bar. Minimum 50 characters on the strengths field enforced at API level (not just frontend).

↳ Triggered by field: strengths min 50 chars

## BR-03: Only the Assigned Interviewer Can Submit Feedback

The POST feedback endpoint checks interviewer_user_id = auth session user. An interviewer cannot submit feedback for another interviewer's interview.

↳ Triggered by field: interviewer_user_id ownership check

[Normal] 2. WHY THIS EXISTS
[Normal] Fact extraction (HRMS-0422) uses LLM to extract all facts from a message. The Response Parser is more specific: when Thunder just asked about a specific field (e.g. 'What is your notice period?'), the parser focuses on extracting that specific field's value from the candidate's reply and converting it to a structured format stored in the candidates table.
[Normal] Raw text 'around 30 days' must become notice_period_days=30 in the database. '18 lakhs' must become current_ctc=1800000. '3 years and 6 months' must become total_experience_years=3.5. This normalization is essential for scoring engines.
[Normal] 3. WHAT YOU ARE BUILDING
[Normal] Build parseFieldResponse() — a focused parser that takes the field Thunder just asked about and the candidate's reply, extracts the specific value, normalizes it to the correct data type, validates it, and updates the candidates table via markFieldReceived().

[Normal] 5. STEP-BY-STEP EXECUTION
[Normal] ▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.
[Normal] Step 1: Build parseFieldResponse() function
[List Bullet] parseFieldResponse(candidate_id, tenant_id, field_name, message_body) → { parsed_value, normalized_value, confidence }
[List Bullet] Use LLM with field-specific parsing prompt. Different prompt per field type.
[List Bullet] Prompt template: 'Extract the {field_label} from this candidate message. Return ONLY valid JSON: { value: string, confidence: 0.0-1.0 }. If the value cannot be determined: { value: null, confidence: 0.0 }. Message: [{message_body}]'
[List Bullet] For numeric fields (salary, experience, notice): also run normalization (see Step 2)
[List Bullet] If parsed confidence < 0.6: do not update the profile field. Log PARSE_LOW_CONFIDENCE. Ask Thunder to clarify.
[List Bullet] If confidence >= 0.6: call markFieldReceived() and UPDATE candidates table with normalized value
[Normal] Step 2: Build field-specific normalization rules
[List Bullet] notice_period_days: parse '30 days'→30, '2 weeks'→14, '1 month'→30, '3 months'→90, 'immediate'→0. Convert all to integer days.
[List Bullet] current_ctc and expected_ctc: parse '18 LPA'→1800000, '18 lakhs'→1800000, '$120k'→120000, '18,00,000'→1800000. Store in base currency units (paise or cents). currency field set from candidate's country.
[List Bullet] total_experience_years: parse '5 years'→5, '3 years 6 months'→3.5, '5+'→5. Store as DECIMAL(4,1).
[List Bullet] location: parse 'based in Chicago'→'Chicago', 'I am in Mumbai'→'Mumbai'. Store as-is after extraction.
[List Bullet] skills: parse comma-separated or bullet-listed skills into array. Normalize capitalization.
[List Bullet] resume_url: set to the S3 URL from HRMS-0427 (not parsed from text — set when file is uploaded).
[Normal] Step 3: Build clarification request when parsing fails
[List Bullet] If parseFieldResponse() returns confidence < 0.6 OR value=null: do not update profile
[List Bullet] Trigger clarification: Thunder sends a follow-up message asking candidate to be more specific
[List Bullet] Clarification messages per field: notice_period_days → 'Could you share your notice period in days or weeks? For example: 30 days, 2 weeks, or 3 months.' current_ctc → 'Could you share your current salary as a number? For example: 18 LPA or $120,000 per year.'
[List Bullet] Log event: CLARIFICATION_REQUESTED { field_name, original_message, candidate_id }
[Normal] Step 4: Wire parseFieldResponse() to qualification conversation
[List Bullet] After each inbound message during QUALIFYING state: HRMS-0425 (Qualification Engine) calls parseFieldResponse() with the field Thunder just asked about
[List Bullet] Parse happens before Thunder sends the next question — if parse succeeds, that field is marked received and Thunder moves to the next one
[List Bullet] If parse fails: Thunder sends clarification instead of next qualification question

[Normal] 6B. BUSINESS RULES
[Normal] ▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.
[Normal] BR-01: Never Store a Value With Confidence Below 0.6
[Normal] Only update candidates table when parseFieldResponse() returns confidence >= 0.6. Low-confidence values go into candidate_memory_facts only (via HRMS-0422) as uncertain data, not into the authoritative profile. This prevents incorrect data corrupting scoring engines.
[Normal]   ↳ Triggered by field: confidence >= 0.6 to update candidates table
[Normal] BR-02: Salary Values Always Stored in Base Units
[Normal] current_ctc and expected_ctc must always be stored as integers in the smallest currency unit. India: paise (1 LPA = 100000 paise). US: cents ($120k = 12000000 cents). Display layer handles formatting. This prevents decimal/formatting bugs in calculations.
[Normal]   ↳ Triggered by field: current_ctc, expected_ctc
[Normal] BR-03: Clarification Is Asked At Most Once Per Field
[Normal] If the candidate provides a low-confidence answer, ask for clarification once. If the second answer is also low-confidence: accept the raw string as-is with low confidence in memory_facts and move to the next field. Never send more than one clarification request per field.

## 2. WHY THIS EXISTS

John Smith messages Thunder on WhatsApp on Monday. He emails on Tuesday. He logs into the portal on Wednesday. These are three separate channels but one person. Without cross-channel merge, there are three separate conversation threads, three separate memory stores, and Thunder greets him as a new contact on each channel.

After HRMS-P101 ensures one candidate record, this story ensures one unified conversation — all channels contributing to a single thread that Thunder reads as one continuous relationship history.

## 3. WHAT YOU ARE BUILDING

Build: (1) Enforce one candidate_conversations record per candidate. (2) All channels write to the same conversation. (3) Conversation timeline shows all channels interleaved chronologically. (4) Thunder's context builder reads from the single merged thread.

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Enforce one conversation per candidate per tenant

- The UNIQUE constraint on candidate_conversations(candidate_id, tenant_id) was created in HRMS-0401. Verify it exists and is enforced.

- Conversation lookup function: getActiveConversation(candidate_id, tenant_id) → conversation_id

- All three channel storage functions (HRMS-0402, 0403, 0404) must use this lookup before inserting messages — always using the canonical conversation_id.

- If getActiveConversation() returns null (brand new candidate): the first message from any channel triggers conversation creation (HRMS-0401 normally handles this, but for inbound-first scenarios like email, it must create the workspace).

## Step 2: Handle inbound-first scenario (candidate contacts BlitzenX before being added)

- Scenario: A candidate emails thunder@blitzenx.com directly before a recruiter adds them to WROS.

- HRMS-0403 inbound email handler: after identity check (HRMS-P101), if candidate_id found but no candidate_conversations exists: create conversation workspace (call HRMS-0401 ConversationInitializationService).

- If candidate_id NOT found: create a new candidate record (status=NEW, email=from_address) AND create conversation workspace. Log SOURCE=EMAIL.

- This handles inbound-first contact gracefully.

## Step 3: Build conversation merge event logging

- When a second (or third) channel is used for an existing candidate: log conversation_events: CHANNEL_ADDED_TO_CONVERSATION { candidate_id, new_channel, message_id }

- This tracks which channels a candidate has used over time

- GET /api/candidates/{id}/channels — returns all channels used by this candidate with message counts: { WHATSAPP: 12, EMAIL: 3, PORTAL: 1 }

## Step 4: Ensure Thunder's context builder reads from merged thread

- HRMS-0432 buildCandidateContext(): the recent_messages load already uses conversation_id — since there is one conversation per candidate, this automatically includes all channels.

- Verify: context.recent_messages contains messages from all channels, not just the channel Thunder is currently replying on.

- Thunder's response references the FULL conversation: if candidate sent their resume via email and then asks a WhatsApp question, Thunder already knows about the resume.

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: One Conversation Per Candidate — No Channel Silos

A candidate can never have two separate conversation_conversations records for the same tenant, regardless of which channel they used to enter the system. All channels write to the same conversation_id.

↳ Triggered by field: UNIQUE constraint: candidate_conversations(candidate_id, tenant_id)

## BR-02: Inbound-First Creates Conversation and Candidate

If a candidate contacts BlitzenX via email or WhatsApp before being added by a recruiter: WROS must automatically create the candidate record and conversation workspace. Never reject inbound contact from an unknown sender — always create and engage.

↳ Triggered by field: inbound-first flow

## 2. WHY THIS EXISTS

Thunder sends messages on WhatsApp and Email in parallel. Over time, it becomes clear that some candidates always reply on WhatsApp but never email, while others do the opposite. Sending every message on both channels wastes budget and can feel spammy. By detecting the preferred channel, Thunder focuses on what works and stops wasting effort on what doesn't.

Channel preference also drives a better candidate experience — if a candidate is a WhatsApp-first person, every Thunder message should lead with WhatsApp.

## 3. WHAT YOU ARE BUILDING

## 5. STEP-BY-STEP EXECUTION

▶  Follow these steps in exact order. If a step is unclear, ask the lead BA — never assume.

## Step 1: Add channel_preference to candidates table

- ALTER TABLE candidates ADD COLUMN IF NOT EXISTS channel_preference ENUM('WHATSAPP','EMAIL','PORTAL') DEFAULT 'WHATSAPP'

- ALTER TABLE candidates ADD COLUMN IF NOT EXISTS channel_preference_confidence DECIMAL(3,2) DEFAULT 0.5

- ALTER TABLE candidates ADD COLUMN IF NOT EXISTS channel_preference_detected_at TIMESTAMP

## Step 2: Build detectChannelPreference() function

- detectChannelPreference(candidate_id, tenant_id) → { channel, confidence }

- Query last 20 inbound messages: SELECT channel, COUNT(*) as reply_count FROM conversation_messages WHERE candidate_id=X AND direction='INBOUND' GROUP BY channel

- Query response speed by channel: for each channel, calculate avg_minutes_to_reply = AVG(inbound.sent_at - preceding_outbound.sent_at)

- Score each channel: reply_count_score (50% weight) + response_speed_score (50% weight)

- reply_count_score: channel with most replies = 100, others proportional

- response_speed_score: fastest avg reply time = 100, slower proportionally lower

- Preferred channel = highest composite score. confidence = (winner_score - second_score) / 100

- If only one channel used: that channel wins with confidence=1.0

- If total inbound < 3: insufficient data, return current preference unchanged

## Step 3: Wire to inbound message flow

- After every inbound message stored: call detectChannelPreference() asynchronously

- If result differs from current candidates.channel_preference: UPDATE candidates SET channel_preference=new_channel, channel_preference_confidence=confidence, channel_preference_detected_at=NOW()

- Publish event: candidate.channel_preference_updated { candidate_id, new_channel, confidence }

- Invalidate candidate context cache (HRMS-0432) so Thunder uses new preference on next message

## Step 4: Use preference throughout Thunder sends

- In QualificationConversationService (HRMS-0425): after qualification complete, send via candidate.channel_preference (not both channels)

- In FollowUpScheduler (HRMS-0441): schedule follow-ups on preferred channel first

- First contact (HRMS-0412, 0413): always both channels (too early to know preference)

- Critical messages (interview confirmation, offer): always both channels regardless of preference

## 6B. BUSINESS RULES

▶  Every rule is non-negotiable. If in doubt, escalate to lead BA — never silently skip a rule.

## BR-01: Critical Messages Always Use Both Channels — Override Preference

Interview confirmations, offer notifications, and joining instructions always send on BOTH channels regardless of channel_preference. The stakes are too high to rely on preference detection alone.

↳ Triggered by field: See Section 5 Step 4

## BR-02: Minimum 3 Inbound Messages Required for Detection

Do not update channel_preference based on less than 3 inbound messages. A single reply on Email after WhatsApp doesn't mean the candidate prefers Email — they may have just checked email once.

↳ Triggered by field: minimum 3 inbound messages
